# React Wrapper (@handsontable/react-wrapper)

## Critical Rules

- **No business logic** in wrappers - data transformation, validation, cell manipulation belongs in `handsontable/src/`
- **Feature parity**: React wrapper must expose identical Handsontable functionality
- **Build core first**: `npm run build --prefix handsontable` - wrappers consume `handsontable/tmp/` not `dist/`
- **Preserve selection** during updateSettings: use `selection.exportSelection()` / `selection.importSelection()`
- Cross-platform scripts: Use Node.js `.mjs` helpers, never bash-only constructs

## Architecture

- `HotTable` (public) -> `HotTableInner` (forwardRef) -> Handsontable instance via `useRef()`
- `SettingsMapper.getSettings()` converts React props -> Handsontable settings
- `useImperativeHandle` exposes the instance
- React portals and context for component-based renderers/editors
- `useHotEditor()` hook for custom editors

## Key Files

- `src/hotTable.tsx`, `src/hotTableInner.tsx`, `src/settingsMapper.ts`
- `src/hotColumn.tsx`, `src/hotEditor.tsx`

## Build & Test

- Build: Rollup 4 (CommonJS, ES, UMD, minified)
- Lint: `npm run lint --prefix wrappers/react-wrapper` (`.eslintrc.js` extends the root config, same
  pattern as `wrappers/vue3`; picked up automatically by root `npm run lint` and CI). `no-use-before-define`
  and the `jsdoc/require-*` rules are off here, as in `handsontable/.eslintrc.js`'s TS/test overrides —
  the former false-positives on hooks closing over a later-declared state setter, the latter doesn't fit
  inline test components. `@typescript-eslint/no-empty-function` allows empty methods/functions
  (editor lifecycle stubs, test doubles).
- Test: `npm run test --prefix wrappers/react-wrapper` (Jest + React Testing Library). `test/useClientDirective.spec.ts` reads the built `es/` and `commonjs/` entries, so build the wrapper first (`npm run build --prefix wrappers/react-wrapper`).
- **Test paradigm:** the presence gate covers `wrappers/**` — a wrapper source change must ship a matching test. The Jest suite here is **jsdom** (props, lifecycle, reactivity). Anything user-visible / real-browser goes to **Playwright E2E** in `tests/e2e/` — see the `handsontable-playwright-e2e` skill (React StrictMode / single-instance gotchas in its `references/wrappers.md`). Local gates + exact rules: `.ai/LOCAL-ENFORCEMENT.md`.

## Common Pitfalls

| Pitfall | What to do instead |
|---|---|
| `arr.push(...largeArray)` with large arrays | Causes stack overflow with 10k+ elements. Use `forEach` loop instead. |
| A source-level `'use client'` on the React wrapper | Rollup strips a program-level directive other than `'use strict'` and warns `Module level directives cause errors when bundled, "use client" was ignored`. The ES and CommonJS builds prepend `'use client';` with `output.banner`. Rollup places that banner before its own `"use strict"`, so it is the first statement of `es/react-handsontable.mjs` and `commonjs/react-handsontable.js` (the `exports['.']` entries). The UMD and minified files are script-tag builds. `addLicenseBanner` owns their `output.banner`, and they do not get the directive. |
| Adding a modern type helper (e.g. `as` key-remapping, TS 4.1+) in `src/types.tsx` | The `.d.ts` build uses this package's own `typescript@3.8.2`, which silently mangles it. `prepare-types.mjs` has to swallow `tsc`'s exit code — TS 3.8.2 cannot parse `handsontable/tmp`'s inline type modifiers or `@types/react`'s `ts5.0` tree, so it reports ~40 parse errors on every run while still emitting every `src/` declaration — and its post-emit checks only catch a *missing* emit, not a mangled one. Define the helper in `handsontable/src` and import it via `handsontable/base`. |
| `Omit`/`Pick` on `GridSettings`/`ColumnSettings` for prop types | These carry a `[key: string]: any` index signature; `Omit`/`Pick` collapses `keyof` to `string` and drops every named option, killing `<HotTable>`/`<HotColumn>` prop autocomplete. Strip it first with `RemoveIndexSignature<T>` (from `handsontable/base`). For column props, derive from `RemoveIndexSignature<GridSettings>` (not core `ColumnSettings`, which is intentionally left loose) and override `data` with `ColumnSettings['data']`. **Then re-add `& { [key: string]: any }`** to the final prop type (`ReplaceRenderersEditors`) — cell-type/plugin options not declared on `GridSettings` (e.g. `correctFormat`, `datePickerConfig`) must stay assignable, and named options keep their real types anyway (the `React.CSSProperties` pattern). Dropping this hatch type-breaks existing configs. |
| Adding a hook callback to `HotColumnProps`, or building column props from `GridSettings` without `OmitHooks` | Hooks run from the grid-level settings only, so `<HotColumn>` must not suggest them. `ColumnGridSettings` wraps `RemoveIndexSignature<GridSettings>` in `OmitHooks` (from `handsontable/base`, defined in core for the TS 3.8 reason above). The `& { [key: string]: any }` hatch keeps a hook passed to a column assignable. No test in this package enforces it: React has no type-test harness yet, and `babel-jest` strips types, so a `keyof HotColumnProps` assertion in a Jest spec is hollow (the hatch makes every name a key). The CI guard is the core `OmitHooks` type test in `settings.types.ts`; verify a change to `ColumnGridSettings` by running a modern `tsc` over a sample `<HotColumn>` and reading the emitted `types.d.ts`. A hook on `<HotColumn>` has no contextual type, so under `noImplicitAny` it fails with TS7006: the change is type-breaking for strict users, and the 19.0 migration guide carries a step for it. Core `ColumnSettings` still carries the hooks, so `columns: [{ afterChange }]` is not covered. |
| Trusting a green `npm run build` for types | The type build hides `tsc` errors — inspect the emitted `types.d.ts` after any `src/` type change. |
| Putting a renderer **component** in `columns[].renderer` (or `settings.columns`) | Only two entry points wrap a component for React: the `renderer` prop on `<HotColumn>` (`hotColumn.tsx`) and on `<HotTable>` (`hotTableInner.tsx`). Both route through `getRendererWrapper()`, which is what supplies the `HotRendererProps` object and the portal. A component reaching core through the `columns` array is never wrapped: core calls it with the positional renderer signature `(instance, TD, row, col, prop, value, cellProperties)`, so destructuring `{ instance, row, value }` reads those keys off the `Core` object and every one of them is `undefined`. It crashes on first paint, inside `AutoColumnSize`'s `GhostTable` measuring pass, so the stack points at the plugin rather than at the column config. Use `<HotColumn data="..." renderer={MyCell} />`. |
| Writing `dataProvider={{ ... }}` inline in JSX with inline callbacks | The wrapper skips a prop equal by content to the value it passed last, but compares functions by reference, so an inline `fetchRows` makes a new value on every render, and a new `dataProvider` object reloads the rows. Create it once (a module constant or `useMemo`). Pinned by `test/dataProvider.spec.tsx`. |
| Forwarding every prop on each render | `SettingsMapper.getSettings` leaves out a prop whose forwarded value equals a copy of the value it passed last (`isSameAsForwarded()`, with the copies in `forwardedSettings`, a `Map` `hotTableInner.tsx` keeps per instance and starts again on init). A setting passed again re-applies the plugin it names, which drops the state the user gave it: Filters' conditions, Pagination's page, a `dataProvider` grid's server total, and a refetch. Compare with the copy, never with the grid's live value: an object the app changed in place is the same reference the grid holds, so the live value hides the change, and with the sheets bar on the live value is the visible sheet's own. Plain objects and arrays are compared by content (`areEquivalentSettingsValue()`, `copySettingsValue()`, both cycle-safe for tree rows with `parent` links), functions and class instances by reference. `data` is always forwarded (`ALWAYS_FORWARDED_SETTINGS`; core's UndoRedo keeps the history when the rows are the ones the grid holds, so an unrelated render does not clear it, pinned by `test/undoRedo.spec.tsx`), and `sheetsBar` is compared by reference (`REFERENCE_COMPARED_SETTINGS`): a new `sheets` array is a new workbook. `<HotColumn>` children write into one array the grid also holds, so `hotTableInner.tsx` compares them with a copy of the last forwarded list (`forwardedColumnsSettings`) and drops a `columns` prop while children exist, so the children keep winning. That only works because a column's renderer and editor stay the same function across renders: `getRendererWrapper()` caches its wrapper per component and `makeEditorClass()` its class per hooks reference; a new one per call made `columns` look changed on every render, which re-initialized the index maps and dropped a server sort. `dataSchema` and `columns` props keep their previous-props comparison. Pinned by `test/settingsMapper.spec.tsx`, `test/forwardedSettings.spec.tsx` and `test/dataProvider.spec.tsx`. |
| Passing `dataProvider` together with `sheetsBar` | A grid-level `dataProvider` is ignored while the sheets bar is on. Put `dataProvider` in each server sheet's `settings`, and keep every `sheets[i].data` reference, and each sheet's `dataProvider` object with its callbacks, referentially stable across re-renders: sheet settings are compared structurally and functions by identity, so a new data array or an inline callback rebuilds the workbook and drops each sheet's cached server state (rows, sort, filters, page). |
| Writing `sheetsBar={{ sheets: [...] }}` inline in JSX | The sheets bar writes renames, added sheets and removals into the `sheets` array it was given, the way the grid writes into `data`. An inline array is a new one on every render, without those changes, so the plugin rebuilds the workbook and the user's tab changes, sort and filters are gone. Keep `sheets` in a constant, `useState` or `useMemo`, and do not copy the plugin's changes into state: the array already holds them. A grid-level prop the visible sheet declares in its own `settings` does not override the sheet: it becomes the value for the sheets without their own (`SheetsBar#updateSheetSettings()` changes a sheet's own). |
| Editing an away sorted sheet's `data` in place with `sheetsBar` and `formulas` | A sheet left sorted, or with moved rows or columns, comes back with the formulas the formula engine holds for it, as long as its `data` is the same array with the same length. A cell changed in place in that array while the sheet is away is not seen. To change it, pass a new `sheets` value, which rebuilds the workbook (sheets added with `addSheet()` are dropped). |
| Forwarding a prop that can be `undefined` (`<HotTable copyPaste={props.copyPaste} />`) | `SettingsMapper.getSettings` drops an `undefined` prop at init and when the previous props had no value for it, so the option keeps its default. An own `undefined` key would shadow the default and switch on-by-default features off. On an update of a prop that had a value, it forwards `Handsontable.DefaultSettings[key]` instead, so the grid matches a fresh mount. `height` and `width` are the exception (`CLEARED_BY_NULL_SETTINGS` in `settingsMapper.ts`): core's `applyAxis()` (`handsontable/src/core/rootSize.ts`) reads `undefined` as "leave the size", so their `undefined` default left the old pixel size on the root element. They are forwarded as `null`, which resets the root's inline size to what a fresh mount gives, so `height={full ? undefined : 400}` clears the height. `getSettings().height` then reads `null`, not the `undefined` of a fresh mount. The Angular wrapper does the same (`clearUnsetSizes()` in `hot-table.component.ts`). Add a key to that list only when core resets it on `null` and ignores `undefined`; for most options `null` is a real value. A hook has no default, so a hook prop that had a callback is forwarded as `null` instead, both when it becomes `undefined` and when it is no longer passed at all (`getSettings()` loops over the previous props for that), and core removes the callback. Only hooks get the not-passed case: an option left out of the props keeps its value, as before. The Vue wrapper differs here: its `prepareSettings` drops `undefined` on every update, so the old value stays, except for a hook. For an option, `null` and `false` are real values and are always forwarded. For a hook, any value but a function or an array is forwarded as `null` on an update, because core ignores it: `afterChange={on && logChange}` gives `false`, which left the callback running. |
| Wiping a cell with `TD.removeChild(TD.firstChild)` before appending the portal container | A row at an exact height (the core `rowHeights` option) keeps the cell's content in a `div.htCellClip` wrapper the grid adds after the renderer runs. The renderer in `hotTableContext.tsx` places the portal container through `getCellContentRoot(TD)` (`helpers.tsx`), which returns that wrapper when it is the cell's only child. Wiping the TD instead detaches the container on every grid render and remounts the component (the #10800 symptom). Pinned by the exact-row case in `test/componentInternals.spec.tsx`. |
| Evicting a cell's portal because the last view-render pass did not paint it | A pass does not paint every shown cell: under `renderMode: 'onChange'` the grid skips the renderer for a cell that did not change, and on a vertical scroll the bottom overlay (`fixedRowsBottom`) gets a fast draw that paints none of its cells (`bottomFastDraw` in Walkontable's `Overlays#refresh`). Those cell elements keep the portal container. `pushCellPortalsIntoPortalManager()` (`hotTableContext.tsx`) passes the portal manager every cached portal, and drops an entry the pass did not paint only when its container is no longer connected (the cell element was removed) or its cell element was painted for another cell in this pass (`markCellPainted()`, fed by a `beforeRenderer` hook in `hotTableInner.tsx`). A connected container is not enough: a renderer that does not clear the element (`baseRenderer` plus a style) leaves the old container in it, and the old component would stay visible in the other cell, in the default `'always'` mode too. Dropping every portal the pass did not paint made React unmount those components, so the cells went blank and lost their state on every edit, scroll, and `render()` (the bottom fixed rows in the default mode too). A row-recycling scroll only happens on a real `scroll` event: in jsdom, set the master `.wtHolder`'s `scrollTop` and dispatch `scroll`. `scrollViewportTo()` plus `render()` is a full draw that repaints every row. Pinned by `test/renderModeOnChange.spec.tsx`. |
| Passing a Handsontable editor class or editor name to `editor` | `editor` renders a React component through a portal, so React called a class as a function component and threw a `TypeError` (`Cannot call a class as a function`, or `cannot be invoked without 'new'` for a native class), and a string rendered a stray DOM element. `isNativeEditor()` (`helpers.tsx`) recognizes a non-empty string, or a function whose prototype has the `BaseEditor` methods and no `isReactComponent`. It does not use `instanceof BaseEditor`, so a second Handsontable copy still matches. `isComponentEditor()` and `createEditorPortal()` skip such a value, and `resolveEditorSetting()` uses it as a fallback `hotEditor` with a one-time `NATIVE_EDITOR_IN_EDITOR_PROP_WARNING`. A name no editor is registered under is dropped after the warning (checked with `getEditor()` in a `try`, never `hasEditor()`: the UMD build maps `handsontable/editors/registry` to `Handsontable.editors`, which has no `hasEditor`): forwarded, it made core throw `No registered editor found` on every selection of the cell, where 18.1 left a dead editor. A `hotEditor` value that names an editor or disables editing still wins. Pinned by `test/nativeEditorWarning.spec.tsx`. |
| Setting a grid-level `editor` or `renderer` fallback on `HotTable` when no prop names one | A same-payload `editor` or `renderer` wins over `type` in core's `extendByMetaType()`, so the old `getEditor('text')`/`getRenderer('text')` fallback gave `<HotTable type="dropdown">` the text editor and renderer, with no arrow. `createNewGlobalSettings()` in `hotTableInner.tsx` leaves an unnamed `editor`/`renderer` out of the payload, and core expands the `type` when the grid is created. Core expands a grid-level `type` again on every `updateSettings()` that names one, and a grid-level option the user set (a same-payload or earlier `editor`/`renderer`) keeps winning over it. `undefined` in a payload means "unset", so when the prop that named an editor or renderer is removed the wrapper sends `undefined` for that key and the current `type` supplies it again, a `type` prop that changes at runtime included. Do not send the creation-time type's editor there instead: core records an explicit value as user-set, so it would pin the editor of a type the grid no longer has (the `createdCellType` workaround that did that is gone). Pinned by the `Grid-level cell type` cases in `test/hotTable.spec.tsx`. |
| Repositioning an `EditorComponent` editor from a wrapper `afterRefreshDimensions` hook | Core moves an open editor after a grid resize through `EditorManager`, which waits out a pending validator and suspended rendering, scrolls the edited cell into view, and only then calls `refreshDimensions()` on the editor instance. `EditorComponent` puts its repositioning function on the instance as `refreshDimensions` in `onOpen`. The `afterScrollHorizontally` and `afterScrollVertically` hooks call the same function directly, with no wait. So it returns at once unless `editor.state` is `STATE_EDITING`, as core `TextEditor#refreshDimensions` does: a cancel during a pending async validator does not stop the validation, and a rejected value then put the closed editor back in edit mode. When the function finds the cell not rendered (scrolled out), it ends the edit with `cancelChanges()`, which resets the editor so the next key starts a new edit. Core `TextEditor` only hides itself there. A bare `close()` runs `onClose` but leaves `isOpened()` true and the `editor` shortcut context active, so the editor never showed again and swallowed keys. A wrapper hook would skip that order and close the editor on a cell that is not rendered. A raw `useHotEditor` editor positions its own element and gets none of this; the cell editor guide says so. Pinned by `test/editorResize.spec.tsx`. |
| Mounting a React editor on `document.body` | Core `#isPathWithinGrid` treats only `rootElement` / `rootPortalElement` (plus the grid's shadow hosts) as inside the grid. After the 18.1 document-mouseup deselect, a body-mounted editor is a foreign click: `setValue` + `finishEditing` run on a closed editor and the cell does not change. Always portal into `hot.rootPortalElement` (the stable host in `HotTableInner`). Keep `mousedown` `stopPropagation` on the editor root as defense in depth. |
| Adding a wrapper spec that imports `hyperformula` or `hyperformula-ui` (as `test/formulaBuilder.spec.tsx` does) | Neither package is declared in this package's `package.json`. Jest finds them only through pnpm's hoisted layout (`node_modules/.pnpm/node_modules`), so `require.resolve` from `test/` under plain Node fails while the spec passes; a lockfile or hoisting change can break it with nothing in this package changing. `hyperformula-ui` ships ES modules only and lives outside this package's root, where `.babelrc` does not reach, so the `jest` block in `package.json` routes it through `test/hyperformulaUiTransform.js` (`babel-jest` with `@babel/preset-env` inline) and exempts it in `transformIgnorePatterns` (the pattern covers the `.pnpm/` path too). Keep both entries when you touch the Jest config. Declaring the two packages as devDependencies is a lockfile change, made in its own commit; `hyperformula-ui` must then match the exact version the other workspace packages pin (`tests/lib/__tests__/hyperformula-ui-pin.test.mjs`). |
