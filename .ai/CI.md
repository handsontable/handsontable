# CI, release, and dependency traps

Read this before you change a workflow or action under `.github/`, the `postbuild` packaging step, the styles build's BOM strip, `pnpm-lock.yaml` or an example lockfile, `pnpm.overrides`, or anything a Dependabot alert touches. Most entries are pinned by a test that fails with the reason; each entry names it.

- CI orchestrators are per-stage: `test.yml` = PRs (+ master push + the rc/stable `workflow_call`); `develop.yml` = the develop push (same reusable modules + trunk-only stages, minus the visual golden seed — that is `visual-seed.yml`, a develop-push workflow with `cancel-in-progress: false`, because develop.yml's cancellation kept the seed from landing and left every open PR comparing against a stale baseline; never add a `visual:` job back to develop.yml, `visual-seed.test.mjs` pins it. That decoupling is also why a *failed* seed is quiet — it is not a required check, not in test-health.yml's list, and no longer reds the Develop run — so `visual-seed.yml` carries a `notify` job that posts a failed seed to Slack through `SLACK_VISUAL_WEBHOOK_URL`; an absent secret is an empty string, so the step skips itself and the hook stays optional;; `visual-nightly.yml` renders the full visual matrix (real wrappers, all themes, all browsers) on develop each weekday night, compares it against the seed and reds on any difference outside the visual quarantine (`visual-tests/visual-quarantine.json`; a quarantined changed capture is listed, not failed); it never writes `base/` — the PR pipeline renders the `pr` tier — `js × {main, main-dark}` on chromium plus a wrapper only when that wrapper's own tree changed — or the `full` tier when the scope router flags `visual-full` (a change under `visual-tests/**` or `examples/next/visual-tests/**`); the routing is `checks.yml`'s `visual-wrappers` and `visual-full` outputs into `visual.yml`'s `tier` and `wrappers` inputs, table in `visual-tests/src/config.mjs`. A theme- or browser-only regression that merges is recorded by the develop seed's own diff, which comments it on the merged PR — the nightly compares against that seed, so what turns it red is a wrapper drifting from js, a flaky or poisoned golden, or a commit whose seed never landed); `publish.yml` = **every** `npm publish` (experimental via a `workflow_run: ['Develop']` chain or an on-demand `workflow_dispatch` from any non-release branch — the dispatch requires ticking the `publish-experimental` checkbox and pauses for an `approvers`-environment sign-off, since npm trusted publishing trusts the workflow *filename* on any ref; rc/stable directly). npm trusted publishing (OIDC) allows **one workflow file per package** and it is pinned to `publish.yml` — never move a publish job to another workflow, and never rename `publish.yml` or the `Develop` workflow name without updating the chain. Never add explicit `permissions:` to develop.yml's module-caller jobs: nested job-level requests (e.g. integration.yml's preview `pull-requests: write`) are validated against the caller grant **statically at run startup**, PR CI cannot see it, and one miss fails every develop push.
- **The runner image is pinned (`ubuntu-26.04`), never `ubuntu-latest`, and every workflow uses the same label.** GitHub moves the floating label to a new Ubuntu release over weeks, so during the rollout a job lands on either image, and the visual goldens (rendered on the runner itself: core in S3 `base/<branch>`, docs in R2 `docs/base/<branch>`) fail at random when seeded on one image and compared on the other. A mixed pin does the same, for example `docs.yml` (the PR compare) on one image and `docs-visual-seed.yml` (the seed) on another. **Bumping the image re-seeds the goldens only if the bump PR triggers both seeds, and it needs a human look at the new render before it becomes the baseline.** Core: a workflow-only PR does not route the Visual module, so touch a file under `visual-tests/**`; the PR then renders the full tier against `base/develop`, a `changed` verdict waits for `visual-approval`, and the develop seed has nothing left to report (it comments only the out-of-`pr`-tier differences). Docs: `docs-visual-seed.yml` runs on the `docs-staging.yml` deploy, whose push trigger watches `docs/**` and `handsontable/package.json`, so touch `docs/**` in the bump PR or dispatch `docs-visual-seed.yml` with `branch: develop` after the merge. Every cache keyed on `runner.os` (`Linux` on every Ubuntu image) also carries `$ImageOS`, read through a `runner-image` step output because the `env` context cannot see runner variables; Playwright downloads Firefox and WebKit per distro release, so a cache saved on one image must not restore onto another. `master` takes the pin from the develop merge at the next release, and `prod-docs/*` branches carry their own `ubuntu-24.04` pin because their Playwright 1.45.x does not support 26.04. `.github/scripts/__tests__/runner-image-pin.test.mjs` pins the single label and the image in every `actions/cache` key.
- **Performance CI uses the single self-hosted runner.** `performance.yml` runs PR comparisons and `performance-tests.yml` records develop goldens; keep both on `runs-on: self-hosted` while it is the only runner service, or their deltas become machine differences. The runner needs Git and a clean checkout. The `gh-pages` deploy blocks are hand-synced. Fetch and read `origin/gh-pages`, use detached worktrees in the `$RUNNER_TEMP` `handsontable-performance-gh-pages.*` namespace, remove abandoned namespace directories before adding a worktree, and keep the prune-and-trap cleanup sequence so a cancelled job cannot lock the baseline branch for the next run. `performance.yml` runs on `pull_request`, so fork-authored code executes on this persistent organization hardware: Settings → Actions → General → **Fork pull request workflows from outside collaborators** must be set to **"Require approval for all outside collaborators"**, since the default (first-time contributors only) still lets a contributor with one merged PR run their branch on the runner unreviewed. `performance-tests.yml` has no fork exposure; it is reached only through the develop push. **Keep the UMD artifact download a job step, never a step of the `performance-run` composite.** A composite step cannot take `timeout-minutes`, and in run 37947963835 `actions/download-artifact` logged "Download artifact has finished successfully" and then never exited, holding the runner for the whole 90-minute job timeout. A healthy download takes 4 to 15 seconds. So `performance.yml` downloads and extracts before it calls the composite, and both workflows make two attempts of 8 minutes each, just above the 6-minute `ListArtifacts` stall that run's own toolkit retry recovered from. The first attempt is `continue-on-error`, and a timeout and an error look the same there (`outcome == 'failure'`). A check after a failed first attempt keeps an archive that lists cleanly, since that run had already written and verified the file when the step stopped exiting, and deletes anything else; the retry runs only when no archive is left. `performance.yml` runs the composite with `if: ${{ !cancelled() }}`, so a failed download or extract still reaches the composite's first step, which stops with the reason in `result.md`, and its `always()` steps publish it in the job summary and the sticky comment. The job timeout is a backstop, not the guard: both jobs allow 126 minutes, enough for setup (the slowest of the 204 successful runs since 2026-09-24 took 19.3 minutes, a 10.7-minute pnpm cache restore), both attempts, and 18 scenarios run one at a time at their 5-minute Playwright timeout, so a run whose scenarios time out still reports which. A healthy run takes about 8 minutes. `.github/scripts/__tests__/perf-artifact-download.test.mjs` pins all of it and derives the job-timeout floor from the Playwright config and the scenario count.
- **`test-health.yml` is the cross-run flake ledger, and it is `workflow_run`-chained on purpose.** It runs after every completed `Tests`, `Develop`, `Publish`, `Visual nightly` or `E2E nightly` run (cancelled ones excepted), downloads the run's `playwright-report-*` (the Playwright JSON report; a green leg uploads it too when a flaky test was under quarantine), `puppeteer-failed-specs-*`, and `visual-compare-*` artifacts (plus the durations family of the next entry, which never enters the ledger) — `visual-compare-*` is the record every visual Compare job uploads (`visual-tests/lib/visual-compare-record.mjs`), a pull request's arriving on its `Tests` run and the nightly's on `Visual nightly`; a seed-tier record is skipped, because a seed's differences are its merge's own, and `Visual seed` is not in the trigger list for the same reason — and appends every flaky or failed test, and every changed visual capture, to `test-health/ledger.json` on `gh-pages`, published at <https://handsontable.github.io/handsontable/test-health/> — per test: 7- and 30-day counts, distinct runs, legs hit, last sighting, and a "needs ticket" flag at 2+ distinct runs in 30 days, the flakiness playbook's line for a fix or migration ticket. A visual capture is one test whatever variants it differed on (the leg is the variant), and its ticket line is 2+ `Visual nightly` runs or 2+ distinct branches in 30 days (`VISUAL_NIGHTLY_WORKFLOW` in the lib; the nightly counts as develop). Nothing in that tier is ever `flaky`, so nights stand in for the functional rule's flaky reruns, and the nightly is one branch, so distinct branches alone could never flag a capture red on two nights. A raw run count would, but the record is written before anyone approves a pull request's change, so it would also flag an intended change on the pull request's second push; distinct branches keep that on one. A pull request's record arrives only when its `Tests` run completes (approved, rejected, or clean): a `changed` verdict holds the run on the approval, the next push cancels it, and cancelled runs are skipped. Two consequences of the trigger. It runs in the base repository's context with a write token whatever started the run, so fork and Dependabot flakes are recorded with **no** fork guard (it is deliberately absent from the guarded-site list in the secret-guarding entry below). And it always runs the copy on the **default** branch, so a change to it is exercised only after it lands on `develop`: use its `workflow_dispatch` with a run id to test it there, and to backfill a run whose artifacts (3-day retention) still exist. It has no `concurrency` group by design — GitHub keeps one pending run per group and cancels the rest, which would drop collections when several runs finish together — and instead re-reads `gh-pages` and re-runs the idempotent collector before every push attempt. The pure half is `.github/scripts/lib/test-health.mjs`; `.github/scripts/__tests__/test-health.test.mjs` also pins the JSON report path across `tests/playwright.config.ts`, `e2e.yml` and the collector, so moving it means changing all three. Hand-recorded observations (a flake seen before the collector existed, or only locally) go in `.github/test-health/seed.json` and are merged on every publish. Quarantined Playwright tests (`tests/AGENTS.md`, Quarantine) show on the page with their entry, so nothing is parked silently; the published files change only when an observation is added or pruned, or when a develop push records its durations, so a pull request's run with nothing new commits nothing.
- **Every Playwright leg uploads its durations, red or green, and the two post-steps that do it run on `${{ !cancelled() }}` with `continue-on-error: true`.** Both Playwright jobs in `e2e.yml` end with `Summarize the Playwright durations` (`node .github/scripts/playwright-durations.mjs --leg <leg>`, the leg being the artifact's suffix) and `Upload the Playwright durations` (`playwright-durations-<leg>`, or `playwright-durations-<leg>-s<i>` for a shard of a sharded leg, the entry after next: one JSON file from `tests/test-results/`, never the HTML report; 3-day retention; `overwrite: true` for re-run attempts). The condition is the rule: a bare `if:` gets `success()` ANDed on and skips every red leg, and `failure()` alone skips every green one. The steps are an instrument and never turn a leg red: `continue-on-error` covers an upload hiccup, and the summarizer ends a leg without a report (Playwright never ran, or did not finish writing it) with a `::notice` (uploading nothing, `if-no-files-found: ignore`) and an unreadable report with a `::warning`. Keep them after the report upload, so that step's `failure()` never sees them. `test-health.yml` records them **from develop pushes only** (`isDevelopPush`: a `push` event on `develop`, so a manual run there does not count), into `test-health/durations.json`, never into the flake ledger, and downloads the family only for such a run. That is what keeps the `gh-pages` push rate where it was: every push starts a Pages build (the legacy builder's soft limit is about 10 an hour, and the perf reports push to the same branch), and recording every pull request run would roughly double the pushes in the busiest hours, so a pull request's run still commits only when it records a flake and its leg files stay in its own run for 3 days. The file keeps its own 30-day retention, a 2 MiB cap that drops the oldest runs first, and per-test rows for each leg's latest push (ranked by run id, then attempt, so a late re-run of an older push never wins), at most half the cap, where a test that failed or was flaky keeps its time from the run before. The reducer itself refuses any other run, so nothing in the file can come from a pull request. A record is keyed by the attempt the summary names (`GITHUB_RUN_ATTEMPT`), because a "Re-run failed jobs" attempt collects the untouched legs' attempt-1 artifacts again. The durations half never stops the ledger: a `durations.json` the collector cannot read, or one of another version, is left as it is (a version bump ships its own migration), the page and the step summary say why, a `::warning` flags the run, and the ledger is recorded all the same. The artifacts are still pull-request input, so the summary check takes only the file at the artifact's root, a UTC ISO start time, a numeric run id and bounded strings, the reducer records only the legs on its table of legs and shard counts (`DURATIONS_LEGS`, pinned to `e2e.yml`'s matrix by a test, so changing a leg or its shards means changing the table), and the page inlines its data with every `<` escaped and builds run links from run numbers alone. The page's "Where the time goes" section reads that file, and so will the e2e budget a later change derives from its per-leg P50/P90 (one vote per push, the last attempt of a re-run leg; left out when a test failed every attempt or no test ran); no gate reads it yet. The pure half is `.github/scripts/lib/playwright-durations.mjs`; `.github/scripts/__tests__/test-health.test.mjs` pins the step shape, the artifact name, the file path and the download filter across `e2e.yml`, `test-health.yml` and the collector, and `.github/scripts/__tests__/playwright-durations.test.mjs` pins the summarizer against a trimmed real report and the stored document's idempotence, pruning and cap. Two consequences of the leg declarations (next entry): the `E2E nightly`'s files upload like every leg's and are never recorded, because a schedule is not a develop push; and since each leg runs the tests its specs declare, a leg's count and wall-clock compare with that leg's own history only, never with another leg's, and not across the merge that introduced the declarations.
- **A long Playwright leg runs in shards, a shard is a job, and the shard-part artifacts are folded back into the leg by name.** `e2e.yml`'s `playwright` job lists every leg and shard as one explicit `include` row (no base axes: an `include` entry keyed on a base `theme × bundle` combination merges into it, so a second row for the same leg would overwrite the first row's shard instead of adding a job), each shard running the same project with `--shard=<i>/<n>` (`fullyParallel` deals at test granularity) at the worker count `tests/playwright.config.ts` pins for CI (`workers: process.env.CI ? 4 : undefined`; a local run keeps the default). A shard's report and durations artifacts carry `-s<i>` after the leg (`playwright-report-main-s2`, `playwright-durations-main-s2`; an unsharded leg's names are unchanged), the summarizer is told its shard (`--shard <i>/<n>`) and records it, and the collector names a part's leg and shard from the artifact (`parseLegArtifact`), then folds a leg's parts into one record (`foldShardParts`): wall-clock = the longest part, since the shards run side by side; counts, summed time and per-test rows add up; the record keeps a row per part and the page lists them. `DURATIONS_LEGS` is the table of shard counts, and a leg with a part missing is recorded as partial, left out of the budget, and keeps the per-test rows it had, like a leg that ran no test; a part for a shard the table does not have is noted and skipped. The record also keeps the span from the first shard's start to the last shard's end (`spanMs`): `wallMs` is what the leg costs when its shards start together, the span is what a pull request waited when they queued. A part without a shard for a leg that runs in shards (a re-run of a push from before the shards) is recorded as the whole leg it is, with a note, or skipped with a note when shard parts are there too; it is never read as shard 1. The budget counts only the records of each leg's latest shape (shards and workers): a 17-minute unsharded 2-worker record beside 5-minute 4-worker shards would make the P50 the shard counts are pinned from meaningless, so a change to either starts the budget input over, and the page marks such records as left out. The flake ledger's `leg` is the project each test names, so a shard never becomes a leg there. The two `!cancelled()` post-steps stay exactly as they were, one pair per shard job. "Re-run failed jobs" re-runs the red shard alone and the collection of that attempt reads the other shards' attempt-1 parts again: the leg is recorded at the latest attempt from the new part and the old ones, and the budget's one-vote-per-push rule takes that attempt. The quarantine reporter decides each shard's exit status on the tests it saw, so its cap of six is counted per shard; `tests/lib/__tests__/quarantine-policy.test.mjs` counts the tree's quarantined tests against the same cap through the leg-declarations block reader (one test at a time: a describe-level `quarantined()` is refused there, and the specs with a quarantine are listed in that test). **An empty shard is not Playwright's own red:** 1.62.1 skips its "No tests found" error whenever `--shard` is set (`lib/runner/index.js`), so the quarantine reporter, which owns the exit status, fails a run that saw no test, naming the shard (`tests/e2e/quarantine-policy.spec.ts` proves it on a one-test project split in two). The engines job keeps 2 workers: `tests/playwright-engines.config.ts` pins `workers: process.env.CI ? 2 : undefined`, because the 4-worker measurement was Chromium's and a contention flake on Firefox or WebKit holds back Visual and the publish paths. Pinned by `.github/scripts/__tests__/e2e-legs.test.mjs` (the shard table, the run line, the artifact names, the worker pin), `.github/scripts/__tests__/playwright-engines.test.mjs` (the engines' worker pin), `.github/scripts/__tests__/playwright-durations.test.mjs` (`DURATIONS_LEGS` derived from the rows, the fold, the span, the shape filter) and `.github/scripts/__tests__/test-health.test.mjs` (the post-steps and the collector's naming); the shard counts are the agreed starting point, from each leg's 2-worker wall-clock scaled by the gain measured on main at 4 workers against the five-minute target, and the e2e budget phase pins them from the P50s the page collects at this shape. The concurrent-job cap was checked when the jobs went from 7 to 11: the organization's Team plan allows 60, and three overlapping runs started 38 E2E jobs at once without a queue.
- **Each Playwright spec runs on the theme × bundle legs it declares; the full matrix runs on the `E2E nightly`, the rc/stable publish path and a master push.** `e2e.yml` takes a `full-matrix` input (boolean, off by default) and sets `HOT_E2E_FULL_MATRIX` from it on the six-leg `Run Playwright E2E` step only, as `'1'` or `''` – `tests/playwright.config.ts` reads it through `parseFullMatrix()` and throws on anything else, so a `true` there would red every leg rather than quietly pick a shape; the engines job takes neither, since every `@cross-browser` spec runs on Firefox and WebKit whatever its leg tags say. `test.yml` forwards `full-matrix: ${{ inputs.test-all || github.ref_name == 'master' }}`: `publish.yml` calls it with `test-all: true` on the rc and stable paths, and the master push has no nightly of its own, while a pull request and `develop.yml`'s push keep the declared shape (the durations and the later budget measure that shape). `e2e-nightly.yml` (`E2E nightly`, cron `30 3 * * 2-6`, clear of the visual nightly, the stability run, the code-quality baseline and the readme) calls `build.yml` with `run-umd: true` and `e2e.yml` with `run-playwright: true` and `full-matrix: true` (and the frozen Jasmine suite's six legs through `run-e2e`, `run-e2e-min` and `jasmine-full-matrix`, the Jasmine entry below; no `run-all`); it is dispatchable from any ref on purpose – a dispatch from a feature branch is the cheapest full-matrix proof run for a change to the declarations, and visual-nightly.yml's ref guard exists only because its compare needs a base branch – and its `notify` job posts to Slack through `SLACK_VISUAL_WEBHOOK_URL` on `failure()` on develop only, with the empty-secret skip; a `pull_request` trigger on its own path validates its graph on a pull request that touches it, with `build` and `e2e` gated off that event, which also makes a temporary run-on-pull-request edit unmergeable. `test-health.yml` chains on `E2E nightly`, so a nightly-only red reaches the ledger with `branch: develop`: it means the spec runs on an axis it did not declare – declare the axis, never quarantine (`tests/scripts/leg-replay.mjs` replays the ledger against the declared tree and names the declaration each off-main red asks for). There is no `--pass-with-no-tests` anywhere: a project whose grep matches nothing is a red "No tests found", never a green job that ran nothing; a shard of a sharded leg that lands on no test is failed by the quarantine reporter, because Playwright 1.62 skips that error under `--shard` (the shard entry above). Pinned by `e2e-legs.test.mjs` (the workflows), `tests/lib/__tests__/leg-declarations.test.mjs` (the declarations and the config's greps) and `tests/e2e/leg-declarations.spec.ts` (what Playwright lists against what the tags say); the rules are `tests/AGENTS.md` → Declaring the legs.
- **`A11y / axe` is one warn-mode job in the Tests pipeline, and a violation never turns it red; its visible gate is the `A11y / axe report` check run.** `a11y.yml` (called by `test.yml`, gated like the Playwright legs on the `build-handsontable-umd` scope, which includes `tests/**`) runs `tests/playwright.a11y.config.ts` inside the pinned Playwright container against the UMD build artifact: axe-core over the curated fixture pages of `tests/a11y/pages.mjs`, on the three themes, compared with the committed baseline `tests/a11y/axe-baseline.json` by `tests/reporters/a11y.ts`. The job is red only for a tooling failure (a fixture that does not load, an invalid baseline, a run that completed no scan), and `ci-gate` needs it, so that red blocks the merge: a scan that silently proved nothing is worse than none. A finding that needs action is a `::warning`, a job-summary row, and a `neutral` conclusion on the `A11y / axe report` check run, which `tests/scripts/a11y-check-run.mjs` posts through the Checks API on the pull request's **head** commit (`A11Y_HEAD_SHA`; a check on the merge commit never shows on the pull request). That is why the job requests `checks: write` at job level, the pattern `docs.yml`'s `angular-types` uses, and why the step carries the canonical fork guard and `continue-on-error`: a fork's token cannot write checks, and the check reports, it never decides the job. Only `CI Gate` is required, so a neutral or failed check never blocks a merge by itself. The stock axe HTML report (`axe-html-reporter`) is uploaded unzipped (`archive: false`, so the artifact is named after the file and opens in the browser from the run page) and linked from the job summary and the check run. It stays one job on purpose (the run has about fifty already and the scan is a minute long), and its artifacts (`a11y-axe-results`, `a11y-report.html`) are named outside the `playwright-report-*` glob, so `test-health.yml` never reads a scan as a flake. The flip to blocking is `A11Y_MODE` in `tests/lib/a11y-baseline.mjs`; the policy and the baseline schema are `tests/AGENTS.md`, "A11y: the axe scan and its baseline". Pinned by `.github/scripts/__tests__/a11y-workflow.test.mjs` (the module's one job, its permissions and head-commit env, its container, its run step, both uploads and the check-run step, the caller's gate and the CI Gate edge, the config's shape), `.github/scripts/__tests__/fork-guards.test.mjs` (the check-run step's guard) and the tests under `tests/lib/__tests__/` (the baseline's shape, the mode constant, the comparator, the check run's payload).
- **The frozen Jasmine suite runs one leg on a pull request and a develop push, `E2E / UMD (theme: main)`; its six legs run on the `E2E nightly`, the rc/stable publish path and a master push.** `e2e.yml`'s `puppeteer` job keeps its scope gate (`run-all || run-e2e || run-e2e-min`; the e2e and e2e-min filters are identical, so one gate decides whether the leg runs at all) and takes a `jasmine-full-matrix` input (boolean, off by default, declared beside `full-matrix`). Each matrix axis is `${{ fromJSON(inputs.jasmine-full-matrix && '<six-leg JSON>' || '<one-leg JSON>') }}`: `&&`/`||` return their operands, so the input picks the three themes × UMD / UMD.min or `main` × UMD alone, and `test:production` (the minified bundle) runs in the full matrix only. The literals are JSON on one line and carry no space after a colon on purpose – a `: ` inside a plain YAML scalar ends the scalar. `test.yml` forwards `jasmine-full-matrix: ${{ inputs.test-all || github.ref_name == 'master' }}`, exactly as it forwards `full-matrix`; `develop.yml` forwards neither, so the develop push runs the one leg; `e2e-nightly.yml` sets `run-e2e: true`, `run-e2e-min: true` and `jasmine-full-matrix: true` beside the Playwright inputs – one nightly carries both suites, and a suite that needs a full-matrix night extends it rather than adding a third. Nothing in the record changes: `HOT_E2E_LEG` is still the bundle label, the runner still appends the theme, and `puppeteer-failed-specs-<label>-<theme>` uploads on `failure()` from one leg or six, so the ledger's `jasmine` tier reads the nightly's records with `branch: develop`. A Jasmine spec red on the nightly and green on pull requests fails on another theme or on the minified bundle, and the record's isolation verdict decides the answer: `passes alone` (order-dependent) is a migration ticket under the ledger rule; `fails alone` is fixed or migrated before the next RC cut, because `publish.yml` reaches `test.yml` with `test-all: true` on the rc and stable paths, the six legs run there, and `first-rc-publish` / `rc-publish` need them green (`handsontable/.ai/TESTING.md`, "The Jasmine suite is frozen"). Neither is a leg added back to pull requests. The leg count moved a gate with it: the chained `experimental` npm publish (`publish.yml`'s `pre-release`, after a green `Develop` run) is now held by one Jasmine leg instead of six, while the rc/stable publish still has all six. Pinned by `e2e-legs.test.mjs`: both literals by value, the forwarding, the nightly's inputs, the record's name, and the six-leg shape held equal to the Playwright matrix (the parity the two jobs used to have on every run, now on the full-matrix runs).
- `manual-qa.yml` is a tickbox-armed manual gate inside the Tests DAG: ticking "MANUAL QA NEEDED" in the PR description makes its `sign-off` job wait on the **`manual-qa` environment** approval (designated reviewers; self-review allowed by decision — see the `visual-approval` bullet), which holds CI Gate through its `needs` edge — unticked PRs skip the module (skipped, never a misleading green, no runner spent). The box is read live but **per run**, when the Checks scope router evaluates it: ticking or unticking later needs a "Re-run all jobs" to re-decide, in either direction, so a box ticked after a green run leaves the PR mergeable until someone re-runs it (a known limitation — the alternative was a label/arming workflow, dropped as too much machinery for the value). The sign-off job **fails closed** — it asserts an approval is recorded for the run via the approvals API, so an unprotected or drifted `manual-qa` environment turns CI Gate red instead of silently waving PRs through. The template line's wording is the router's regex contract — don't reword either side; `.github/scripts/__tests__/manual-qa-gate.test.mjs` pins the two together. The environment must exist **with required reviewers** before the first ticked PR — a job referencing a missing environment auto-creates it unprotected, and the gate would wave everything through. The red `Requires Manual QA` label is applied by hand (the `pr-creation` skill instructs it), like every other label here: GitHub's `actions/labeler` matches changed paths, not PR-body text, so there is no declarative option and a workflow was not worth the lines.
- **A job `if:` with no status-check function gets an implicit `success()`, so a condition that only wants to run when its dependency FAILED never runs at all.** GitHub's default job condition is `success()`. Writing an `if:` does not replace it — writing an `if:` that *contains* one of `always()`, `!cancelled()`, `failure()` or `success()` replaces it. Without one, `success()` is ANDed on, so `if: ${{ needs.<job>.result == 'failure' }}` asks for a job that both succeeded and failed, and is simply unreachable. It fails silently and in the worst direction: the job reports `skipped`, which is indistinguishable from the skip you intended, and nothing goes red. That is how `visual-seed.yml`'s `notify` job shipped a Slack alert for a failed seed that could never fire. Every other `needs.<job>.result` condition in this repository carries a function — `publish.yml`'s nine gates, `docs.yml`'s `functional` — and `publish.yml`'s `first-rc-notify`, `rc-notify` and `stable-notify` are the exact shape to copy: `!cancelled() && needs.<job>.result == '<state>'`. The rule was written down before this, but only inside the workflows that already got it right (`visual.yml`'s `approve` and verdict steps, `visual-stability.yml`'s upload), which is why it did not travel. `.github/scripts/__tests__/job-status-functions.test.mjs` now sweeps every workflow and fails with the offending job named, so it travels mechanically instead.

- **A release cut must never regenerate `pnpm-lock.yaml`.** The lockfile records `specifier: workspace:^` for every in-repo dependency and never a package's own version, so a version bump cannot legitimately change it — and 14 specifiers are `latest`, which re-resolve to whatever the registry serves that day. Manifests stay out of the audit loop, because `npm audit` needs a lockfile and a leaf directory has none. - **The minified CSS is BOM-stripped at emit, and it must stay that way.** sass writes `@charset "UTF-8"` into `handsontable.css` because the themes contain a non-ASCII glyph. From **postcss 8.5.24** on, the `css-loader` → `CssExtractRspackPlugin` → `LightningCssMinimizerRspackPlugin` chain turns that at-rule into a UTF-8 BOM instead, and it lands **after** the preserved `/*!` license banner (byte 1662), not at offset 0 — which is what makes it dangerous. A *leading* BOM is stripped by the CSS decoder and by nothing else; one at a non-zero offset is stripped by neither, and U+FEFF is an ident code point in CSS rather than whitespace, so it fuses with the selector that follows. The first rule, `.ht-root-wrapper`, becomes `\uFEFF.ht-root-wrapper` and silently stops matching: the grid's root wrapper loses `display:flex`, `position:relative` and `height:100%`, cells stop receiving pointer events and popovers mis-anchor. **There are two consumers and both break.** `css-to-js-export-plugin.js` reads the file with `fs.readFileSync(path, 'utf8')` — which does not strip a BOM in Node — and `JSON.stringify`s it into `src/styles/handsontableStyles.{js,ts}`, so every bundle that inlines the runtime theme string carries it; and `handsontable/styles/handsontable.min.css` itself ships corrupted to anyone who loads the minified stylesheet directly. Only the second was ever observed, as three `dblclick` timeouts and a popover-position assertion on the `full`/`.min` E2E legs, which is why it first read as an unrelated bundle-axis flake rather than a CSS regression. `strip-css-bom-plugin.js` now removes the BOM from the emitted asset in `.config/styles-production.js`, before `addCssToJsExport` reads it back — registration order is load-bearing, since both are `afterEmit` taps — and the export plugin repeats the strip as a belt to those braces. Verified at postcss 8.5.28: the emitted stylesheet is byte-identical to the 8.5.23 output and both inlined exports are clean. This is why the root override is `postcss: '^8.5.23'` and not a cap: `>=8.5.18` is what GHSA-r28c-9q8g-f849 requires and `>=8.5.23` is what GHSA-fxqj-rqcc-2cmp raised it to, and the BOM no longer constrains the upper bound. **Do not reintroduce a `<8.5.24` cap** — it admits exactly one published version, so the next postcss advisory would leave no satisfiable range. - **`.github/dependabot.yml` is security-only, and `allow`/`ignore`/`target-branch` must never come back.** Security updates run only when "Dependabot security updates" is on in the repository settings (admin-only; it was off while the alerts piled up), and then for every manifest in the dependency graph; the config only groups and filters them. `allow` and `ignore` filter *security* updates as well as version updates, so the old single block with `allow: @playwright/test` would have blocked every root fix even with the setting on, and `target-branch` drops the block's options from security updates. One `directories` block lists every lockfile directory: the root pnpm workspace, `performance-tests`, and `examples/next/{docs,visual-tests}/*` (globbed). It sets `open-pull-requests-limit: 0` (version updates off, security updates unlimited) and a `groups` entry with `applies-to: security-updates`. With a group on a `directories` block, Dependabot groups security fixes across all listed directories of one ecosystem, so every fix lands in **one PR**, and one fix that fails CI holds back the rest until it is bumped by hand (Dependabot then rebases it out of the group). Playwright (`@playwright/*`, `playwright`, `playwright-core`) is excluded from the group and gets its own security PR, because the catalog version and the `e2e.yml` container tag move in one PR, which Dependabot cannot do (`playwright-version-sync.test.mjs`); that PR always needs the tag bump added by hand. Add a lockfile and you add it here; every directory a pattern matches needs a committed lockfile, or Dependabot opens manifest-only PRs that fail the frozen-lockfile install. Workspace globs in those manifests must be plain (`"*"`): dependabot-core matches workspaces with `File.fnmatch?` and no extglob support, so the old `@(!(node_modules))/` in the nine example trees expanded to nothing and Dependabot saw only an empty root manifest. The Angular postinstall linker (`examples/scripts/link-packages.mjs`) reads the same field; it expands entries through `expandWorkspaceDirs` (directories holding a `package.json`, as npm does), because a raw `glob("*")` also returns the framework's own manifests and `node_modules` (`examples-workspace-dirs.test.mjs`). A fix in `examples/next/visual-tests/*` renders the `visual-full` tier on the grouped PR; that cost is accepted (see the `visual-full` comment in `checks.yml`). Pinned by `dependabot-coverage.test.mjs`.
- **Dependabot remediation runs through two different override mechanisms, and the npm one silently no-ops.** Nearly every alert lands on a *transitive* dependency, so bumping a declaration is rarely the lever. The monorepo tree is governed by `pnpm.overrides` in the root `package.json` — scope each entry as narrowly as the advisory (a bare name where one major is installed, `name@<major>` where several are, `parent>child` where only one consumer is affected), then `pnpm install --lockfile-only`. The `examples/next/<category>/<framework>/` trees are **separate npm workspaces with their own committed `package-lock.json`**, which inherit nothing from the root; they need an `overrides` block in the framework-level `package.json`. **`performance-tests/` is a third such tree** — npm-managed with its own committed lockfile, equally outside `pnpm.overrides`. It resolves patched versions today, but a remediation sweep that fixes only the `examples/next` trees has missed one. The trap: `npm install` applies a *new* `overrides` entry only when it re-resolves from scratch. With a valid `package-lock.json` present, or with a `node_modules/` on disk (including a per-example `<example>/node_modules/`, which is easy to miss), npm prints `up to date` and ignores the block, so the lock looks regenerated while the vulnerable version stays pinned. The sanctioned way into that state is `node ./scripts/clean-subpackages.mjs next --reset-lockfiles` from `examples/`, which removes the nine framework lockfiles **and** every `node_modules` under those trees — the per-example ones included — so the reinstall that follows re-resolves from scratch and honours the block. Run it, review the diff, land it on `develop` as its own change. **That full re-resolve is the expensive option, so weigh it against the bullet above**: it floats the whole tree (61-211 packages per lock in DEV-2772, `handsontable` 18.0.0 → 18.1.0 among them, which then broke the react demos' pinned `typescript@4.2.4` on the grid's own inline `type` imports), and those trees ship in no bundle, which is exactly why their audit is report-only. A **direct** dependency bump in a leaf manifest — the usual security fix there, e.g. `vite` — needs none of this: a plain `npm install` with the lockfile left in place picks it up and re-resolves nothing else. Reach for the throwaway re-resolve only when the fix genuinely has to travel through `overrides`, and say in the PR why the float was worth it. After any lockfile work, confirm the compile floor did not move: `core-js`, `hyperformula` and `typescript` must be byte-identical, and `browserslist`/`caniuse-lite` may only move when an advisory demands it. `esbuild` must stay byte-identical inside core's tree (`pnpm why esbuild --filter handsontable` prints nothing today; core builds with swc and rspack), while the copies the Angular wrapper's `@angular/build` and the docs' astro and `vite` pull in may take an advisory patch, preferably by bumping their direct parent and otherwise through an exact-version selector such as `esbuild@0.28.0` (`BROWSERS_LIST` is pinned integers, so caniuse data cannot shift the target — see the ES-floor entry in the root `AGENTS.md`).

- **A bot pull request's token is a real trade-off, and `docs-sync.yml` uses `GITHUB_TOKEN`.** A pull request opened by `GITHUB_TOKEN` does **not** trigger `pull_request` workflows, so it gets no CI at all — the reason a bot PR is often opened with a GitHub App token (as `publish.yml` mints from `RELEASE_APP_*`). `docs-sync.yml` deliberately goes the other way: it grants `GITHUB_TOKEN` the `contents`/`pull-requests`/`issues` write scopes per-workflow (`issues: write` is the Issues API, which both the `docs-sync` labels and the hold comment need), the pattern `handsontable/examples`' import workflows use — no App to install or keep permissioned. The cost is that the sync pull request gets no CI (docs lint, build, preview): there is no run to "re-run", so a maintainer **closes and reopens** the pull request (or pushes a commit) to fire CI — and if the `prod-docs/*` base has any *required* status check, a zero-run PR is unmergeable, making that close/reopen mandatory, not optional. Two pre-flight settings gate the first live run and are invisible to the code: Settings → Actions → General → **"Allow GitHub Actions to create and approve pull requests"** must be on at **both** repo and org level (the `permissions:` block does not override it — `gh pr create` 403s otherwise), and `DOCS_SYNC_REVIEWERS` must hold plain usernames (`GITHUB_TOKEN` cannot resolve a team slug, and one in that variable fails the whole `gh pr create`). The App route was tried first and abandoned: the `RELEASE_APP` App lacked `issues: write`, so the first live run failed on `gh label create` with `403 Resource not accessible by integration`, and widening an App's permissions needs an org owner. Weigh both when adding a new bot. The `docs-sync/*` branches are owned by that workflow: it rebuilds them from the target tip on every run and stops only while a branch carries a commit whose committer is not `docs-sync[bot]` (the script sets that committer itself, independent of the token).
- **`docs/content-type-check/` gates the CHANGED docs examples only, by comparing each file against its own base version (DEV-3420).** The `content-types` job in `docs.yml` (routed by the `docs-content-types` filter in `checks.yml`, PR-only) builds just the core types (`npm run build:types --prefix handsontable`) and runs `docs/content-type-check/check.mjs`. It compiles every changed `javascript/*.ts`, `react/*.tsx` and `vue/*.vue` example twice (head, and the base revision's copy of the whole example folder under `docs/content-type-check/.tmp/base/`, so a changed sibling helper is compared too) against the same types, one program per example folder, and fails only on errors the head has beyond the base, compared per file by code and message shape, not by line. It is deliberately not a whole-tree gate: many examples carry old errors, so a full gate would need a baseline decision first. Five traps. (1) The base is the merge ref's first parent (`git rev-parse HEAD^1`, resolved in `.github/actions/docs-content-typecheck/action.yml`; the job checks out `fetch-depth: 2`), never the payload's frozen `base.sha`, per the blocking-gate rule above: a re-run after the base moved would otherwise list every example other pull requests changed since. A non-merge checkout falls back to its last commit with a warning. (2) The script uses built-in Node modules only and resolves `tsc` from `docs/` and `vue-tsc` from `wrappers/vue3` (both already devDependencies, installed by the root `pnpm install` through `setup-workspace`), so nothing new is added to any manifest; a dependency imported there would break any path that skips the install, so do not add one (no `chalk`). (3) The job is not a prebuilt-artifact job: it needs only `handsontable/tmp/*.d.ts`, so do not widen its build to the full package. (4) A core change with no example change has nothing to check, so the filter omits `handsontable/**` on purpose, and a core export removal that breaks an example import is not caught. (5) `test.yml` starts the Docs module only on the `docs` flag, so every `docs-content-types` glob must also match the `docs` filter in `checks.yml` (the wiring test asserts it); an action-only change reaches the job through the `./.github/actions/docs-content-typecheck/**` entry in `docs`. The error key is the code, headline and whitespace-normalized elaboration lines (positions stripped, single-quoted names and types removed so a rename or a new property keeps an old error's key), so two `TS2769` overload failures with different wording do not cancel. A compiler config error (`TS5xxx`, `TS6xxx`) exits 2, never a pass. Known limits of the rule: fixing one error and adding another with an identical code, message and elaboration in the same file nets to zero; a newly added unresolved import of a package that is already unresolved in that file is flagged only by count, so the second one fails; and a failing `content-types` job also skips `preview`, the same as `angular-types`.
