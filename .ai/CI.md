# CI, release, and dependency traps

Read this before you change a workflow or action under `.github/`, the `postbuild` packaging step, the styles build's BOM strip, `pnpm-lock.yaml` or an example lockfile, `pnpm.overrides`, or anything a Dependabot alert touches. Most entries are pinned by a test that fails with the reason; each entry names it.

- CI orchestrators are per-stage: `test.yml` = PRs (+ master push + the rc/stable `workflow_call`); `develop.yml` = the develop push (same reusable modules + trunk-only stages, minus the visual golden seed — that is `visual-seed.yml`, a develop-push workflow with `cancel-in-progress: false`, because develop.yml's cancellation kept the seed from landing and left every open PR comparing against a stale baseline; never add a `visual:` job back to develop.yml, `visual-seed.test.mjs` pins it. That decoupling is also why a *failed* seed is quiet — it is not a required check, not in test-health.yml's list, and no longer reds the Develop run — so `visual-seed.yml` carries a `notify` job that posts a failed seed to Slack through `SLACK_VISUAL_WEBHOOK_URL`; an absent secret is an empty string, so the step skips itself and the hook stays optional;; `visual-nightly.yml` renders the full visual matrix (real wrappers, all themes, all browsers) on develop each weekday night, compares it against the seed and reds on any difference; it never writes `base/` — the PR pipeline renders the `pr` tier — `js × {main, main-dark}` on chromium plus a wrapper only when that wrapper's own tree changed — or the `full` tier when the scope router flags `visual-full` (a change under `visual-tests/**` or `examples/next/visual-tests/**`); the routing is `checks.yml`'s `visual-wrappers` and `visual-full` outputs into `visual.yml`'s `tier` and `wrappers` inputs, table in `visual-tests/src/config.mjs`. A theme- or browser-only regression that merges is recorded by the develop seed's own diff, which comments it on the merged PR — the nightly compares against that seed, so what turns it red is a wrapper drifting from js, a flaky or poisoned golden, or a commit whose seed never landed); `publish.yml` = **every** `npm publish` (experimental via a `workflow_run: ['Develop']` chain or an on-demand `workflow_dispatch` from any non-release branch — the dispatch requires ticking the `publish-experimental` checkbox and pauses for an `approvers`-environment sign-off, since npm trusted publishing trusts the workflow *filename* on any ref; rc/stable directly). npm trusted publishing (OIDC) allows **one workflow file per package** and it is pinned to `publish.yml` — never move a publish job to another workflow, and never rename `publish.yml` or the `Develop` workflow name without updating the chain. Never add explicit `permissions:` to develop.yml's module-caller jobs: nested job-level requests (e.g. integration.yml's preview `pull-requests: write`) are validated against the caller grant **statically at run startup**, PR CI cannot see it, and one miss fails every develop push.
- **Performance CI uses the single self-hosted runner.** `performance.yml` runs PR comparisons and `performance-tests.yml` records develop goldens; keep both on `runs-on: self-hosted` while it is the only runner service, or their deltas become machine differences. The runner needs Git and a clean checkout. The `gh-pages` deploy blocks are hand-synced. Fetch and read `origin/gh-pages`, use detached worktrees in the `$RUNNER_TEMP` `handsontable-performance-gh-pages.*` namespace, remove abandoned namespace directories before adding a worktree, and keep the prune-and-trap cleanup sequence so a cancelled job cannot lock the baseline branch for the next run. `performance.yml` runs on `pull_request`, so fork-authored code executes on this persistent organization hardware: Settings → Actions → General → **Fork pull request workflows from outside collaborators** must be set to **"Require approval for all outside collaborators"**, since the default (first-time contributors only) still lets a contributor with one merged PR run their branch on the runner unreviewed. `performance-tests.yml` has no fork exposure; it is reached only through the develop push.
- **`test-health.yml` is the cross-run flake ledger, and it is `workflow_run`-chained on purpose.** It runs after every completed `Tests` or `Develop` run (cancelled ones excepted), downloads the run's `playwright-report-*` (the Playwright JSON report; a green leg uploads it too when a flaky test was under quarantine) and `puppeteer-failed-specs-*` artifacts, and appends every flaky or failed test to `test-health/ledger.json` on `gh-pages`, published at <https://handsontable.github.io/handsontable/test-health/> — per test: 7- and 30-day counts, distinct runs, legs hit, last sighting, and a "needs ticket" flag at 2+ distinct runs in 30 days, the flakiness playbook's line for a fix or migration ticket. Two consequences of the trigger. It runs in the base repository's context with a write token whatever started the run, so fork and Dependabot flakes are recorded with **no** fork guard (it is deliberately absent from the guarded-site list in the secret-guarding entry below). And it always runs the copy on the **default** branch, so a change to it is exercised only after it lands on `develop`: use its `workflow_dispatch` with a run id to test it there, and to backfill a run whose artifacts (3-day retention) still exist. It has no `concurrency` group by design — GitHub keeps one pending run per group and cancels the rest, which would drop collections when several runs finish together — and instead re-reads `gh-pages` and re-runs the idempotent collector before every push attempt. The pure half is `.github/scripts/lib/test-health.mjs`; `.github/scripts/__tests__/test-health.test.mjs` also pins the JSON report path across `tests/playwright.config.ts`, `e2e.yml` and the collector, so moving it means changing all three. Hand-recorded observations (a flake seen before the collector existed, or only locally) go in `.github/test-health/seed.json` and are merged on every publish. Quarantined Playwright tests (`tests/AGENTS.md`, Quarantine) show on the page with their entry, so nothing is parked silently; the published files change only when an observation is added or pruned, so a run with nothing new commits nothing.
- `manual-qa.yml` is a tickbox-armed manual gate inside the Tests DAG: ticking "MANUAL QA NEEDED" in the PR description makes its `sign-off` job wait on the **`manual-qa` environment** approval (designated reviewers; self-review blocked), which holds CI Gate through its `needs` edge — unticked PRs skip the module (skipped, never a misleading green, no runner spent). The box is read live but **per run**, when the Checks scope router evaluates it: ticking or unticking later needs a "Re-run all jobs" to re-decide, in either direction, so a box ticked after a green run leaves the PR mergeable until someone re-runs it (a known limitation — the alternative was a label/arming workflow, dropped as too much machinery for the value). The sign-off job **fails closed** — it asserts an approval is recorded for the run via the approvals API, so an unprotected or drifted `manual-qa` environment turns CI Gate red instead of silently waving PRs through. The template line's wording is the router's regex contract — don't reword either side; `.github/scripts/__tests__/manual-qa-gate.test.mjs` pins the two together. The environment must exist **with required reviewers** before the first ticked PR — a job referencing a missing environment auto-creates it unprotected, and the gate would wave everything through. The red `Requires Manual QA` label is applied by hand (the `pr-creation` skill instructs it), like every other label here: GitHub's `actions/labeler` matches changed paths, not PR-body text, so there is no declarative option and a workflow was not worth the lines.
- **A job `if:` with no status-check function gets an implicit `success()`, so a condition that only wants to run when its dependency FAILED never runs at all.** GitHub's default job condition is `success()`. Writing an `if:` does not replace it — writing an `if:` that *contains* one of `always()`, `!cancelled()`, `failure()` or `success()` replaces it. Without one, `success()` is ANDed on, so `if: ${{ needs.<job>.result == 'failure' }}` asks for a job that both succeeded and failed, and is simply unreachable. It fails silently and in the worst direction: the job reports `skipped`, which is indistinguishable from the skip you intended, and nothing goes red. That is how `visual-seed.yml`'s `notify` job shipped a Slack alert for a failed seed that could never fire. Every other `needs.<job>.result` condition in this repository carries a function — `publish.yml`'s nine gates, `docs.yml`'s `functional` — and `publish.yml`'s `first-rc-notify`, `rc-notify` and `stable-notify` are the exact shape to copy: `!cancelled() && needs.<job>.result == '<state>'`. The rule was written down before this, but only inside the workflows that already got it right (`visual.yml`'s `approve` and verdict steps, `visual-stability.yml`'s upload), which is why it did not travel. `.github/scripts/__tests__/job-status-functions.test.mjs` now sweeps every workflow and fails with the offending job named, so it travels mechanically instead.
- **The visual gate's approval is the `visual-approval` environment, and it fails closed like `manual-qa`.** When `Visual / Compare` finds differences, `visual.yml`'s `approve` job waits on that environment; a reviewer approves or rejects the pending deployment on the run page (the deployment URL opens the diff report), and `CI Gate` holds through its `needs` edge until then. Approval is per run — a push re-asks — and all-or-nothing for the build. The job asserts an approval is recorded via the approvals API, so a missing or unprotected environment turns the job red instead of waving differences through; **the environment must exist with required reviewers, and with "Prevent self-review" ticked, before the first pull request with visual differences runs**, or that pull request is stuck red until an admin creates it. The tick is not optional: the assertion cannot tell a self-approval from any other (it is a recorded approval either way), so without it the person who pushed the branch signs off their own differences — the rubber-stamping this replaces. `manual-qa`'s environment is configured the same way. The `visual-approved` label, `visual-cleanup.yml` and `visual-approval-rerun.yml` are gone; **delete the label from the repository's label list as part of the cutover** — nothing acts on it any more, so one left in the picker is a button that silently does nothing and whoever applies it waits for a re-run that never comes. Do not bring it back: it was content-blind, rubber-stamped on 40% of gated PRs, and unusable on fork runs.
- **`postbuild` composes the publishable package, and it is strict by default.** `handsontable/scripts/prepare-package-for-publish.mjs` copies the `handsontable.copy` list into `handsontable/tmp/` and regenerates the `exports` map from that merged tree, so the map can never describe a different tree than the one that ships. It fails when a copy entry did not land or when an `exports` rule matches no file. Two consequences. First, **the npm lifecycle runs `postbuild` automatically after `npm run build` in `handsontable/`** (pnpm 10 runs it too) — every new full-build call site inherits the strict gate without opting in, while calling the task runner directly (`node scripts/run.mjs build`) never triggers it, which is how a stale `tmp/package.json` survives a local rebuild. Second, only a tree that **never reaches a registry** may skip the checks, through `npm run postbuild:partial`: today the `es-cjs` job in `build.yml` (it runs before the UMD bundles and the theme stylesheets exist), the screenshot composition in `visual.yml`, and the on-demand stability matrix in `visual-stability.yml`, which composes the same ES + CJS tree on a dispatch that has no Build artifacts to download. `handsontable/test/__tests__/previewPackaging.unit.js` pins both lists — strict and partial — but only for the call sites that name `postbuild` in `.github/workflows/**` or `.github/actions/**`. The lifecycle callers are invisible to it by construction (`emitted-types.yml`, `docs-angular-typecheck.yml` and the `docs-angular-typecheck` action all run `npm run build --prefix handsontable`): they inherit the strict gate silently, and they pass only because they build the whole package from source. A job that builds part of it and then runs `npm run build` inherits a red gate with no test to warn it. One half of that is now checked: `.github/scripts/__tests__/partial-packaging.test.mjs` asserts that every **job** running `postbuild:partial` also runs `build:types` and `downlevel:types`, because the regenerated `exports` map names the type declarations and the check fails on eight missing `.d.ts`/`.d.mts` files without them. `visual.yml`'s artifact-fallback path shipped without those tasks in #13210 and stayed latent until the first pull request that changed `visual-tests/**` without touching `handsontable/**` — the only shape that skips `Build`, leaves the artifacts absent, and actually takes the fallback. The same fallback had a second gap with a narrower trigger: the ES+CJS branch built types but not the language packs, while the UMD artifact carries `dist/` and `styles/` only, so a pull request whose scope ran `Build / UMD` but skipped `Build / ES + CJS` (a `visual-tests/**` + `performance-tests/**` + `tests/**` change) composed a `tmp/` with no `languages/all.js` and `postbuild:partial` failed on the `./languages/all` require target. The fallback now runs `build:languages` and `build:languages.min` like `build.yml`'s ES+CJS job, and the partial-packaging test asserts `build:languages` beside the two type tasks. One copy entry is worth knowing on its own: **the npm README is the repository root `README.md`**, reached through the `../README.md` entry the same way `../CHANGELOG.md` and `../LICENSE.txt` are. There is deliberately no `handsontable/README.md`. There used to be, as a hand-maintained second copy with nothing syncing it to the root, and it drifted far enough to lose the Themes sections and keep a stale copyright year on the npm landing page. Never re-add one; `previewPackaging.unit.js` fails if you do.
- **Fork pull requests and Dependabot pull requests both run on a read-only `GITHUB_TOKEN` with no Actions secrets.** Guard any step that writes through the API (a PR comment, a check run, a label), pushes to a repository ref, or genuinely *fails* without a secret. Unguarded, it 403s or exits non-zero and takes `CI Gate` (`test.yml`'s single required check, which passes only on `success|skipped`) down with it, making every external contribution unmergeable. Dependabot is the trap: its branch is same-repo, so a fork-only check passes while the token is downgraded exactly like a fork's (verified on run `30857196770`, an all-read grant). The canonical guard:
  ```yaml
  if: github.event_name != 'pull_request'
    || (github.event.pull_request.head.repo.full_name == github.repository
        && github.actor != 'dependabot[bot]')
  ```
  Both halves earn their place. The `github.event_name != 'pull_request'` half is **mandatory**: `publish.yml` calls `test.yml` on the RC path, `github.event.pull_request` is null there, and without it a bare comparison reads as "fork" and silently disables the step on every release run. Use `github.actor`, not `pull_request.user.login`, so a human pushing to a Dependabot branch re-enables the step along with the token. Carry both halves at every site, even where a job's own `if:` already restricts to `pull_request`: one shape across all of them is what makes the set greppable and testable.
- **A blocking diff-scoped PR gate must diff from the merge-base with the base branch's live tip, never from `github.event.pull_request.base.sha`.** The PR checkout is `refs/pull/N/merge`, and that SHA is already an ancestor of it, so `merge-base(base.sha, HEAD)` is `base.sha` itself and the diff is base-tip..merge-commit. A "Re-run all jobs" replays the old payload against a merge ref GitHub has since rebuilt, and a branch that merged the base after it forked has the same shape: every base commit in between then reads as a line the PR added. The determinism ratchet step in `lint.yml` therefore fetches `refs/heads/<base.ref>` and passes `GATE_BASE=origin/<base.ref>`; `.github/scripts/__tests__/lint-ratchet-cli.test.mjs` pins both shapes against a real merge commit, and `lint-ratchet-workflow.test.mjs` pins that the step hands the CLI that tip and nothing else. The three warn-only `GATE_BASE` gates (`checks.yml` presence and weakening, `unit.yml` coverage) still take the payload SHA and can over-report on a stale re-run — harmless while they only report.
- **Do not guard a step just because it names a secret.** An absent secret is an empty string, not an error, and several paths degrade gracefully: `visual.yml` carries a second, **credential-free** comparison for fork and Dependabot runs, which reads the golden records from the public bucket over anonymous HTTPS so external contributors keep visual review even though the R2 write path needs secrets (guarding the comparison away outright removed that coverage once, reverted in #13222), and `docs/angular-type-check/check.mjs` turns a Checks-API 403 into a `::warning`. Guarding either would delete working coverage for external contributors, which the "functional continuity" rule in the root `AGENTS.md` forbids. Confirm against a real fork or Dependabot run before adding a guard. Current guarded sites: `.github/actions/performance-run/action.yml` and `performance-tests.yml` (gh-pages push, sticky comment, report URL), `integration.yml`'s `preview-packages` (sticky comment), `code-quality.yml`'s `sonarcloud` and `fossa` (hard secret dependency), `docs.yml`'s `preview` (the `docs-staging.yml` call, whose first step is a sticky comment) and its `Comment the docs visual verdict on the pull request` step (sticky comment), `.github/actions/docs-visual-run/action.yml`'s `Publish the report` and `Seed the golden records` steps (R2 writes), `visual.yml`'s credentialed compare, seed, PR-comment and approval-record steps, and `pr-cleanup.yml`'s `purge-visual-screenshots` (R2 delete, both `pr-<n>/` and `docs/pr-<n>/`). `.github/scripts/__tests__/fork-guards.test.mjs` asserts this list against the workflows, so add new sites in both places. Prefer **step-level** guards where the job still does useful work; job-level only where the job is entirely secret-dependent. Withheld content goes to `$GITHUB_STEP_SUMMARY`, which needs no token. Never reach for `pull_request_target`: it would run fork-controlled code that builds and publishes preview packages with a write token.
- **A release cut must never regenerate `pnpm-lock.yaml`.** The lockfile records `specifier: workspace:^` for every in-repo dependency and never a package's own version, so a version bump cannot legitimately change it — and 15 specifiers are `latest`, which re-resolve to whatever the registry serves that day. Deleting it and reinstalling floats the build toolchain (core-js, browserslist, caniuse-lite) straight into the shipped bundle: that is DEV-2667, which floated 509 packages at the `18.1.0-rc1` cut and left every production-bundle leg red for six release candidates. Nothing downstream catches it — a floated lockfile is internally consistent, so `pnpm install --frozen-lockfile` installs it happily. `.github/scripts/lockfile-float-gate.mjs` is the only check, wired at **six** sites in `publish.yml`: after each of the three version bumps (`first-rc-build`, `rc-build`, `stable-prepare`) and before each of their three `git add .` commits. Pass it the branch the job builds from — `develop` for the first RC, the release branch for the other two — or the error sends the operator to fix the wrong branch. Separately, `publish.yml` makes six `pnpm install --lockfile-only` calls, and three of those are ungated, in two different ways. The two in `stable-merge` resolve a real merge conflict, so they legitimately rewrite the file. The third, `docs-lockfile` in `stable-publish`, is a genuine dependency addition: the docs branch gains `@handsontable/angular-wrapper` at the released version, and that entry **must** reach `pnpm-lock.yaml` or every docs deploy dies on `ERR_PNPM_OUTDATED_LOCKFILE`, since `docs-production.yml` installs with `--frozen-lockfile`. The float gate's "must not change at all" cannot express that, so the step asserts the intended `specifier: ~<version>` landed in the `docs` importer and that no other package lost its resolved `name@version` identity — removals only, because a float always removes an old identity while a new transitive dependency only ever adds one. Line counts cannot express it either: a first release adds the devDependency, but a patch release onto an existing `prod-docs/*` branch rewrites it, so "no deletions" would fail every patch. That call is confined to a `prod-docs/*` branch that never reaches a registry. `.github/scripts/__tests__/release-lockfile.test.mjs` pins all of that — the gate count, the ungated-call count, the step ordering, that every step reading `$VERSION` also assigns it (each `run:` is a separate shell, and an unset `VERSION` silently weakens the docs check instead of breaking it), that every `continue-on-error` docs step's outcome is consulted by both the push gate and the job summary, and a ban on `pnpm install --force` and on deleting the lockfile anywhere under `.github/workflows/` or `.github/actions/` — so add new sites in both places.
- **The nine tracked example lockfiles are a second, separate float surface, and it is report-only.** `examples/next/{docs,visual-tests}/<framework>/package-lock.json` are npm lockfiles shared by each framework's examples, and `first-rc-build` is their only automated writer: it runs `examples:install` and then commits the tree with a bare `git add .`. `lockfile-float-gate.mjs` hardcodes `pnpm-lock.yaml`, so it never saw them. Two things to know before touching this. First, **the float came from deleting them, not from the `latest` pins**: 104 leaf specifiers are `latest`, but npm honours a locked edge for a dist-tag spec, so with the lockfile present `npm install` re-resolves nothing (verified on three trees, including a second install over the `link-packages` symlink). `examples/scripts/clean-subpackages.mjs` used to `rimraf` all nine before installing; it now keeps them unless `--reset-lockfiles` is passed, which is how a deliberate refresh is done (run it, review, land on `develop`). `examples/.gitignore` is now a pair, `**/package-lock.json` plus `!*/*/*/package-lock.json`, which ignores every lockfile under `examples/` and re-includes only the shared framework-level ones at exactly `<version>/<category>/<framework>/`. It needs no edit when a framework or category directory is added, which the old per-name list did: it named `angular`, `react` and `vue` while the directories are `angular-wrapper`, `react-wrapper` and `vue3`, had no `visual-tests` entries, and so left 5 of the 23 leaf paths inside `git add .`'s reach (per-leaf `.gitignore` files covered the other 18). One consequence worth knowing: the report's untracked scan can now only ever surface a *shared* lockfile that was never committed, never a leaf one, so its remedy says commit it or ignore it rather than assuming a float. Do not reintroduce an unconditional delete, and do not add `overrides` to the leaf manifests: `install-subpackages.mjs`'s `alignTypescriptWithAngular` *writes* `devDependencies.typescript` into every Angular leaf manifest at install time, so a hand-pinned list would fight it. **That alignment now reads its answer from the framework's own `package-lock.json`**: the locked `typescript` version first, because that is what actually installs and npm resolved it under the locked builder's peer range to begin with, then the locked `@angular-devkit/build-angular`'s own `peerDependencies.typescript` (recorded per package by `lockfileVersion: 3`) for a lockfile that pins the builder but not TypeScript. Either way no registry call. It falls back to `npm view ...@latest` only when there is no lockfile at all, which is the post-`--reset-lockfiles` state. Keeping those two on the same source of truth is load-bearing: with the lockfile reused, `latest` no longer decides which Angular installs, so aligning to `latest` would move the TypeScript pin on the day Angular bumps its range while the lockfile still installed the older builder. `--legacy-peer-deps` would swallow the peer conflict and `ng build` would fail on the compiler's own version check, inside `first-rc-build`. Second, the guard is `.github/scripts/example-lockfile-report.mjs`, which **always exits 0**: it writes the diff of both the lockfiles **and the leaf manifests** (the alignment writes those, and the same `git add .` commits them), any untracked lockfile that no ignore rule covers, and each changed lockfile's `npm audit` counts to `$GITHUB_STEP_SUMMARY`. Manifests stay out of the audit loop, because `npm audit` needs a lockfile and a leaf directory has none. The step sets `SKIP_AUDIT` when `job.status` is no longer `success`, so a job that is already red does not spend minutes auditing a half-installed tree. Report-only is deliberate: these trees ship in no bundle, so a transitive bump must not red an RC. It sits **above** the float gate in `first-rc-build` because `release-lockfile.test.mjs` asserts the gate is the step immediately before `Commit and push`, and its step must not spell out the gate's path: another assertion counts raw occurrences of that exact string and expects six.
- **The minified CSS is BOM-stripped at emit, and it must stay that way.** sass writes `@charset "UTF-8"` into `handsontable.css` because the themes contain a non-ASCII glyph. From **postcss 8.5.24** on, the `css-loader` → `CssExtractRspackPlugin` → `LightningCssMinimizerRspackPlugin` chain turns that at-rule into a UTF-8 BOM instead, and it lands **after** the preserved `/*!` license banner (byte 1662), not at offset 0 — which is what makes it dangerous. A *leading* BOM is stripped by the CSS decoder and by nothing else; one at a non-zero offset is stripped by neither, and U+FEFF is an ident code point in CSS rather than whitespace, so it fuses with the selector that follows. The first rule, `.ht-root-wrapper`, becomes `\uFEFF.ht-root-wrapper` and silently stops matching: the grid's root wrapper loses `display:flex`, `position:relative` and `height:100%`, cells stop receiving pointer events and popovers mis-anchor. **There are two consumers and both break.** `css-to-js-export-plugin.js` reads the file with `fs.readFileSync(path, 'utf8')` — which does not strip a BOM in Node — and `JSON.stringify`s it into `src/styles/handsontableStyles.{js,ts}`, so every bundle that inlines the runtime theme string carries it; and `handsontable/styles/handsontable.min.css` itself ships corrupted to anyone who loads the minified stylesheet directly. Only the second was ever observed, as three `dblclick` timeouts and a popover-position assertion on the `full`/`.min` E2E legs, which is why it first read as an unrelated bundle-axis flake rather than a CSS regression. `strip-css-bom-plugin.js` now removes the BOM from the emitted asset in `.config/styles-production.js`, before `addCssToJsExport` reads it back — registration order is load-bearing, since both are `afterEmit` taps — and the export plugin repeats the strip as a belt to those braces. Verified at postcss 8.5.28: the emitted stylesheet is byte-identical to the 8.5.23 output and both inlined exports are clean. This is why the root override is `postcss: '^8.5.23'` and not a cap: `>=8.5.18` is what GHSA-r28c-9q8g-f849 requires and `>=8.5.23` is what GHSA-fxqj-rqcc-2cmp raised it to, and the BOM no longer constrains the upper bound. **Do not reintroduce a `<8.5.24` cap** — it admits exactly one published version, so the next postcss advisory would leave no satisfiable range. If you touch the styles build, keep both invariants: `handsontable/styles/handsontable.min.css` must contain no `EF BB BF` at any offset, and `dist/handsontable.full.min.js` must contain exactly one `\uFEFF` (HyperFormula's own whitespace table). The `examples/next/*/react-wrapper` npm overrides deliberately stay at `^8.5.18`: those trees build through Create React App's postcss chain, never through lightningcss, and are unaffected.
- **Dependabot remediation runs through two different override mechanisms, and the npm one silently no-ops.** Nearly every alert lands on a *transitive* dependency, so bumping a declaration is rarely the lever. The monorepo tree is governed by `pnpm.overrides` in the root `package.json` — scope each entry as narrowly as the advisory (a bare name where one major is installed, `name@<major>` where several are, `parent>child` where only one consumer is affected), then `pnpm install --lockfile-only`. The `examples/next/<category>/<framework>/` trees are **separate npm workspaces with their own committed `package-lock.json`**, which inherit nothing from the root; they need an `overrides` block in the framework-level `package.json`. **`performance-tests/` is a third such tree** — npm-managed with its own committed lockfile, equally outside `pnpm.overrides`. It resolves patched versions today, but a remediation sweep that fixes only the `examples/next` trees has missed one. The trap: `npm install` applies a *new* `overrides` entry only when it re-resolves from scratch. With a valid `package-lock.json` present, or with a `node_modules/` on disk (including a per-example `<example>/node_modules/`, which is easy to miss), npm prints `up to date` and ignores the block, so the lock looks regenerated while the vulnerable version stays pinned. The sanctioned way into that state is `node ./scripts/clean-subpackages.mjs next --reset-lockfiles` from `examples/`, which removes the nine framework lockfiles **and** every `node_modules` under those trees — the per-example ones included — so the reinstall that follows re-resolves from scratch and honours the block. Run it, review the diff, land it on `develop` as its own change. **That full re-resolve is the expensive option, so weigh it against the bullet above**: it floats the whole tree (61-211 packages per lock in DEV-2772, `handsontable` 18.0.0 → 18.1.0 among them, which then broke the react demos' pinned `typescript@4.2.4` on the grid's own inline `type` imports), and those trees ship in no bundle, which is exactly why their audit is report-only. A **direct** dependency bump in a leaf manifest — the usual security fix there, e.g. `vite` — needs none of this: a plain `npm install` with the lockfile left in place picks it up and re-resolves nothing else. Reach for the throwaway re-resolve only when the fix genuinely has to travel through `overrides`, and say in the PR why the float was worth it. After any lockfile work, confirm the compile floor did not move: `core-js`, `hyperformula`, `typescript` and `esbuild` must be byte-identical, and `browserslist`/`caniuse-lite` may only move when an advisory demands it (`BROWSERS_LIST` is pinned integers, so caniuse data cannot shift the target — see the ES-floor entry in the root `AGENTS.md`).
- **Four high-severity Dependabot alerts have no fix and must not be chased.** `image-size@0.5.5` (an optional dependency of `less`) has no patched release at all. `extract-zip@2.0.1` has no patched release either, but it *is* escapable and must not be crossed off permanently: `puppeteer@25.9.0` ships `@puppeteer/browsers@3.2.1`, which depends only on `yargs` and `modern-tar` and has dropped `extract-zip` outright. The `^24.2.1` pin in `handsontable/package.json` is what holds us on `@puppeteer/browsers@2.13.2` and its `extract-zip ^2.0.1`. Taking a puppeteer major is a real decision, so this is **deferred until we move to puppeteer 25**, not closed. `xlsx@0.18.5` is the last SheetJS build ever published to npm — patched versions exist only on the SheetJS CDN, and it is kept here purely so the TypeScript docs examples type-check, while the browser examples load it from a CDN `<script>`. `svgo@1.3.2` in the two `react-wrapper` example trees is capped by `@svgr/plugin-svgo@5` under `react-scripts@5.0.1`; forcing svgo 2 breaks the SVG loader, so it clears only when those Create React App examples migrate to Vite. The `@angular/*` 19.2.x alerts are the same shape: Angular has not backported them, so they clear only when the wrapper's support matrix moves.
- **`docs/angular-type-check/` is a pnpm workspace member, not an npm project.** It is installed by the root `pnpm install` and its dependencies resolve from `pnpm-lock.yaml`; nothing ever runs `npm ci` there. A `package-lock.json` in that directory is dead weight that drifts out of step with `package.json` (it sat on Angular 21.2.11 against a declared `^19.2.20`) and Dependabot scans it anyway, so it is gitignored.
- **A bot pull request's token is a real trade-off, and `docs-sync.yml` uses `GITHUB_TOKEN`.** A pull request opened by `GITHUB_TOKEN` does **not** trigger `pull_request` workflows, so it gets no CI at all — the reason a bot PR is often opened with a GitHub App token (as `publish.yml` mints from `RELEASE_APP_*`). `docs-sync.yml` deliberately goes the other way: it grants `GITHUB_TOKEN` the `contents`/`pull-requests`/`issues` write scopes per-workflow (`issues: write` is the Issues API, which both the `docs-sync` labels and the hold comment need), the pattern `handsontable/examples`' import workflows use — no App to install or keep permissioned. The cost is that the sync pull request gets no CI (docs lint, build, preview): there is no run to "re-run", so a maintainer **closes and reopens** the pull request (or pushes a commit) to fire CI — and if the `prod-docs/*` base has any *required* status check, a zero-run PR is unmergeable, making that close/reopen mandatory, not optional. Two pre-flight settings gate the first live run and are invisible to the code: Settings → Actions → General → **"Allow GitHub Actions to create and approve pull requests"** must be on at **both** repo and org level (the `permissions:` block does not override it — `gh pr create` 403s otherwise), and `DOCS_SYNC_REVIEWERS` must hold plain usernames (`GITHUB_TOKEN` cannot resolve a team slug, and one in that variable fails the whole `gh pr create`). The App route was tried first and abandoned: the `RELEASE_APP` App lacked `issues: write`, so the first live run failed on `gh label create` with `403 Resource not accessible by integration`, and widening an App's permissions needs an org owner. Weigh both when adding a new bot. The `docs-sync/*` branches are owned by that workflow: it rebuilds them from the target tip on every run and stops only while a branch carries a commit whose committer is not `docs-sync[bot]` (the script sets that committer itself, independent of the token).
