# FreezeBar plugin – a draggable bar on each freeze line

Covers `freezeBar.ts` (the plugin), `snapResolver.ts` (pointer to count) and the pure fit helper it uses, `src/utils/frozenAreaFit.ts`. Read this before touching how a count is written, or where a bar is mounted.

## What it owns and what it does not

- It owns the bars, the indicators of a drag (guide and ghost), and the write of the four frozen counts (`fixedRowsTop`, `fixedRowsBottom`, `fixedColumnsStart`, `fixedColumnsEnd`) that a user starts.
- It does not own freezing itself. `ManualColumnFreeze` moves a column to the freeze line and keeps the first N columns frozen. This plugin never moves a column and never touches the column index mapper, so the two can run together.
- It does not own the viewport clamp of the rendered area (#4259), which is `limitFixedToViewport` in `TableView`. It keeps its own drag inside what fits with the same helper (`resolveFittingFrozenCounts` and `getMaxFittingFrozenCount` in `src/utils/frozenAreaFit.ts`) and the same measurement (`TableView#getFrozenTrackSize` and `getFrozenViewportSize`), so the End target of a bar and the drawn clamp never disagree by a track.

## The traps

- **The count is written on the table meta inside `runOperation`, never through `updateSettings()`.** `getSettings()` returns the table meta, so assigning to it creates an own property that shadows the global value, which is what `alter()`, `ManualColumnFreeze` and UndoRedo do. Three things break with `updateSettings`: a wrapper re-sends every prop on each render, so a changed global value is reverted by the next render (the drop of the shadow is keyed on a changed incoming value, `FROZEN_COUNT_OPTIONS` in `core.ts`); a grid configured with `fixedColumnsLeft` throws when `fixedColumnsStart` is also passed; and a write of `fixedRowsTop` disables Pagination silently. Start columns are written to `_fixedColumnsStart`, the backing field both names share.
- **The cost of that choice is the app's contract.** The settings the app passed in are not changed, so an app that re-sends the same value after a drag keeps the dragged count. An app that keeps the counts in its own state copies them in `afterFreezeChange`. Do not also write the global value to "fix" this: the re-sent original value then differs and reverts the drag.
- **Undo needs no code.** UndoRedo's grid state already captures and restores all four counts, and one `runOperation` per release is one undo step.
- **Pagination is blocked here.** A write on the table meta never reaches the conflict registry, so Pagination would stay enabled next to fixed rows, a combination it does not support. `#isEdgeAvailable` hides the row bars and refuses `setFreezeCount('top' | 'bottom')` while it is on.
- **Counts are visual.** A hidden track keeps its slot in the band and a trimmed track gives its slot up. The resolver sees a hidden track as size 0 and, on equal distances, picks the lowest count, so a hidden track right after the last frozen one stays unfrozen. A keyboard step skips hidden tracks (`#stepOverHidden`).
- **Everything is measured against the rendered content, not the container.** `#measureFrame` returns the root rectangle, the viewport (the root in view, minus scrollbars), the content (`getTotalTableWidth()` and `getTotalTableHeight()` from the root's edge, shifted by the scroll position, headers included) and the rendered area (the viewport cut down to the content). A grid smaller than its container ends before the container does, and the end and bottom bands sit at the edge of the content, so the pointer distance, the guide, the empty handles and the length of every bar use the rendered area. Do not use `hot.table`: the master table is shifted past the headers, and its rectangle starts after them. It is measured once per render and reused for the four bars, because a read after a write forces a layout.
- **A bar is as long as the viewport, through the other frozen rows and columns.** A freeze line crosses the overlays of the other frozen bands, and a bar inside one clone would stop at the next one. So the bar of an edge has pieces (`#segments`, class `ht-freeze-bar--segment`) in the corner overlays it crosses (`CORNER_OVERLAYS`): the top bar also lies in the two top corner overlays, which cover the row headers and the frozen start and end columns, and so on. The pieces are not focusable and carry no ARIA, they draw and start a drag. Page objects must use `:not(.ht-freeze-bar--segment)` to find the real bar.
- **An edge with nothing frozen can be grabbed along its whole length but draws only a short piece on the header corner**. The start and top handles (class `ht-freeze-bar--wide`) take the whole height or width of the grid as a transparent hit area, and the visible piece is an `::after` as long as the headers (the `::before` stays the larger hit area for a finger under `@media (pointer: coarse)`, and a more specific rule must not take it over) (`--ht-freeze-bar-corner`, at least `MIN_HANDLE_LENGTH` for a grid without headers). The end and bottom handles have no such edge to start from, and a hit area along the last column or row would sit over the column resize handle, so they are the short piece only, on the opposite header corners. The handles live in the root element and follow the viewport on `afterScroll*`, because the header corner stays pinned while the page scrolls. They stay while the grid is scrolled to the middle, because a drag scrolls to the edge first. A bar that holds the focus when its count reaches 0 (Home) stays in place.
- **The page or an ancestor can own a scroll axis.** An axis the root element does not clip (`overflow: visible`) is scrolled by the window or by a scrolling ancestor, and the overlays stick to that scroller. `#getClipRange` finds it with `getTrimmingContainer()` and `#measureFrame` cuts the root down to it. The window is covered by the grid's scroll hooks, but a scrolling `div` is not, so `#syncScrollAncestors` listens to it. In element scroll mode (the root clips both axes) the handles do not move, and the scroll pass returns at once.
- **The end and bottom handles keep `RESIZER_CLEARANCE` from the edge when `manualColumnResize` or `manualRowResize` is on**, because the resizer is as wide as the handle. The bar has the higher `z-index` and would take the press meant for the resizer. Inside an overlay the bar is at `z-index` 105 (`base/_z-index-map.scss` lists it): above the selection borders and the moveCells bands, below the fill handle (110), so a grab on the handle starts an autofill and not a freeze drag.
- **The resize handle keeps clear of the bar.** The column and row resize handle is a 10px box in the root element with a 2px pill on each side, and its edge lies 6px into it, so a 4px bar on the frozen side of the edge covered one pill and left the other 2px away. `ResizeGesture` marks a handle that sits on the edge of a frozen band (`ht-resize-handle--freeze-before` for the start and top bands, `--freeze-after` for the end and bottom bands, see `../../utils/manualResize/AGENTS.md`), and `_freeze-bar.scss` moves the pills 2px clear of the bar on both sides, mirrored in RTL. The rules are scoped by `ht-freeze-bar-columns` / `ht-freeze-bar-rows` on the root element, which `#onAfterRender` sets for the axes that have bars and `#teardown` removes, so a grid without the bars keeps the pills where they were.
- **Styles are written only when they changed** (`#applyStyles`): the placement runs on every render, and a scroll renders every frame. `updatePlugin()` does not sync, because `updateSettings` renders next.
- **Colors, cursor and the indicators of a drag:** a bar is drawn in its own token, `--ht-freeze-bar-color` (JS `freezeBarColor`, a step lighter than `--ht-resize-indicator-color` in the main theme, one step darker in classic and horizon), and STAYS that color while it is held; the parts drawn over the headers (the hover and both drag shadows) use `--ht-freeze-bar-highlight-color` (`freezeBarHighlightColor`, the accent color by default). The three tokens are in all four theme layers and in the Figma generator's `tokensKeys.mjs`, but not in Figma yet: regenerating the themes before Figma has them drops them. A hovered bar (`ht-freeze-bar--hover`, set on the bar and its pieces by `#setHover` on `pointerenter`, cleared on `pointerleave` and when the pointer of a press first moves past `DRAG_THRESHOLD`) draws its part over the header strip in `--ht-freeze-bar-hover-color` (`freezeBarHoverColor`, a darker gray), and in the highlight color while it is pressed (`ht-freeze-bar--active`), and only a press (not a hover) takes the accent color. Once the drag starts the bar goes back to its plain color and the guide and the ghost take over. Do not clear the hover in `#setActive`: the press would then never show the highlight; the part is given to each piece in its own coordinates (`--ht-freeze-bar-header-from`/`-to`), because the pieces start in different overlays, and `#onAfterRender` computes it again for the hovered edge (`#hoveredEdge`), because the headers can change size under a pointer that does not move and no pointer event fires then. The wide empty handles color their whole `::after` instead. `ht-freeze-bar--active` (on the bar and its pieces for the length of the drag) only closes the hand. What shows where the bar lands are two elements in the root element, placed by `#showGuide` through `#placeIndicator` and removed by `#hideGuide`: the guide (`.ht-freeze-bar-guide`, a gray shadow as thick as the bar at the snapped position) and the ghost (`.ht-freeze-bar-ghost`, a light accent shadow centered on the pointer, kept between the headers and the end of the rendered area). The headers are deliberately NOT tinted during a drag (a highlight of the tracks that change was tried and removed: it was not wanted). Both shadows are solid accent over the header strip, drawn with a gradient whose stop is `--ht-freeze-bar-header` (set inline) and whose direction is `--ht-freeze-bar-header-side` (the row header strip is on the right in RTL). The cursor is an open hand (`grab`), not a resize arrow, and closes (`grabbing`) on `ht-freeze-bar--active`; `#setActive` also puts `ht-freeze-bar-dragging` on the root element, which closes the hand over every element of the grid for the length of the drag. Do not rely on the pointer capture for that: it was measured not to hold during a real mouse drag, and the cells then showed their own cursor.
- **The pointer distance is measured from the visible part of the root element, not its bounding box.** In window scroll mode the overlays are `position: sticky`, so the root element's own edge may be scrolled out of view; `#measureFrame` intersects it with the viewport on the axes the window scrolls. The guide is placed from the root element's edge, so it adds the difference back.
- **Where a bar lives (measured on a demo page).** A bar for a band with frozen tracks is a child of that overlay's root (`.ht_clone_*`). It needs no repositioning in element or window scroll, or in RTL, and the clone roots do not clip it. With nothing frozen and no headers every clone is 0×0, so the handle of an empty edge cannot live there: it is a child of the root element, placed on the edge of the data area. In window scroll mode that handle is on the grid's own edge, so the end and bottom handles are at the far end of the page.
- **A drag scrolls the grid to the edge of its axis when the pointer first moves past `DRAG_THRESHOLD`, not when it is pressed.** A click that only focuses the bar, a wobble of a finger, or a drag cancelled at once leaves the grid where it was and the count alone. The drag works from the measurements taken after that scroll. The limit of a drag is `max(what fits, the current count)`, so a count that no longer fits is not lowered by a drag that did not touch it. `setPointerCapture()` is called in a `try`: it throws for a pointer that is not active (a synthetic one), and the drag must go on.
- **A drag scrolls the grid to the edge of its axis first** (`#scrollToEdge`): the first scrollable row or column for the top and start bars, the last one for the bottom and end bars. The rows a drag freezes are always the first (or last) ones, so without the scroll the guide would show a line between rows that are not the ones that get frozen. The target is the first or last scrollable track, because the scroll never goes to a frozen one. Measurements are taken after the scroll.
- **A scroll while a bar is held is undone, not followed** (`#pinDragToEdge`, called from `#onScroll`). The guide sits at the sum of the sizes of the first (or last) tracks, and the drag measured the viewport right after `#scrollToEdge`, so it names the right boundary only while those tracks are the ones in view. A wheel, a trackpad or a scrollbar that moves the grid mid-drag left the guide in the middle of a cell and the frozen band next to a half scrolled column. The pin runs only once the drag has started (`started`, set after the first scroll to the edge) and only for an axis the grid's own holder scrolls (`mainTableScrollableElement` of the axis overlay is the holder), which includes a grid of an automatic height in a scrolling `div`, whose root is unclipped. When the window or a real scrolling ancestor owns the axis, the page keeps its scroll and the drag keeps the measurements it took at the start, so a scroll mid-drag there still leaves the guide misplaced (open). The pin is a no-op when the grid is already at the edge, so the scroll it causes does not loop. A second finger that scrolls during a touch drag snaps back, which is intended.
- **The drag uses Pointer Events**, so mouse, touch and pen share one path. `touch-action: none` is on the bar, and `@media (pointer: coarse)` grows its hit area 12px towards the frozen side with a pseudo-element: a narrow last frozen column (a checkbox or an index) must stay tappable, and `touch-action: none` is on the bar. The gesture is tracked by `pointerId`; `pointercancel` stores nothing.
- **The keyboard works on the focused separator, not through the shortcut manager.** It lives on a SEPARATOR, not on the bar (see the point on the separator below): a `role="separator"` with its own `keydown` handler that stops EVERY key, not only the ones it uses: the grid keeps listening while a separator has the focus, so Delete would clear the selected cell and Enter or a letter would open its editor. Tab and the browser's own chords keep their default (nothing calls `preventDefault`), but a chord is still stopped, because `Ctrl+X` or `Ctrl+Enter` would reach a grid shortcut that writes to the selected cell. Undo and redo (`Ctrl/Cmd+Z`, `Ctrl/Cmd+Y`) are the one exception: they put the frozen counts back, and the bar must not take them away. The arrows point in the direction the bar moves: start and top grow with ArrowRight and ArrowDown, end and bottom grow with ArrowLeft and ArrowUp, and the horizontal arrows swap in RTL. While the grid listens, Tab moves the cell selection, so F6 (a shortcut in the `grid` context, group `freezeBar`) moves the focus to the first bar, and on a bar F6 moves to the next one (Shift+F6 to the previous), which is the only keyboard path to the top, end and bottom bars. The shortcut claims the key only while there is a bar to focus, so it stays the browser's key otherwise. End goes to the largest count that fits (never fewer than there are), Home to 0.
- **`updatePlugin()` keeps the bars.** A wrapper re-sends every prop on each commit, and an app that copies the count into its state in `afterFreezeChange` triggers a commit per arrow press. Tearing the bars down there dropped the focus from the bar and cancelled a drag. A bar that changes host (an edge going from 0 to 1 frozen tracks moves it from the root element to an overlay) is re-focused after the move, because moving a node blurs it.
- **`aria-valuemax` is resolved on focus and on drag start, not on `afterRender`.** It walks the size of every track on the axis, and `afterRender` runs on every scroll. Keep `#syncBar` cheap. The attributes follow the `ariaTags` setting.
- **`getFreezeCount()` is the CONFIGURED count; the bar follows the DRAWN one.** Apps save `getFreezeCount()`, and the hooks report it as `oldCount`, so it must be what the app configured (the end band clamped by the start band, as before the option existed). With `limitFixedToViewport` the grid can draw fewer tracks, and everything that positions or measures reads `#getDrawnCount()` (`TableView#countFixedColumnsStart()`, `countFixedRowsTop()`, `countFixedRowsBottom()`, `countFixedColumnsEnd()`): the bar's host and `aria-valuenow`, `#scrollToEdge`, the drag start, the keyboard step and the room the opposite band takes. `#applyCount` compares the request with the configured count, so `setFreezeCount('start', drawn)` commits the drawn count (configured 10, drawn 3: it writes 3 and the hook gets `oldCount` 10), and a request equal to the configured count is a no-op that keeps the columns coming back on resize. A drag is an explicit choice of the user, so it replaces the configured count, but a gesture that ends where it began (a click, `End` on a full band, a grow step that cannot fit) writes nothing: a grow step is cut down to what fits like `End` is, or it would read as a shrink below a larger configured count. The tracks that remain for a band are counted after the CONFIGURED opposite band (as `resolveFittingFrozenCounts` does), while the room it takes is the DRAWN opposite band.
- **Turning the plugin off removes the bars, not the counts.** The counts live on the table meta as own properties, so the frozen area stays as the user left it until `updateSettings` changes the option that holds it.
- **Only a count that GROWS is cut down to what fits.** `#applyCount` leaves a count the user did not touch alone: with 4 frozen columns on a grid where only 3 fit, a click on the bar or a step down must not rewrite it to 3 and fire the hooks with source `drag`. The maximum subtracts the band on the OPPOSITE edge for every edge (the start bar leaves room for the end band too), so the two bands together never fill the viewport. The walk over the tracks stops once the viewport is used up, because a grid can have a million rows.
- **Labels follow the language, and each edge has its own.** The bars keep their translated name through `updatePlugin()`, so `afterLanguageChange` translates it again. There are four keys (`FREEZE_BAR_ROWS_TOP`, `FREEZE_BAR_ROWS_BOTTOM`, `FREEZE_BAR_COLUMNS_START`, `FREEZE_BAR_COLUMNS_END`), because F6 cycles through all four bars and a screen reader announces two bars of one axis identically otherwise. There is no `aria-valuetext`: it would need a plural form per language.
- **Focus in a shadow root:** use `getDeepActiveElement()`, never `document.activeElement`, to tell whether a bar holds the focus before it is moved to another host.
- **The focusable separator sits NEXT to the grid, never in it.** The grid is a `role="treegrid"`, which may own only rows and row groups, so a `role="separator"` anywhere inside it (the clones are `presentation`, and do not break the ownership) makes axe report `aria-required-children` on every grid with the plugin on. So each edge has two nodes: the BAR (and its pieces) in the overlays draws, takes the pointer and the wheel, and is `aria-hidden`; the SEPARATOR (`data-ht-freeze-separator`, in the parent of the root element, visually hidden by inline styles because it lies outside `.handsontable`) carries the role, the value, the label and the keyboard. A press on a bar focuses its separator, and the ring is drawn on the bar (`ht-freeze-bar--focused`, only for a keyboard focus, as `:focus-visible` is). Page objects use `separator(edge)` for the keyboard and ARIA, `bar(edge)` for the geometry.
- **The shortcut lives in the `grid` context, not in a focus scope of its own.** A scope would switch the shortcut manager to a context that has none of the grid's keys, and the bar is part of the grid (it sits in its overlays and is a keyboard stop of it). The separator handles its own keys and stops the others instead, and F6 is the one entry from the grid.
- **Only one separator is a Tab stop** (the first that exists, `tabIndex` 0, the others -1): four stops after the grid would be four extra Tab presses, and F6 is the documented way between them. A separator reached with Tab has an unknown focus source, so the grid does not listen to the keys yet: Escape calls `hot.listen()` before it hands the focus back. A separator that holds the focus when it is removed (the edge goes away, Pagination turns on, the plugin is turned off) hands the focus back to the grid first, or it would drop to the page.
- **The column move veto of the ticket is not here on purpose.** Freezing is positional since #13755 and the bar never moves a column, so there is no move to veto.
- **Escape gives the focus back to the grid and goes on to the page**, so a modal around the grid still closes on it. `cut` and `paste` are stopped on the separator as well, because a stopped `keydown` does not stop the clipboard events it starts.
- **A wheel over a bar scrolls the grid** (`#onWheel`): the grid listens for the wheel on its holders only. An axis the root does not clip goes to the page or the ancestor as it is.
- **Filters has to be told.** `filterFixedRows: false` re-checks the rows that are exempt from the filter when `fixedRowsTop` or `fixedRowsBottom` change. A write on the table meta is not an update, so `#applyCount` calls `Filters#_markPinnedRowsStale()` for the top and bottom edges. Never fake an `afterUpdateSettings` run for it: user hooks, the wrappers, the focus manager and the `SETTING_KEYS: true` plugins would all react to an update that never happened.
- **The shadow reaches the conflict check.** `isHardConflictBlocked` reads `getSettings()`, so after a drag to 3 rows `updateSettings({ pagination: true })` is refused, and `updateSettings({ fixedRowsTop: 0 })` is a no-op when the app's own value is already 0. `setFreezeCount()` is the way back, and the guide says so.
- **SheetsBar captures the four counts per sheet and clears the shadow when it restores them.** Without that, a freeze dragged on one sheet followed the user onto every sheet they had not opened yet (see `../sheetsBar/AGENTS.md`). Any other plugin that restores or resets a frozen count through `updateSettings()` has the same problem and needs the same two steps.
- **A press saves an open editor, and commits only when it became a drag.** `preventDefault()` on the press drops the compatibility `mousedown`, which is what saves an editor on a press outside the grid, so `#onPointerDown` calls `finishEditing()` itself. A release that never passed the threshold writes nothing., for the count read at the press may be stale by then (an undo, for example).
- **Teardown must be safe mid-drag.** Wrappers call `disablePlugin()` and `enablePlugin()` on a rerender. `#teardown` aborts the drag (it removes the document listeners and stores nothing), removes the indicators of the drag and every bar.
- **`SETTING_KEYS` is left at its default.** The bars follow `afterRender`, so a change of the frozen counts from anywhere (the API, `alter()`, undo) repositions them without a settings round trip.
- **A drag ends when the data is replaced.** `beforeLoadData` and `beforeUpdateData` run `#abortDrag`, which stores nothing. With a sheets bar the count a drag would write belongs to the sheet that was left, and the drag measured that sheet's tracks. Pinned by `tests/e2e/sheets-bar-in-flight-drags.spec.ts`.

## Testing

- `npm --prefix handsontable run test:unit.jest -- --testPathPattern=freezeBar` runs the unit tests. jsdom has no layout, so the unit tests give the viewport a size with `jest.spyOn` on the view.
- `tests/e2e/freeze-bar.spec.ts` (mouse, keyboard, RTL, window scroll, pagination, teardown) and `tests/e2e/freeze-bar-touch.spec.ts` (a real finger through the DevTools protocol) drive the fixture `tests/fixtures/demo/freeze-bar.html` through `tests/fixtures/pages/FreezeBarPage.ts`.
- After a change to `src/styles`, rebuild `build:umd` before an end-to-end run: the bundle inlines the base stylesheet.
