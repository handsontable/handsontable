# DataProvider plugin — server-backed grids and error UI

The `dataProvider` plugin backs the grid with a remote source via `fetchRows` and CRUD callbacks (`onRowsCreate` / `onRowsUpdate` / `onRowsRemove`). Read this before touching `dataProvider.ts` or wiring up error handling.

## Error UI contract (the trap)

- **Built-in error toasts require the `notification` plugin.** Enable `notification` (`notification: true` or a config object) to get toasts on failed fetches or mutations. **`dialog: true` alone does NOT show these errors** — Dialog is for blocking overlays (Loading, ExportFile export progress, custom modal content), not fetch/mutation errors.
- **Fetch-failure toasts include a Refetch button** that retries the request that failed. The toast uses `duration: 0`, so it stays until dismissed or Refetch is clicked.
- **Refetch retries the query that FAILED, not `#queryParameters`.** `fetchData()` stores the query only after a successful fetch, so a failed page or page-size change leaves `#queryParameters` on the previous state (and Pagination's `revertPageTo()`/`revertPageSizeTo()` puts the pager back there). The toast therefore captures the failed request's snapshot and passes it to `#fetchDataSilently()`; a no-override refetch would silently reload the old page. A failed sort or filter change was always retried correctly, because those write `#queryParameters` before they fetch. Because the snapshot is replayed whole, an old toast would roll back any page, sort, or filter the user requested after the failure – whether that later request succeeded, failed, or is still in flight. The callback therefore replays it only while `#queryParameters` is still the object it saw at failure time, and **every write to `#queryParameters` assigns a new object**: a successful fetch, `disablePlugin()`, `#applyQueryParametersFromPlugins()` (the sort path), and the filter ctx. A changed reference means the user asked for something newer, and Refetch reloads the current query instead. Never write into `#queryParameters` in place – the check cannot see such a write, and an old toast would then replay a stale query over it. DataProvider deliberately keeps no list of open toasts, since the toast lifecycle is the Notification plugin's. Pinned by `tests/e2e/data-provider-refetch-failed-query.spec.ts`.
- **A refetch that follows a save starts from the running fetch's query, not `#queryParameters`.** `#queryParameters` is written only after a fetch succeeds (sort and filter write it first), so a page change still loading leaves it on the old page, and the refetch aborts that fetch. `#refetchFor()` therefore passes `#pendingQueryFor()` as the base query: a snapshot of the `params` of the binding's in-flight fetch (a context that is not shown included), `undefined` when none runs. The snapshot keeps the base to the query keys, so a key a `beforeDataProviderFetch` listener added is not merged back in. Only `#refetchFor()` does this (the update follow-up, the post-create refetch, and `removeRows()`, whose fallback page reads the same pending query, and whose "remove every row, load the previous page" shortcut is skipped while the pending page differs from the shown one, because the row count it checks belongs to the shown page); the public `fetchData()` keeps reading the current query. **Known limit:** the save's refetch aborts the pending page fetch, so Pagination never runs `revertPageTo()` for it; if that refetch then fails, the pager shows the new page over the old rows until the user clicks Refetch in the toast. The refetch sends `skipLoading: true`, but it replaces a page fetch that was loading, so it takes over that fetch's loading state (see "A silent fetch that supersedes a loading one" below) and `isFetching()` stays `true` until it lands. Pinned by `__tests__/refetchPendingQuery.unit.js`.
- **For custom error UI when Notification is disabled**, hook `afterDataProviderFetchError` and `afterRowsMutationError` instead of relying on the built-in toasts.

## Who is allowed to let `fetchData()` reject

`fetchData()` fires `afterDataProviderFetchError` and shows the error toast, then rethrows. That rethrow is public API — a caller awaiting `fetchData()` still gets the rejection.

- **Internal fire-and-forget refetches must go through `#fetchDataSilently()`**: the fetch of an enable or update (the ready step, `onGridReady()`, and `onDataReady()`), the sort ctx, the filter ctx, and the Refetch toast action. The wrapper logs `Data fetch failed:` and resolves `null`. `void this.fetchData()` does NOT work — `void` discards the value, not the rejection, so a failing `fetchRows` reaches the page as an `unhandledrejection` (Sentry HANDSONTABLE-DOCS-20B / 1JN).
- **`#commitRowsUpdate`'s ctx (`fetchData: () => this.#refetchFor(target, { skipLoading: true })`) must keep rejecting for a visible binding.** `query/crud.ts` catches it to revert the optimistic cell values and log `Data reload failed:`. Do not "consistency-fix" this one to the silent wrapper.
- **Pagination ctx callbacks stay rejecting too** — `query/pagination.ts` catches them to revert the page or page size.
- **The one exception is a request whose context is no longer shown.** See "Owner contract: contexts (internal)" below — without an owner every request is in the default context (`null`), which is always visible, so a plain grid never takes this path.

## Owner contract: contexts (internal)

Another plugin (the in-tree one is SheetsBar) can show several views of the grid, each backed by its own requests. The plugin knows nothing about what a view is: it only tracks an opaque **context** (`object | null`) that the owner names. Keep it that way — no owner-specific ids, hook names, `getPlugin()` calls into the owner, per-view state maps, replay, or deferred-toast storage belong here.

**The contract is internal, not API.** It is a TypeScript interface (`DataProviderContextOwner`, exported from `dataProvider.ts` for SheetsBar's `import type` but not from the plugin barrel) plus six `_`-prefixed methods carrying `@private` in their JSDoc: `_setContextOwner()`, `_runContextChange()`, `_runWithoutFetching()`, `_restoreFetchResult()`, `_showRequestError()`, `_releaseContext()`. That is the repo's idiom for a member other in-tree code may call but integrators must not (`Core#_getColWidthFromSettings`, `_registerTimeout`): the API reference generator (`docs/scripts/jsdoc-convert`, `jsdoc-to-markdown` + `dmd`) drops `@private` doclets, and the `_` prefix flags it in the emitted `.d.ts`. **Do not turn any of it into a hook.** A registered hook is public by construction (it lands in `GridSettings`, in `Handsontable.hooks.getRegistered()` — which a docs guide lists at runtime — and in the hooks reference), and a hook is also the wrong transport: `Hooks.run` feeds a listener's non-`undefined` return into the next listener as its first argument (`core/hooks/index.ts`), so any user listener can corrupt what the owner receives. `isFetching()` is the one public member here (it was accepted as public API and is documented). It already answers `false` inside the `afterDataProviderFetch`, `afterDataProviderFetchError`, and `afterDataProviderFetchAbort` listeners of the fetch that settled (and in `onShownResponse`): `#fetchFor()` releases the in-flight entry before it applies the result or runs those hooks, not only in its `finally`. A listener asking "is it still loading?" otherwise got `true`. Pinned in `__tests__/ownerContext.unit.js`.

**`updatePlugin(newSettings)` skips a payload whose `dataProvider` is no longer the grid's.** An earlier `afterUpdateSettings` listener (SheetsBar, putting a server sheet's own value back over a re-sent grid-level one) can replace the value with a nested `updateSettings()` call, which already re-applied this plugin; re-applying for the outer payload would abort the visible fetch and refetch. A plain grid never takes this path: without a nested call the two values are the same object.

**Pagination's sync to a response must not read as a user's page-size change, and that rests on an ordering rule.** Pagination's `afterDataProviderFetch` listener takes the response's page and page size and fires `afterPageSizeChange` when its own size differed — which happens whenever a view with another page size was shown before (a replay on return, or a fetch that lands after a switch). The handler (`handleAfterPageSizeChangeExternalPagination` in `query/pagination.ts`) skips that event only while `#isApplyingResponse` is set (`#runAfterDataProviderFetch()`, used by both `#applyFetchResult()` and `_restoreFetchResult()`) and the pager's page equals the query's page; outside a response it keeps the rule it always had (same size on page 1), so a user's page-size change behaves as before. **`#queryParameters` must be written BEFORE `afterDataProviderFetch` fires on both paths**: the skip compares Pagination's sync against the query, and writing it after the hook reopens the replay refetch and the fetch-lands-after-switch refetch, both of which reset the user to page 1. A listener that sets another page size during that hook still fetches: its size differs from the query.

- **A binding is `{ context, config, query }`, captured when a fetch or mutation starts** (`#currentBinding()`). `#currentContext()` asks `this.#contextOwner?.getContext()`; without an owner it is `null`. Compare contexts by identity — the owner hands out one object per view that it never reuses (SheetsBar: a frozen empty token per sheet, never the sheet record), because a numeric id is reused by a rebuilt workbook and would let a stale request land on a new view.
- **`#isDropped(binding)`** is true for a released context (`#releasedContexts`, a `WeakSet`), and for a default-context (`null`) binding while the owner reports a context of its own — a request made before the owner appeared (a plain grid's save still pending when SheetsBar is enabled). `#isVisible(binding)` is false for a dropped binding, true for the default context otherwise (a plain grid: always, as in base), and for an owner's context only while the plugin is enabled and the owner reports it as current. `#mutationTarget()` re-reads the binding for the default context only while the current context is also `null`, so a dropped save neither refetches nor reverts into the owner's view; its callback, its public mutation hooks, and its console log still run.
- **`#inFlight` is a `Map<object | null, …>`, one fetch per context.** A newer fetch supersedes (aborts) only a fetch of its own context (`#abortFetchesFor()`). `disablePlugin()` aborts only the current context's fetch (`#abortFetchesFor(current)`, no reason); `destroy()` aborts everything.
- **A response loaded for an owner's context goes to the owner through `onShownResponse(result, context)` BEFORE `afterDataProviderFetch` fires**, as the same normalized `{ rows, totalRows, queryParameters }` shape, so no hook listener can change what the owner keeps for its replay.
- **Anything that settles for a context that is not shown goes to the owner through ONE channel, `onDetachedRequest(kind, outcome, context)`, and nothing else happens.** A response is `('fetch', { result }, context)` from `#applyFetchResult()` — no `loadData`, no `afterDataProviderFetch`, no render; the result carries `rows`, `totalRows`, and `queryParameters` but no `columnSortConfig`/`filtersConditionsStack`, because those go through `hot.propToCol()`, which answers for the columns shown NOW (they are built when the response is shown, in `_restoreFetchResult()`). A failure is `(kind, { error }, context)` from `#notifyRequestError()`, for `fetch` and for `create`/`update`/`remove` alike; DataProvider shows no toast for it — it decides visibility itself, so no listener can change which kind the owner stores. A dropped binding reports nothing. An off-screen refetch starts from the query of the owner's optional `getContextResult(context)` (the latest response it keeps for that view), falling back to the query the request was queued with — `#queryFor()`; a visible one starts from the current query, as the base code always did, except a refetch through `#refetchFor()` while a fetch of that context is running (see "A refetch that follows a save"). The response stays the owner's: DataProvider keeps no per-view map. The visible path still builds its payload after `loadData()`, as the base code did (a grid without `columns` resolves a `prop` through the loaded rows' schema). Nothing here writes into an array it did not create: the owner replaces its own array reference.
- **A failure for a context that is not shown resolves `null` instead of rejecting** (`#fetchFor`, `#refetchFor`). `query/crud.ts` reverts an update's optimistic cell values on a rejection, and that revert would land on whatever is shown now. `afterDataProviderFetchError` fires immediately with a third argument, `isVisible: false` — for such a failure only; every other failure keeps the two base arguments (a legacy spec, `hooks/afterDataProviderFetchError.spec.js`, pins the exact call). Filters' rollback and EmptyDataState's overlay clear honor it; any new listener that changes the grid on a fetch error has to skip `isVisible === false` too.
- **`beforeDataProviderFetch` runs BEFORE the running fetch of the context is aborted.** `#fetchFor()` aborts the earlier fetch and registers the new one in `#inFlight` only once the hook let the new request through. In the old order a listener that canceled the new request also killed the running one, whose answer was then dropped, and `afterDataProviderFetchAbort` fired for a fetch nothing replaced. So that hook now means "a newer fetch STARTED", and `isFetching()` inside a `beforeDataProviderFetch` listener answers for the earlier fetch, not the one being asked about. Pinned by `__tests__/dataProviderLoadingSettle.unit.js`.
- **Every way a shown fetch ends syncs EmptyDataState's loading overlay.** A response fires `afterDataProviderFetch` and a failure `afterDataProviderFetchError`, which EmptyDataState listens to. The other three endings fire neither: a listener's cancel, an `AbortError` rejection, and a signal aborted before the answer. Each calls `#syncLoadingIfShown(binding)`, which runs `#syncLoading()` (`_syncDataProviderLoading(this.isFetching())`) for a binding the grid shows. Without it the overlay EmptyDataState raised from its own `beforeDataProviderFetch` listener said "Loading data" for good on a plain grid. A fetch a newer one superseded keeps the overlay, because `isFetching()` answers for the newer one. `#abortFetchesAndSyncLoading()` shares `#syncLoading()`; add a new ending through the same helper, never a copy of the call.
- **A silent fetch that supersedes a loading one takes over its loading state** (`#resolveSkipLoading()`). The sort refetch (`query/sorting.ts`) and the save follow-ups (`#refetchFor()`) pass `skipLoading: true`, and `isFetching()` ignores such an entry. Since the superseded fetch's abort ending syncs the overlay, a sort or a save made during a load hid the overlay while the refetch still ran, and the grid was uncovered under it. The successor is registered as loading when the entry it aborts was loading, so `isFetching()` answers `true` until it lands, and its `afterDataProviderFetch` clears the overlay. `beforeDataProviderFetch` still receives the caller's own `skipLoading`. A silent fetch that supersedes another silent one stays silent.
- **The page-clamp refetch releases its own entry before it recurses.** A response past the last page refetches the clamped page from inside the `try`; with the outer entry still in `#inFlight`, a listener's cancel of the clamped request synced the overlay against that entry and kept "Loading data" for good, and the outer `finally` syncs nothing. The recursive call gets the outer fetch's effective `skipLoading`, so the clamped request keeps the loading state it took over.
- **DataProvider tells EmptyDataState about a running fetch when a settings update turns it on** (`#onAfterUpdateSettings`, `orderIndex` 1, behind the plugins' own settings listeners). EmptyDataState raises its overlay from `beforeDataProviderFetch`, so an enable made while a fetch ran showed "No data" or nothing until the fetch landed. The sync runs for any payload naming `emptyDataState`; it is a no-op when the plugin is off or when nothing changes, and skipped while passive, because the owner's context change syncs with the arriving view's selection. It lives here, not in EmptyDataState, because that plugin must not know DataProvider exists (`releasedPluginsViewAgnostic.unit.js`).
- **A real `disablePlugin()` syncs EmptyDataState's overlay after its abort, the `updatePlugin()` cycle does not.** Both go through `#disable()`; the sync is `#abortFetchesAndSyncLoading()`, the same helper `_releaseContext()` uses. Without it, `updateSettings({ dataProvider: null })` during the first fetch aborted the fetch and left the loading overlay over the local rows that followed. The update cycle skips it because its refetch takes the overlay over, and hiding it in between would restore the selection and show the overlay again for the same fetch. A passive disable aborts nothing and syncs nothing: `_runContextChange()` syncs after its callback. Pinned by `__tests__/dataProviderDisableLoading.unit.js`, whose never-settling provider is the case that needs the sync: a provider that rejects on abort reaches the abort ending, which syncs on its own.
- **`_releaseContext(context)` aborts that context's fetch (no reason, like `destroy()`), adds it to `#releasedContexts`, and syncs EmptyDataState's overlay.** The default context is never added (a `WeakSet` cannot hold `null`, and a plain grid must keep working after its owner goes away); releasing it only aborts its fetch.
- **`_runWithoutFetching(callback)` is the owner's only way to reconfigure without side effects**, and its state lives in a `try/finally` (`#isPassive`, restored to the previous value, so calls nest), so a callback that throws cannot leave the plugin passive. While passive: `updatePlugin()` does not refetch, `disablePlugin()` aborts nothing, and `#onBeforeColumnSort`/`#onBeforeFilter` answer through `#answerPassiveSort()`/`#answerPassiveFilter()` — applying a sort or a filter is canceled (the rows came from the server), a clear runs locally (the sort clear only resets ColumnSorting's sort state: a local clearing pass would read a pre-sort index cache ColumnSorting never builds for a server-driven sort). An explicit `fetchData()` inside the callback still fetches. The scope is synchronous: an async callback leaves the passive state at its first `await`. When the plugin is (re-)enabled while a fetch of the current context is still in flight, `enablePlugin()` adopts that fetch's query (`#adoptPendingQuery()`).
- **`_runContextChange(callback)` is how the owner changes the view, and the only place the driven plugins' per-view state is synced.** It calls Pagination's `_resetDataProviderTotal()` first (the change renders, so the pager must already be neutral), runs `callback` inside `_runWithoutFetching()`, and in a `finally` calls EmptyDataState's `_syncDataProviderLoading(this.isFetching(), true)` and Filters' `_resetDataProviderRollback()`. `_restoreFetchResult()` calls `_resetDataProviderRollback()` once more, after the replay has put the arriving view's conditions back. Those three entry points are `_`-prefixed `@private` methods named for DataProvider concepts, reached through `getPlugin()` like the query modules reach Pagination, Filters, and ColumnSorting. The released plugins must never listen to an owner plugin's hooks (SheetsBar is unreleased, and they must not know it exists); `test/__tests__/releasedPluginsViewAgnostic.unit.js` enforces that for `emptyDataState/`, `filters/`, and `pagination/`.
- **What `_runContextChange()` does after the callback, in order, and why each step exists.** (1) `#detachErrorToasts()`: every error notification shown for an owner's context is tracked with its request kind and that context (`#errorToasts`, an entry dropped on `afterNotificationHide`, which also fires when a mutation notification times out; default-context notifications are not tracked). The ones still on screen for a view that was left are hidden and handed back through `onDetachedRequest` — the LATEST fetch failure of each such view, and every create/update/remove failure — so no Refetch action (which fetches whatever is current) can fetch the new view, no mutation failure sits over the new view, and the owner shows the failures again on return. A successful fetch shown for a context hides that context's FETCH notifications first (`#hideErrorToastsFor(context, true)`), so a failure already resolved is never handed back; a mutation failure is not resolved by a fetch and stays. (2) `#rederiveQuery()`: when the owner keeps no response for the arriving context (`getContextResult()` answers nothing: a never-visited view, or one whose first fetch failed), Pagination is put back on its configured `initialPage` and `pageSize` first (`_resetDataProviderPage()`, silent: a page hook here would start a fetch). It returns the configured `initialPage`, because the pager clamps its own page to the rows the grid holds until a response gives a total. Then the query is rebuilt from INITIAL + the plugins, takes that returned page, and the pending fetch's query is adopted. The page is no longer forced to 1: a view with a response has it replayed over the query right after, and one without fetches the configured page, as a plain grid's first fetch does (it used to fetch the page size the previous view left, on page 1). It must run after the callback, because enabling the plugin inside the switch reads the plugins while they still hold the departing view's sort and filters, and the arriving view's passive restore never re-syncs `#queryParameters`; the query a view without a stored response fetches with, its Refetch action, and its row header offsets all read it. A replay sets the stored query afterwards. (3) The EmptyDataState sync and (4) the Filters rollback reset. `_releaseContext()` syncs EmptyDataState too, because an aborted fetch fires no hook that would hide the overlay, and a release can happen outside a context change (a late owner, a rebuild, a teardown). It also hides every error notification of the released context, and `#detachErrorToasts()` drops entries of released contexts without reporting them: a teardown or a rebuild releases contexts without `_runContextChange()`, and a notification left on screen kept a Refetch that fetched whatever view was current then (or nothing). The EmptyDataState sync of a context change passes `isViewChange: true`, which makes the overlay take the arriving view's selection as the one it restores, and restore nothing when the change hides it: the selection it stashed when it appeared belonged to the view that was left.
- **The released plugins' entry points do nothing while their plugin is disabled** (`if (!this.enabled) return;` in all three). EmptyDataState is off by default, and its `#show()` → `activateScope()` throws on the scope a disabled plugin never registered. Pagination and Filters get the same guard for symmetry; neither has an observable effect while disabled (Pagination resets its total on enable, Filters overwrites the rollback target when each filter starts).
- **A fetch started for a context that is not shown never asks for the loading overlay**: `beforeDataProviderFetch` receives `skipLoading: true` for it, because its detached landing fires no hook that would clear the overlay on the view in sight (the page-clamp refetch, which inherits the original request's `skipLoading`, is the path that reaches this). The in-flight entry keeps the original flag, so `isFetching()` still answers for a view that is shown again while that fetch runs. The hook then gets a COPY of the params, so a listener that mutates them in place changes what `fetchRows` receives only for a visible fetch; an off-screen fetch (owner contexts only) ignores such a mutation.
- **After `destroy()`, every mutation still in the queue settles quietly, and none touches the destroyed instance.** `BasePlugin#destroy` deletes `this.hot`, and core replaces the instance's methods with post-mortem throwers, so each path checks `this.hot` at the moment it would use it: `#mutationTarget()`, `#refetchFor()`, `#notifyRequestError()`, `#revertUpdateFor()`, `#commitRowsUpdate()`, the remove follow-up, the enqueued functions of `updateRows()` and `#onAfterChangeForServerUpdate`, and the hook and render callbacks passed to `queueCrud()` and `commitRowsUpdate()` in `query/crud.ts` (which fall back to calling `hot` only when a caller passes none). A mutation that has not started is skipped; one that is running resolves without hooks, reverts, or renders. The unit test spies on the destroyed instance's `runHooks`/`render`, because the queue swallows an edit's rejection and a thrown post-mortem error is otherwise invisible.
- **Internal refetches bypass the public `fetchData()`**: the mutation follow-ups, the revert reload, and the page clamp go through `#fetchFor()`/`#refetchFor()` directly (they need the queued binding); only the default-context entry points (the ready step, `onDataReady()`, sort, filter, Refetch) go through `fetchData()`. A spy on `fetchData()` does not see them.
- **`_restoreFetchResult(result)` replays a kept response without `fetchRows` and without reloading rows.** The payload's rows are the rows the grid shows (the parameter type omits `rows` for that reason), and it carries `isRestored: true` — the one public trace of the contract, documented on `afterDataProviderFetch` so a listener can tell a replay from a network response. A network response never carries the key (a legacy spec may compare payloads with `toEqual`).
- **Known limitation: a manual `updateRows()` that runs after a context change is validated against the grid shown THEN.** The call builds its `rowData` from what is shown when it is made, but `runManualUpdateRowsMutation()` validates when the mutation runs — possibly behind a slow save — by finding each id in the rows the grid shows at that moment (`findVisualRowById()`), and `onRowsUpdate` goes to the context the call was made in. Only the grid's own edits (`#onAfterChangeForServerUpdate`) validate at queue time. Likewise, a default-context edit queued (not yet running) when an owner appears builds its payload when it runs, from the owner's view — parked, pre-existing class.
- **Pre-existing, documented, not fixed:** a failed update reverts through the VISUAL row it was queued with, so a sort that lands between the edit and the failure reverts the wrong visible row (base behavior, visible context only). An update whose validation settles after `destroy()` stops there (`runUpdateFromChanges()` and `runManualUpdateRowsMutation()` check `hot.isDestroyed` after the `await`), because every instance method throws once destroyed. The mutation queue is not cancelled on `destroy()`: a user callback (`onRowsCreate`/`onRowsUpdate`/`onRowsRemove`) already running still settles, but nothing after it reaches the grid (see the destroy rule above).

## Mutations and contexts

A mutation captures `#currentBinding()` when it is queued (`createRows`, `removeRows`, `updateRows`, the `afterChange` path), and `#mutationTarget()` resolves what its follow-up work runs for: an owner's context keeps the queued binding, so its callbacks and its refetch serve the context it was made in even after a switch; the default context re-reads the binding when the work runs, exactly as before. **Call `#mutationTarget()` at the moment each piece of work runs, never once up front**: `crud.ts` awaits `onRowsUpdate` before it refetches, and a plain grid whose `dataProvider` changed in between must refetch with the new config (pinned by the "a grid without sheets" Playwright spec).

- **Edit payloads of an owner's context are built when the edit is queued.** `#onAfterChangeForServerUpdate` calls `prepareUpdateFromChanges(..., { validateNow: true })` for a non-default context, so the row ids, changed values, and validation come from the rows the user edited, even when the mutation runs behind a slow one after a switch. The default context keeps building them when the mutation runs.
- A remove whose context is not shown when its follow-up runs reads the page and the row count from the latest response the owner keeps for that context (`getContextResult`), and falls back to the binding's query and the row count captured at queue time when the owner keeps none; a refetch for such a context takes its base query the same way (`#queryFor`, used by `#fetchFor`). Both numbers come from one response, so a remove queued on a full page 1 of a sheet the user then left on page 3 does not refetch page 2.
- A failed `onRowsUpdate` for a context that is not shown does not run the cell revert (the tuples address the grid shown now); `#revertUpdateFor` refetches that context instead, and the response goes to the owner.
- Unit coverage of the contract without SheetsBar: `__tests__/ownerContext.unit.js` (a fake owner object).

## Optional config keys vs the completeness check

`isCompleteDataProviderConfig()` (`utils.ts`) decides `hasExternalDataSource`. It iterates `REQUIRED_CONFIG_KEYS`, **not** `Object.keys(SETTINGS_VALIDATORS)`. Every validator in `SETTINGS_VALIDATORS` runs only when the key is present (`BasePlugin#updatePluginSettings`), but the completeness check runs the validator on the *absent* value. So a new optional key with a strict validator (`refetchAfterCreate`, `typeof value === 'boolean'`) would have made every existing config incomplete and silently turned server mode off — the pre-existing "complete config" unit test fails the moment the check iterates the validator keys again. Add optional keys to `SETTINGS_VALIDATORS` and `DEFAULT_SETTINGS`; add a key to `REQUIRED_CONFIG_KEYS` only when the plugin cannot run without it (DEV-1679).

`refetchAfterCreate` is read from the raw config (`#shouldRefetchAfterCreate()`), like every other key here, not through `getSetting()`. `#pluginSettings` in the base class keeps keys a later `updateSettings()` omits, so `getSetting()` would keep an old `false` alive after the integrator drops the key. Only the create path honors the flag; update and remove keep their unconditional refetch (remove also owns page-rollback logic that a skip would have to reason about).

**A manual apply after `refetchAfterCreate: false` must use `updateData()`, never `loadData()`.** `fetchData()` itself calls `loadData(rows, PLUGIN_KEY)`, and that is a full reload: it re-initializes the index maps, so ColumnSorting's column-state map comes back empty (no `beforeColumnSort`/`afterColumnSort` fires; `getSortConfig()` is just `[]`). The plugin survives this only because `afterDataProviderFetch` carries `columnSortConfig` and ColumnSorting's `#onAfterDataProviderFetch` restores it from the payload. An integrator who runs `hot.loadData(rows)` inside `onRowsCreate` gets the wipe without the restore: the header loses its indicator, and the next `updatePlugin()` copies the empty state into the query, so the following fetch runs unsorted (measured on the DEV-1679 demo page; the ticket's own snippet has this bug, and its `runHooks('afterDataProviderFetch', { queryParameters: {} })` makes it worse because a payload without `columnSortConfig` is read as "no sort"). `updateData(rows)` keeps the sort and the meta. Two gaps stay open as follow-ups: there is no public way to update the Pagination total without firing that hook by hand, and `afterRowsMutation('create')` does not carry the rows `onRowsCreate` resolved with.

**`updateData()` keeps cell meta by physical row, so the documented apply pattern appends.** Only `loadData()` calls `metaManager.clearCellsCache()`; `updateData()` rebuilds the `DataMap` and `fitToLength()`s the row index mapper, which adds the new index at the end. A `splice` into the middle therefore moves the data under the meta: the new row shows the pushed-down row's `readOnly`/comment/invalid mark, and every row below is off by one, until the next fetch. The guide's example uses `push` for that reason (review of #13563); a Playwright spec (`tests/e2e/data-provider-refetch-after-create.spec.ts`) pins that a `readOnly` mark stays on its record across the insert.

**The skip has two exceptions. The first: an in-flight `fetchRows` forces the refetch anyway.** The old post-create `fetchData()` also aborted whatever fetch was running (a sort or filter fetch started just before the insert) through `#createFetchAbortController()`. With the refetch skipped nothing aborts it, the mutation queue does not wait on fetches, and the integrator has no public cancel, so the late response would `loadData()` the applied row out of the grid. `createRows()` checks `#inFlight.has(context)` for its binding's context and refetches when it is true; `afterDataProviderFetchAbort` fires for the superseded request. `refetchAfterCreate: undefined` is valid (the base plugin validates every key that is `in` the object, and wrapper props send explicit `undefined`), and reads as the default.

**A second exception: a create whose context is not shown when it finishes refetches that context.** With the refetch off, `onRowsCreate` applies the rows itself, through `hot`, which shows another view by then. The recipe the guides show applies them only while the view that made the request is shown, so without the refetch that view kept the stored response it had before the create, and the new row was missing on return. The refetch goes to the owner through `onDetachedRequest` like every other off-screen refetch. Pinned by the `refetchAfterCreate off` block of `tests/e2e/data-provider-sheets-bar.spec.ts`.

## Row ids come from Core, row data from the copy

- **Read a row's id with `getRowIdByVisualRow()` (`query/crud.ts`), which asks Core's `getRowIdAtPhysicalRow()`, never with `getRowIdFromRowData(hot.getSourceDataAtRow(...))`.** Core applies `dataProvider.rowId` to the source row itself: an own property named exactly as a string key wins, a literal dotted one included, the way a cell is read, and otherwise the dots walk nested objects whatever `dataDotNotation` says. `getSourceDataAtRow()` returns a copy that `DataSource#getAtRow` rebuilds through `getProperty()`/`setProperty()` under `dataDotNotation`, which turns a literal `'sku.code'` key into a nested `sku.code` and lets a nested object at the same path overwrite it, so an id read from the copy disagrees with `getRowId()` and with the cell. The `rowIdOption` argument of the crud helpers is only a presence check now: the key itself is read from the settings.
- **Known limitation: `rowData` in the update payloads is still built from that copy** (`buildChangesAndRowData()`, `buildManualUpdateRowPayloads()`). For a row with a literal dotted key, `onRowsUpdate` gets the correct `id` but a `rowData` where that key is rebuilt as a nested object (or overwritten by one). The copy's rebuild is a `getSourceDataAtRow()` behavior that every source-data reader shares (`DataSource#readFromRow` calls `getProperty()` with no own-key check), and it is by design: the `dataDotNotation` JSDoc tells users with dotted keys to set the option to `false`, which makes every reader, `rowData` included, keep the literal key (GitHub #5439 was closed that way). Do not file it as a DataProvider bug.
- The id read does not run `modifySourceData`, and a function key receives the source row itself, not a copy.

## The fetch of an enable or update starts in the ready step

`enablePlugin()` and `updatePlugin()` fetch nothing themselves. The ready step (`onGridReady()`,
`../base/AGENTS.md`) starts the fetch once the call returns: at init before the `init` hook (it used to wait
for `afterInit`, after the first render), and on a live grid before the render that ends the call.
`#fetchOwed` is set by `enablePlugin()` only when it runs outside `_runWithoutFetching()`, and it is captured
then, not when the step runs: the step can run after the passive scope has ended (an enable made inside an
outer lifecycle pass), and a passive enable must never fetch. `onDataReady()` clears it when it starts the
fetch itself. A direct `enablePlugin()` call on a live grid now fetches; it used to wait for an `afterInit`
that had already fired. Pinned by `__tests__/readyStep.unit.js`.

## A fetch an update starts ahead of its data waits for `onDataReady()`

While core's `_applySettingsAndData()` applies settings ahead of their data (`isDataWorkDeferred()`,
`../base/AGENTS.md`), `updatePlugin()` leaves its silent fetch to `onDataReady()` (on a grid still being built,
where nothing is recorded, the ready step starts it). `fetchRows` is called
synchronously when a fetch starts, so without the hold it ran before the call had loaded its data, against the
grid the call replaces. A tab switch is passive (`_runContextChange()`), so nothing is fetched there; building a
workbook on a live grid is not, and an opening sheet with its own `dataProvider` fetches from `onDataReady()`.
Pinned by `__tests__/deferredFetch.unit.js`.
