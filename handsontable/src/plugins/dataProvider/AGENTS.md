# DataProvider plugin — server-backed grids and error UI

The `dataProvider` plugin backs the grid with a remote source via `fetchRows` and CRUD callbacks (`onRowsCreate` / `onRowsUpdate` / `onRowsRemove`). Read this before touching `dataProvider.ts` or wiring up error handling.

## Error UI contract (the trap)

- **Built-in error toasts require the `notification` plugin.** Enable `notification` (`notification: true` or a config object) to get toasts on failed fetches or mutations. **`dialog: true` alone does NOT show these errors** — Dialog is for blocking overlays (Loading, ExportFile export progress, custom modal content), not fetch/mutation errors.
- **Fetch-failure toasts include a Refetch button** that calls `fetchData()` again. The toast uses `duration: 0`, so it stays until dismissed or Refetch is clicked.
- **For custom error UI when Notification is disabled**, hook `afterDataProviderFetchError` and `afterRowsMutationError` instead of relying on the built-in toasts.

## Who is allowed to let `fetchData()` reject

`fetchData()` fires `afterDataProviderFetchError` and shows the error toast, then rethrows. That rethrow is public API — a caller awaiting `fetchData()` still gets the rejection.

- **Internal fire-and-forget refetches must go through `#fetchDataSilently()`**: the initial load (`afterInit`), `updatePlugin()`, the sort ctx, the filter ctx, and the Refetch toast action. The wrapper logs `Data fetch failed:` and resolves `null`. `void this.fetchData()` does NOT work — `void` discards the value, not the rejection, so a failing `fetchRows` reaches the page as an `unhandledrejection` (Sentry HANDSONTABLE-DOCS-20B / 1JN).
- **`#commitRowsUpdate`'s ctx (`fetchData: () => this.#refetchFor(target, { skipLoading: true })`) must keep rejecting for a visible binding.** `query/crud.ts` catches it to revert the optimistic cell values and log `Data reload failed:`. Do not "consistency-fix" this one to the silent wrapper.
- **Pagination ctx callbacks stay rejecting too** — `query/pagination.ts` catches them to revert the page or page size.
- **The one exception is an off-screen SheetsBar sheet.** See "SheetsBar: per-sheet server state" below — a grid without SheetsBar (`sheetId === null`) is always visible, so it never takes this path.

## SheetsBar: per-sheet server state (DEV-3041)

Each sheet gets its own binding, server view, and in-flight fetch, so a switch never mixes one sheet's rows into another.

- **A binding is `{ sheetId, data, config, workbook }`, captured fresh at the moment a fetch or mutation starts** (`#currentBinding()`). `sheetId` is `null` without SheetsBar. `#isVisible(binding)` compares the binding's `sheetId` with the active sheet id, never the `data` array: every on-screen landing hands the grid a new array (`loadData(rows.slice())`), and so does an `updateSettings` that carries `dataProvider`, so an identity check went stale after ANY on-screen load of the binding's own sheet — two quick edits, or a sort after a queued save, sent the second save's refetch into an orphaned array and deferred its failure toast forever. `workbook` is `#workbook` at capture time; `#isDropped(binding)` is true for a binding of an earlier workbook or of a removed sheet, and `#fetchFor`, the remove refetch, and `#reportRequestFailure` drop such work (no fetch, no recreated state, no toast; the public mutation hooks and the `console.error` log still fire).
- **`#states` and `#inFlight` are `Map<number|null, …>` keyed by sheet id.** `#states` holds each sheet's last successful response, its stored query parameters, a pending failure, and deferred mutation failures — created lazily by `#stateFor()`. `#inFlight` holds at most one running fetch per sheet; a newer fetch of the same sheet supersedes (aborts) the older one through `#abortFetchesFor()`, but a fetch for another sheet is untouched.
- **An off-screen fetch's response writes into the sheet's CURRENT data array in place** (`replaceArrayContents()` in `#storeFetchResult()`), not through `loadData()`. `#sheetData` records the grid's data array when `afterSheetTabStateCapture` reports the sheet being left (SheetsBar has synced the sheet record to that same array just before), and `#offScreenDataOf()` falls back to `binding.data` only for a sheet not left since the binding was captured. That keeps the array the SheetsBar sheet record points at, so the next visit shows the new rows, and the visible grid is never touched. A sheet binding's *visible* load still copies the rows first (`rows.slice()`) before handing them to `loadData()`, so a later off-screen response can never rewrite the array the grid is currently rendering — a grid without SheetsBar keeps loading the returned array directly, as it always did.
- **A stored response is the raw `fetchRows` result, and the `afterDataProviderFetch` payload is built when the sheet is shown** (`#buildReplayResult()`). `columnSortConfig` and `filtersConditionsStack` go through `hot.propToCol()`, which answers for the VISIBLE sheet's columns; building them at an off-screen landing mapped a sheet with its own `columns` through another sheet's layout (the sort indicator landed on the wrong column, filters on the wrong column or nowhere). The visible path builds its payload after `loadData()`, as the base code did — a grid without `columns` resolves a `prop` through the loaded rows' schema, which does not exist before the first load.
- **`#onAfterSheetWorkbookReset` forgets the whole workbook.** SheetsBar fires `afterSheetWorkbookReset` before it builds a workbook (enable, or a `sheets` rebuild) and when it is disabled. A rebuilt workbook numbers its sheets from 1 again, so without the reset a new sheet whose id matched an old visited one replayed the old sheet's rows and fetched nothing, and a plain grid's in-flight fetch (`null` key) could land in the workbook enabled after it. The listener aborts every fetch, clears `#states`/`#sheetData`/`#removedSheets`, bumps `#workbook` (so any older binding is dropped), and forgets the cached active id.
- **`disablePlugin()` outside a switch aborts only the visible sheet's fetch** (`#abortVisibleFetch()`, without a reason, like the base code). Re-configuring the visible sheet (rule 13) must not kill another sheet's detached fetch. `destroy()` and the workbook reset still abort everything.
- **`#isSheetSwitching` is set by `afterSheetTabStateCapture` and cleared by `afterSheetTabChange`, both registered with `this.hot.addHook` in the constructor, not `this.addHook` in `enablePlugin()`.** `disablePlugin()` calls `clearHooks()`, which would drop an `addHook`-registered listener on every `updatePlugin()` cycle; registering directly on `this.hot` (and removing the same way in `destroy()`) keeps the flag tracking a switch that spans a disable/enable pair. `afterSheetTabStateCapture` only fires once no listener has canceled the switch, so the flag is never set for a switch that does not happen.
- **`#onBeforeColumnSort` and `#onBeforeFilter` stand aside while `#isSheetSwitching` is true**, answering through `#answerSwitchSort()`/`#allowSwitchFilter()` instead of running their normal server-refetch path. SheetsBar's own view-state reset and restore fire `beforeColumnSort`/`beforeFilter` mid-switch (clearing, then re-applying, the arriving sheet's stored sort and filter state); running the ordinary handlers there would fetch with the wrong sheet's binding and race the arrival replay in `#onArrival()`, which is what actually puts the sort/filter indicators and rows back once the switch completes.
- **A binding's failure resolves `null` instead of rejecting when the binding is off-screen** (`#fetchFor`, `#refetchFor`). `query/crud.ts` reverts an update's optimistic cell values on a rejection; if an off-screen mutation's refetch rejected, that revert would land on whatever sheet happens to be visible at the time, not the sheet the mutation belongs to. The failure is still reported: `afterDataProviderFetchError`/`afterRowsMutationError` fire immediately, and the notification toast is deferred into `#states`, shown once the sheet becomes visible again (`#onArrival` → `#showDeferredFailure`/`#showDeferredMutationFailures`).
- **`afterDataProviderFetchError` carries a third argument, `isVisible`**, `false` for an off-screen sheet's failure. The in-tree listeners must honor it: Filters' rollback and EmptyDataState's overlay clear both act on the VISIBLE sheet, so an off-screen failure used to replace a filtered local (or other server) sheet's conditions while its rows stayed filtered, and drop the loading overlay of a visible sheet still fetching. Any new listener that changes the grid on a fetch error has to skip `isVisible === false` too.
- **A manual `updateRows()` that runs after a switch is validated against the grid visible THEN.** The call builds its `rowData` from the sheet visible when it is made, but `runManualUpdateRowsMutation()` validates when the mutation runs — possibly behind a slow save, after the user switched sheets — by finding each id in the rows the grid shows at that moment (`findVisualRowById()`), and `onRowsUpdate` goes to the sheet the call was made on. When two sheets share an id, the other sheet's row and validators decide; an id the visible sheet lacks skips validation. Only the sheet's own edits (`#onAfterChangeForServerUpdate`) validate at queue time. Known limitation.
- **A workbook rebuild on a live grid sends one extra `fetchRows` call that is aborted at once.** `#buildInitialWorkbook` resets the view state before it applies the opening sheet, and the sort and filter clears reach `#onBeforeColumnSort`/`#onBeforeFilter` while the departing sheet's `dataProvider` is still enabled (a build is not a switch, so they do not stand aside). Applying the opening sheet supersedes that fetch. It lands nowhere; specs that count fetches across a rebuild read `fetchCount` instead of hardcoding the fetch number.
- **DataProvider learns sheet ids only from the SheetsBar hooks' arguments, plus one `getSheets()` read.** `#onSheetSwitchStart`/`#onSheetSwitchEnd` cache the id from their hook parameters (`#activeSheetId`); the case the hooks cannot answer is the sheet a workbook opens with (startup, a rebuild, SheetsBar enabled later), so `#getActiveSheetId()` reads it from the public `getSheets()` and caches it until the next switch or workbook reset. **Do not gate that read on `sheetsBar.enabled`**: a rebuild applies its opening server sheet — and starts its first fetch — inside `SheetsBar#enablePlugin()`, before `super.enablePlugin()` sets `enabled`, and a gated read bound that fetch to `null`, which is "always visible", so switching away let the server rows overwrite a local sheet. `getSheets()` answers from the model, which exists during the build and is already gone (SheetsBar drops it first) while a teardown restores the grid-level settings, so the restored plain grid binds `null`. Without a workbook nothing is cached. This plugin never reads `getSheets()` on a hot path.
- **The grid-level `dataProvider` gate lives in SheetsBar, not here.** `../sheetsBar/AGENTS.md` covers `#withBaselineFor()` forcing `dataProvider: null` on a sheet without its own, the one console warning, and blocking a later grid-level value through `updateSettings()`. DataProvider only ever sees the config `updateSettings()` actually applies.
- **Known limitation: a switch that throws midway leaves `#isSheetSwitching` set.** If a `beforeSheetTabChange`/`afterSheetTabStateCapture` listener or a view-state validator throws during a switch, `#onSheetSwitchEnd` never runs, so the flag stays `true` — `#onBeforeColumnSort`/`#onBeforeFilter` keep standing aside — until the next switch completes and clears it. There is no recovery path today.

## Mutations under SheetsBar

A mutation captures `#currentBinding()` when it is queued (`createRows`, `removeRows`, `updateRows`, the `afterChange` path), and `#mutationTarget()` resolves what its follow-up work runs for: a SheetsBar sheet keeps the queued binding, so its callbacks and its refetch serve the sheet it was made on even after a switch; a grid without SheetsBar re-reads the binding when the work runs, exactly as before. **Call `#mutationTarget()` at the moment each piece of work runs, never once up front**: `crud.ts` awaits `onRowsUpdate` before it refetches, and a plain grid whose `dataProvider` changed in between must refetch with the new config (pinned by the "a grid without sheets" Playwright spec).

- **Edit payloads of a sheet are built when the edit is queued.** `#onAfterChangeForServerUpdate` calls `prepareUpdateFromChanges(..., { validateNow: true })` for a sheet binding, so the row ids, changed values, and validation come from the sheet the user edited, even when the mutation runs behind a slow one after a switch. A grid without SheetsBar keeps building them when the mutation runs.
- An off-screen remove reads the page from the sheet's state and the row count from the sheet's own array, not from the visible grid.
- A failed `onRowsUpdate` on an off-screen sheet does not run the cell revert (the tuples address the visible grid); `#revertUpdateFor` reloads that sheet from the server instead.
- **Off-screen mutation failures defer their toast like fetch failures.** `#reportRequestFailure` stores a `create`/`update`/`remove` failure in the sheet's `mutationFailures`; `#onArrival` shows each once (`#showDeferredMutationFailures`) and clears the list. The `console.error` log and the `afterRowsMutationError` hook still fire when the failure happens.

## Optional config keys vs the completeness check

`isCompleteDataProviderConfig()` (`utils.ts`) decides `hasExternalDataSource`. It iterates `REQUIRED_CONFIG_KEYS`, **not** `Object.keys(SETTINGS_VALIDATORS)`. Every validator in `SETTINGS_VALIDATORS` runs only when the key is present (`BasePlugin#updatePluginSettings`), but the completeness check runs the validator on the *absent* value. So a new optional key with a strict validator (`refetchAfterCreate`, `typeof value === 'boolean'`) would have made every existing config incomplete and silently turned server mode off — the pre-existing "complete config" unit test fails the moment the check iterates the validator keys again. Add optional keys to `SETTINGS_VALIDATORS` and `DEFAULT_SETTINGS`; add a key to `REQUIRED_CONFIG_KEYS` only when the plugin cannot run without it (DEV-1679).

`refetchAfterCreate` is read from the raw config (`#shouldRefetchAfterCreate()`), like every other key here, not through `getSetting()`. `#pluginSettings` in the base class keeps keys a later `updateSettings()` omits, so `getSetting()` would keep an old `false` alive after the integrator drops the key. Only the create path honors the flag; update and remove keep their unconditional refetch (remove also owns page-rollback logic that a skip would have to reason about).

**A manual apply after `refetchAfterCreate: false` must use `updateData()`, never `loadData()`.** `fetchData()` itself calls `loadData(rows, PLUGIN_KEY)`, and that is a full reload: it re-initializes the index maps, so ColumnSorting's column-state map comes back empty (no `beforeColumnSort`/`afterColumnSort` fires; `getSortConfig()` is just `[]`). The plugin survives this only because `afterDataProviderFetch` carries `columnSortConfig` and ColumnSorting's `#onAfterDataProviderFetch` restores it from the payload. An integrator who runs `hot.loadData(rows)` inside `onRowsCreate` gets the wipe without the restore: the header loses its indicator, and the next `updatePlugin()` copies the empty state into the query, so the following fetch runs unsorted (measured on the DEV-1679 demo page; the ticket's own snippet has this bug, and its `runHooks('afterDataProviderFetch', { queryParameters: {} })` makes it worse because a payload without `columnSortConfig` is read as "no sort"). `updateData(rows)` keeps the sort and the meta. Two gaps stay open as follow-ups: there is no public way to update the Pagination total without firing that hook by hand, and `afterRowsMutation('create')` does not carry the rows `onRowsCreate` resolved with.

**`updateData()` keeps cell meta by physical row, so the documented apply pattern appends.** Only `loadData()` calls `metaManager.clearCellsCache()`; `updateData()` rebuilds the `DataMap` and `fitToLength()`s the row index mapper, which adds the new index at the end. A `splice` into the middle therefore moves the data under the meta: the new row shows the pushed-down row's `readOnly`/comment/invalid mark, and every row below is off by one, until the next fetch. The guide's example uses `push` for that reason (review of #13563); a Playwright spec (`tests/e2e/data-provider-refetch-after-create.spec.ts`) pins that a `readOnly` mark stays on its record across the insert.

**The skip has one exception: an in-flight `fetchRows` forces the refetch anyway.** The old post-create `fetchData()` also aborted whatever fetch was running (a sort or filter fetch started just before the insert) through `#createFetchAbortController()`. With the refetch skipped nothing aborts it, the mutation queue does not wait on fetches, and the integrator has no public cancel, so the late response would `loadData()` the applied row out of the grid. `createRows()` checks `#inFlight.has(sheetId)` for its binding's sheet and refetches when it is true; `afterDataProviderFetchAbort` fires for the superseded request. `refetchAfterCreate: undefined` is valid (the base plugin validates every key that is `in` the object, and wrapper props send explicit `undefined`), and reads as the default.

## Testing

From `handsontable/`:

- Unit: `npm run test:unit --testPathPattern=plugins/dataProvider`
- Legacy specs for one area: `npm run test:e2e --testPathPattern=dataProvider/__tests__/methods/createRows` (the pattern is compiled into the bundle; re-run `test:e2e.dump` when you change it)
- Whole plugin: `npm run test:e2e --testPathPattern=plugins/dataProvider`

The `__tests__/` tree is split by kind: `methods/`, `hooks/`, `plugins/` (interactions with Pagination, Filters, ColumnSorting), `query/*.unit.js`, plus `alter.spec.js` for the context-menu insert/remove path. Specs that must assert "no refetch happened" wait on the `afterRowsMutation` spy: the refetch, when enabled, starts synchronously right after that hook, so `fetchRows` already reflects it.
