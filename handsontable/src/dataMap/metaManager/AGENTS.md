# Metadata management — landmines

This directory holds `MetaManager` and the meta layers that resolve the effective configuration of the grid, every column, and every cell through a prototype-chain cascade. Full reference: `handsontable/.ai/META-MANAGEMENT.md`.

- **Cell meta is keyed by PHYSICAL index — it survives moves and sorts.** `CellMeta` stores objects in physical-row by physical-column `LazyFactoryMap`s. The meta follows the data, not the screen position. Every `MetaManager` method takes physical coordinates (see the class JSDoc). Never store or look up cell meta by visual index.
- **Two `getCellMeta` methods exist — do not conflate them.** `MetaManager.getCellMeta(physicalRow, physicalColumn, { visualRow, visualColumn })` takes physical plus an options bag. `Core`'s `hot.getCellMeta(visualRow, visualColumn)` takes visual and converts to physical (`toPhysicalRow`/`toPhysicalColumn`) before calling the `MetaManager` one. This doc covers the `MetaManager` API.
- **Read defaults from, and add new options to, `metaSchema.ts`.** It is the single declaration point — every built-in option with its default and Typedoc. An option missing here has no default. **Never change an existing default — that is a forbidden breaking change.**
- **Every option needs a `@configScope` tag, and changing one means regenerating the docs.** The tag lists the configuration levels the option actually takes effect at, drawn from `grid`, `columns`, `cells`, `cell` in that order — for example `@configScope grid columns cells cell`. Put it right after `@category`. Decide the value from **where the grid reads the option**, not from where it can be written (the cascade is a prototype chain, so any option can be *written* anywhere): a read through `getSettings()`/`tableMeta` is `grid` only, because `TableMeta` is a sibling of the column branch; a read through `getColumnMeta()` is `grid columns`; a read through `cellProperties`/`getCellMeta()` is every level. A plugin toggle is always `grid`, because `BasePlugin` reads it via `getSettings()[PLUGIN_KEY]`. Two traps: an option read straight off the raw `columns` setting rather than the meta chain does **not** follow that rule (`title` is `columns` only; `columnSorting` and `multiColumnSorting` are `grid columns` because `getMergedPluginSettings()` merges `columns[n][pluginKey]`), and a `@private` option is skipped entirely, since jsdoc drops it from the API reference and the matrix would link at an anchor that does not exist. `handsontable/test/__tests__/optionLevels.unit.js` fails when a public option has no tag, when a level is unknown or out of order, or when the committed page has drifted — so after adding or changing a tag, run `npm run generate:option-levels --prefix handsontable` and commit both regenerated files. Where a level mark alone would mislead (`width` means two different things; a plugin toggle that is grid-level while its sub-options are per column), add a note to `NOTES` in `handsontable/scripts/utils/option-levels.js`; the notes reach the matrix page, not the API-reference badge.
- **Respect the cascade: cell → column → global.** The cascade is a prototype chain. A cell meta object's prototype is its column meta object, whose prototype is the global meta object (schema defaults plus instance settings). `TableMeta` is a sibling snapshot (`getSettings()`), NOT a cascade link — instance settings reach cells through GlobalMeta. The `cells` function layers on the cell, `columns` on the column.
- **Dynamic meta recomputes per render, not per call — keep `cells`/`columns` cheap.** `DynamicCellMetaMod` memoizes through `metaSyncMemo`, cleared on `beforeRender` with `forceFullRender`. The `cells` function and `before`/`afterGetCellMeta` hooks run once per cell per full render cycle. Heavy work there scales with the visible grid.
- **Persist with `setCellMeta`/`updateCellMeta`; do not mutate a returned meta object directly.** `setCellMeta` updates the `_automaticallyAssignedMetaProps` bookkeeping. Direct mutation bypasses it, so the value can be overwritten by `type` expansion or the `cells` function on the next render.
- **Every `setMeta` write is filed under exactly one origin, and the origin decides what survives `updateSettings`.** `updateSettings` clears the whole cell-meta cache whenever `columns`, `cells`, or `cell` is passed, then replays two of the three buckets (`core.ts`, the `clearCache` block). The bucket is chosen by which recording scope is open when `setMeta` runs, and the newest write for a key moves it between buckets — which is what makes an imperative override of a `cell`-option value stick. (1) **Imperative** — no scope open, tracked in `_userDefinedMetaProps`; replayed (GitHub issue #4446). (2) **`cell` option** — inside `startCellOptionMetaRecording()`, tracked in `_cellOptionMetaProps`; replayed, unless the call restates `cell`, because restating it replaces every prior entry (GitHub issue #5661). (3) **Plugin-declarative** — inside `disableUserDefinedMetaRecording()` alone, which is what `Core#_setCellMetaDeclarative` opens; tracked in neither, so it is **dropped**. That third bucket is load-bearing: ColumnSummary writes `readOnly` and `columnSummaryResult` through it and re-applies them from its endpoints on `afterUpdateSettings`, so replaying them would strand a stale value on a cell the new endpoints no longer cover. Do not collapse (2) and (3) into "declarative" — `_cellOptionMetaProps` exists precisely because `_persistedMetaProps` minus `_userDefinedMetaProps` would sweep (3) in with (2). Both replays use **physical** coordinates read from the map keys, so a value goes back onto the record it was resolved to, never onto whatever record now sits at the option's visual position. Four consequences worth knowing before you "fix" one of them:
  - **The bucket test for (2) is an equality, not `> 0`.** A `cell`-option scope raises both counters, a plain suspension raises one, so `#userDefinedMetaRecordingSuspendCount === #cellOptionMetaRecordingCount` means "no plugin scope is open anywhere". Testing `#cellOptionMetaRecordingCount > 0` instead files a `_setCellMetaDeclarative` write nested inside the `cell` loop as a `cell`-option write — reachable, because applying the option fires `beforeSetCellMeta`/`afterSetCellMeta` — and it is then replayed forever. `endCellOptionMetaRecording()` returns early when no scope is open for the mirror-image reason: it must never lift a suspension a plugin owns.
  - **A plugin write on a key the `cell` option declared drops that key from (2) permanently**, so the declared value is lost until `cell` is restated. That is deliberate: the snapshot reads the *current* value off the meta object, so keeping the key would replay the plugin's value as if the option had declared it. Fixing it properly means storing declared values separately from the live meta.
  - **The replay does not fire `beforeSetCellMeta`/`afterSetCellMeta`** — it writes through `MetaManager#setCellMeta`. A veto or a notification on a *restoration* would be wrong, and the (1) replay has always worked this way.
  - **The replay is not bounded to the live grid.** A value at a physical index the current `columns`/data no longer covers is re-materialized and comes back if the grid grows again. Same as (1); bound both or neither.
  - `row` and `col` on a `cell` entry locate it and are stripped before the write — they are not cell meta, and `getCellMeta` stamps those keys with *physical* indexes on every read.
- **Render-derived cell meta is evicted when it leaves the viewport — anything that must survive a scroll goes through `setMeta`.** `DynamicCellMetaMod` listens on `afterScrollVertically`/`afterViewRender` and evicts via a **gap-diff**: it tracks the keep band (viewport + one-viewport hysteresis) in visual space and `CellMeta.evictRow()`s only the visual rows that fall between the previous band and the new one — i.e. the rows that just scrolled out (row-axis only). Cost is O(scroll delta), NOT O(materialized), so a grid with many `setCellMeta`/`cell`-option rows pays nothing extra (do not "fix" this by iterating all materialized rows — that was measured as a real per-render/per-scroll regression). This bounds cell-meta memory to ~viewport instead of growing with every row ever scrolled. A cell is evicted only when it is purely render-derived (rebuilt on the next `getMeta` from the cascade, the `cells` function, and `type` expansion); eviction also clears the cell's `metaSyncMemo` entry so re-extension re-runs on re-mint. **Any value written via `setMeta` — imperative `setCellMeta` OR the declarative `cell` option — is recorded in `_persistedMetaProps` and is never evicted** (it is not rebuilt on access). If you add a path that stores must-survive state directly on a cell meta object without `setMeta`, it WILL be lost on scroll — route it through `setMeta`. Only the focus (highlight) cell's row is skipped — `selectedRange.highlight.row`, where the prepared/active editor holds the meta object by reference — NOT the whole selection: the other rows of a wide selection (whole column, multi-row) stay evictable. Eviction does not target plugin-path bulk materialization; because the gap-diff only scans the previous keep band, a row materialized far outside the viewport is released only when the viewport later scrolls across it (it is not swept while it stays off-screen). Bulk scans must therefore not materialize in the first place — see the read-path bullet below.
- **Bulk scans read meta through the no-retention paths — never loop `getCellMeta` over a row range.** Three reads exist, cheapest first: `getCellMetaUncached` (no hooks/`cells`, no store — used by `dataMap.get` and `filters`), `getCellMetaTransient` (full dynamic extension through the `extendTransientCellMeta` local hook, still no store — public since 18.1.0 as `Core.getCellMetaTransient(visualRow, visualColumn)`, which is how all internal consumers reach it: the `autoColumnSize`/`autoRowSize` samplers, the copy path (`DataMap.getCopyable`/`DataSource.getCopyable`), the `exportFile` data provider, bulk validation, autofill's fill loop, the checkbox toggle-over-selection loop and the checkbox `valueSetter`, and the per-change reads in `processChanges`/`validateChanges`/`populateFromArray`; cells with stored meta return their stored object without re-resolving it), and `getCellMeta` (extends AND permanently materializes — viewport/render use only). A loop of eager `getCellMeta` over the full row range retains O(rows × columns) metas that eviction cannot sweep. Two rules for the transient path: apply dynamic settings directly on the transient object (never through `updateCellMeta` — it materializes), and never read or write `metaSyncMemo` from it (the memo must reflect stored metas only, or later-stored cells skip their extension).
- **Writes stay eager where the result must persist.** `validateChanges` looks the validator up transiently, then switches to the stored meta only for cells that actually have a validator (validation writes `valid` on the meta, and that flag must survive). Cell-type `valueSetter`/`valueGetter` accessors run once per changed/read cell — they must read through `this.getCellMetaTransient`, never `this.getCellMeta` (the checkbox `valueSetter` is the reference example).
- **Bulk validation persists ONLY failures, by direct write.** `Core._validateCells` reads each cell transiently and, when a validator returns `false`, writes `valid = false` directly on the stored meta obtained with `skipMetaExtension` — never through `setCellMeta`, which would record the flag in `_persistedMetaProps` and change updateSettings/eviction semantics. The eviction pass already treats `valid === false` as a keep condition, so invalid markers survive scrolling; `valid === true` is intentionally not persisted for unmaterialized cells (reads back as `undefined`; every core reader branches on `!== false`).
- **A schema default must be read along the same path as the cell value — `schema[prop]` alone is wrong.** `metaSchema.ts`'s default `isEmptyRow`/`isEmptyCol` decide "empty" by comparing each cell against its `dataSchema` default, and `colToProp()` hands back a **dot-separated path** for a column bound to a nested property (`{ data: 'meta.active' }`). A flat `schema[prop]` lookup resolves `schema['meta.active']` to `undefined`, which never equals the leaf value the cell actually holds, so a spare row carrying nothing but schema defaults reports as non-empty — `countEmptyRows(true)` returns 0 and `adjustRowsAndCols` appends `minSpareRows` fresh rows on **every** change, without bound (GH #5069; the flat-schema half of the same bug was DEV-345). Both functions go through the local `getSchemaDefault()` helper, and the reader it must mirror is **`Core#getDataAtCell` -> `DataMap#get`** — not `DataSource#getAtPhysicalCell`, which is a *different* reader with a *different* rule. Five traps if you touch it, and the first two are regressions that were caught in review. (1) `DataMap#get` tests `hasOwnProperty(row, prop)` **first** and only then walks, so an own key wins even a literal dotted one, and even while `dataDotNotation` is on. Walking unconditionally breaks `dataSchema: { 'meta.active': false }`: the value side resolves the literal key while the default side reads `schema.meta`, which reintroduces the unbounded growth for that config. (2) The walk is confined to an **explicit** `dataSchema`. Without one `getSchema()` returns the duck-schema, and resolving a dotted path inside it newly reports a real row whose nested object holds only `null` leaves as empty — a behavior change for grids that never set `dataSchema`. (3) It must resolve a path running into `null` to `undefined` rather than throwing, because a schema may stop short of the depth a column asks for — which is why it does not just call `getProperty()`. (4) The comparison is only reached for a value that is not `null`, `''` or `undefined` (`isEmpty()` has already filtered those out), so an unresolvable path returning `undefined` can never compare equal to a cell's value. (5) The object-typed branch needs the same path-aware read, or a column bound to a nested *object* (`data: 'meta.tags'`) keeps the original miss. A function `columns[].data` accessor is deliberately read flat and resolves to `undefined` — the schema is a plain template with no accessor applied, so such a column is never treated as holding its default; that matches the behavior before the helper existed.
- **Do not confuse that with the duck-column mapping bug next to it.** `DataMap#recursiveDuckColumns` registers a property **only for schema keys whose value is `null`**, so with a `dataSchema` carrying non-null defaults and no `columns` option, those columns get no property, read as `null`, and render blank even though the data holds values. That makes such grids *look* like they pass a spare-row test — the rows count as empty by accident. It is a separate, still-open defect; do not treat a green `minSpareRows` result on a no-`columns` fixture as evidence the schema comparison works.
- **`updateSettings` clears the cell-meta cache, and it needs TWO snapshots to survive it — not one.** When the payload carries `cell`, `cells` or `columns`, `Core#updateSettings` calls `metaManager.clearCache()`. Everything written through `setMeta` is snapshotted by `getUserDefinedCellMetas()` and replayed with `setCellMeta` (GitHub issue #4446). That snapshot reads `_userDefinedMetaProps`, so it structurally **cannot** see `valid` — the validation flow writes it directly, per the two bullets above. The second snapshot, `getInvalidCellMetas()` / `restoreInvalidCellMetas()`, covers exactly that gap (GitHub issue #7553); the restore is a direct property write, because routing it through `setCellMeta` would mark `valid` user-defined and make every later cache clear replay a stale `false` onto a cell that has since been corrected. **Any future state stored directly on a cell meta object today needs its own snapshot pair here as well as its own keep condition in `evictRow()`** — the two guards are the same rule applied to the two different ways a meta object gets dropped, and a `_directMetaProps` set written by the direct-write paths would generalize both (`_persistedMetaProps` cannot be reused: declarative `cell`-option writes live there and must not be replayed). The trap is silent: the cell keeps its bad value and only the marker disappears. All three wrappers can trigger it, on different cadences — React re-sends `columns` on **every** render of a grid with `HotColumn` children (no gate at all), Angular on every `settings` input change, and Vue only when the column settings actually changed (it compares by reference and order first).
- **A cell flagged invalid is recognized by `isFlaggedInvalid()`, and the read is own-property-only.** `valid` is an ordinary meta key, so a grid can inherit `valid: false` from the column or global layer (`columns: [{ valid: false }]`, or any unrecognized top-level setting landing on `globalMeta`). Reading it through the prototype chain would report every materialized cell of such a grid as invalid, and the restore would stamp the flag on as an **own** property that outlives the setting that produced it and pins the cell against eviction forever. Only `false` counts, never `true`. `evictRow()` and `getInvalidMetas()` share the one predicate so the two keep rules can never disagree.
- **An async validator can outlive the cache clear, so every validation result goes through `persistValidationResult()` — in BOTH directions.** `validateChanges` hands `Core#validateCell` the *stored* meta object by reference, so an `updateSettings` landing while the validator is in flight detaches it and a write on it reaches nothing. Three symptoms, one cause, and the first is the only one that is obvious: a **failure** that never lands leaves the cell unmarked (the async half of #7553); a **pass** that never lands leaves behind the `false` that `restoreInvalidCellMetas` re-applied, so a corrected value keeps its red mark; and the `allowInvalid: false` cancel path writes `valid = true` on that same detached reference, so a *rejected* edit — where the cell keeps its old, valid value — stays flagged. Writing only failures through fixes one and creates the other two. Three rules inside the helper. It **peeks** (`getCellMetaIfExists`) rather than resolving, so a passing result never materializes meta on its own and `_validateCells` keeps its O(invalid cells) bound; only a failure materializes, because only a failure has to be rendered. It reads the **physical** coordinates off the meta object (`row`/`col`) rather than the visual pair — but those are not safe either: `LazyFactoryMap` re-keys stored metas on an insert or remove and does **not** rewrite the stamped `row`/`col`, so a pair captured before a structural change can name a different cell after it. `MetaManager#getStructureVersion()` is captured when validation starts and compared when the result arrives; when it moved, the result is **dropped** rather than written onto a cell the user never touched. It counts two different invalidations, and both are needed: row/column inserts and removes, and `clearCellsCache()` — `loadData` replaces the data behind every coordinate and is documented to reset cell state, so a result arriving after it would re-mark a cell the reset just cleared. `clearCache()` must **not** bump it: that is the `updateSettings` path this whole mechanism exists to survive. The direct write on the captured object already happened, and that object follows the shift on its own. And it returns early when the stored object *is* the one the caller already wrote to, which is the normal, still-attached case. The synthetic table-meta object `validateChanges` builds for a change naming no visual column has no stored counterpart and is skipped. This is the shape server-side validation takes, so it is the common case in practice, not an edge one.

- **Every meta write advances the cell's render version, except the per-render extension.** `CellMeta#setMeta`, `#removeMeta` and `#updateMeta` bump `_renderVersion` on the cell meta object (`core/incrementalRender/renderChangeTracker.ts`); `renderMode: 'onChange'` compares that number against the element's last paint. It is an own property on an object the caller already holds, so the read path pays no `LazyFactoryMap` hit — keep it that way, never move it into a side map keyed by coordinates. The dynamic extension (`DynamicCellMetaMod`, through `MetaManager#extendCellMeta` → `CellMeta#extendMeta`) bumps only when a merged value differs from what the meta holds (identity comparison per key): it re-applies the `cells`/`type` result on every full render, and counting an unchanged result as a change would repaint every such cell on every draw, while a `cells` function that reads outside state must still be detected. The `beforeGetCellMeta`/`afterGetCellMeta` hooks mutate the object directly and stay undetected (documented limit). The two validation sites in `core.ts` that write `valid` directly bump it by hand. A meta object rebuilt after eviction starts at version 0 ≠ the stamped one, which reads as "changed" — the safe direction.
