# License key validation and branding

Rules for `src/utils/entitlementLicenseKey/` (the key reader), `src/utils/licenseBranding/` (badge, popover, lock screen), `src/utils/licenseNotification.ts`, and the license half of `src/helpers/mixed.ts`.

- **Only a `tier:<name>` token restricts a key.** Whether a key restricts is decided by the tiers its Handsontable entry names: `getKeyTiers()` in `utils/licenseCapabilities/tiers.ts` reads every `tier:<name>` token from the entry's capabilities, and `_getLicenseState` (`helpers/mixed.ts`) exposes the list as `LicenseStateDescriptor.tiers` - `null` when the entry names no tier, which unlocks every feature. A key issued before tiers carries only `core` (or per-feature ids and the retired `listed-capabilities` flag), and a key issued since for no tier carries only `grid`, so each names no tier and keeps everything on: never read "no tier" or "no `xlsx:*` token" as "nothing unlocked". The flag, per-feature ids (`feat:filters`, `xlsx:styles`), `<namespace>:all`, and `core` in a key are ignored. With tiers, a plugin is on when its `LICENSE.tiers` lists one of them, and an xlsx feature when its `XLSX_TIERS_BY_ID` entry does (`resolveXlsxEntitlement(tiers)` in `utils/xlsxEngine/xlsxEntitlement.ts`); a tier this build does not know therefore turns every gated feature off, and the grid still renders with one console error and one bar. The license state has no `grants` facet any more: `{ lifecycle, channels, tiers, badge }`. `grants.ts` stays, because it is part of the port of the canonical reader. The tier is a capability token, not a payload field, on purpose: the key format does not change, so a key that names a tier is issued the way any other key is. The tier names and the feature-to-tier assignment live in the feature manifest (`src/featureManifest/AGENTS.md`, "Tiers").
- **`__tests__/buildTestKey.js`, `__tests__/fixtures.js` and `__tests__/xlsxLicenseKeys.js` have an external consumer**: the Playwright fixture `tests/fixtures/xlsxLicenseKeys.ts` imports them through Playwright's loader, and `tests/fixtures/licenseTiers.ts` reaches them through it. Moving or renaming any of them breaks the license specs in `tests/e2e/` as well as the Jest suites; update those fixtures in the same change. Two helpers build tier keys. `keyWithTier(tiers, flags)` and `keyWithoutTier(tokens, flags)` in `xlsxLicenseKeys.js` are pure (no `jest`, no registry), so Playwright can import them; a `keyWithTier()` key is perpetual to 2099 so nothing depends on the clock, and a `keyWithoutTier()` key (perpetual to 2099 as well) proves that ids without a tier change nothing. `tierKeyWith(ids, flags, dates)` and `tierKeyWithout(ids, flags, dates)` in `__tests__/tierKeys.js` make a new made-up tier per call and add it to the features the key should unlock (a spy on each plugin's static `LICENSE` getter, and a frozen copy of `XLSX_TIERS_BY_ID` that stands in for the shipped, frozen table). Every suite that calls them calls `resetTierKeys()` in `afterEach`, and a suite that uses `jest.resetModules()` must `require()` the helper after the reset, or it patches a registry the code under test no longer reads. Tests never use the real tier names: a later change to the assignment must not break them.
- **License key validation is inlined and layered**: an entitlement key (plain-English prose followed by a machine-readable `[...]` block) is read by `src/utils/entitlementLicenseKey/` (`detectFormat.ts` = which format a key is in → `extractKeyData.ts` = key reader → `classify.ts` = window evaluation + silencing flags → `grants.ts` = capability tokens) — a port of `src/entitlement-key/` from the private `handsontable/license-key` repo; never add that package as a dependency, and keep the reader byte-compatible with it (a key the canonical validator rejects must not read here). The obfuscated legacy 25-character block in `helpers/mixed.ts` is frozen — an entitlement key routes out BEFORE it via the trailing-block shape test, and legacy CONSOLE behavior (including exact message text) must never change. **One legacy DOM behavior did change, by product decision (DEV-2562):** a missing or invalid key no longer renders a bottom bar — it renders the blocking modal instead (see below). **One legacy console sentence was dropped, by product decision (PRO-1357):** the missing-key message (the console text and the bar text in `mixed.ts`, and the lock copy in `licenseBranding/content.ts`) no longer tells the developer to pass `'non-commercial-and-evaluation'`, because 19.0 reads that key as invalid. Do not bring the sentence back. **And the key itself stopped being recognized, by product decision (PRO-1356, 19.0):** `detectFormat.ts` recognizes no literal key, and the two legacy checks in `mixed.ts` (`_injectProductInfo` and `_classifyLegacyKey`) no longer compare `non-commercial-and-evaluation` or its second form `ht68e-1f2b7-47158-70b05-0842f`. Both reach the frozen legacy validator, fail its checksum, and read as `invalid`: the invalid-key lock and the invalid-key console warning, with no tiers (`tiers: null`, everything on) like every invalid key. The `non_commercial` state is gone from `NonEntitlementLifecycleState` and from both message tables. Do not add a literal key back here: the vendored reader takes its literal keys from the product (`detectLicenseKeyFormat(key, literalKeys)`), and Handsontable has none. Nothing else about the legacy path moved. **How a key is verified is documented in the private `license-key` repository, not here, and must stay out of this public file** - the key format and its versions in `.ai/ENTITLEMENT-KEY-FORMAT.md`, whose "Handsontable port" section holds the rules specific to this reader (18.1 compatibility, the keys already issued, the last sync). Read it before changing `extractKeyData.ts`; `vendor/entitlement-key-reader/` is copied into public repos, so nothing about the scheme goes there either, and keep the verification details out of this file, the code comments and pull request descriptions. The rules that matter here: change the reader only together with the canonical reader, and diff the port against `vendor/entitlement-key-reader` at the revision `__tests__/fixtures.js` names (`license-key` commit 12b800468a, after 6.2.0, at the last sync); every key format must stay readable by Handsontable 18.1, and the keys already issued must keep reading (the website form issues trial keys every day), so never tighten a rule on its own here - a key the canonical reader accepts must read here, and one it rejects must not; read payload fields as own properties, never through the prototype chain; do not bring back the `license-key` 5.0.0 rule, which was never released and locked 18.1 out of new keys and this reader out of the keys already issued. Never cut a key down to its block or strip characters from it before reading. Copy `PROSE_WHITESPACE` and `ESCAPED_WHITESPACE` verbatim from the vendored reader, never as `\s`, and keep their `\u` escapes as escapes - the file must stay 7-bit ASCII, and a raw U+2028 ends the regex literal. Fixtures are whole keys from the generator (`__tests__/fixtures.js` names the commit), because `buildTestKey` uses this reader's own helpers and so cannot catch a mismatch with the generator. A key whose block a mail client wrapped reads here and does NOT read on 18.1 (it locks the grid there). Whitespace AROUND the whole key IS trimmed, by `_trimKey` at the head of both `_injectProductInfo` and `_getLicenseState`, because an untrimmed key reads as `invalid` and `invalid` now blocks — trim in one of the two and they desync). **No contract type in the payload**: which of `usage_until` / `release_until` is present decides how the license is measured, and the `trial` flag decides only how it is worded — a key may name tiers (`tier:<name>`, above), but code never branches on a specific tier name, mode or plan name: a tier is only ever compared with the `tiers` a feature's generated license lists. Exactly one of the two dates per product, a real bare `YYYY-MM-DD` STRING, or the key is invalid (`parseIsoDateToTimestamp` checks the type first: `['2027-08-12']` stringifies to a valid date, and an object with a non-function `toString` throws when stringified - a key must only ever read as data or as `null`, so never stringify a payload value before checking it is a string); `notice`/`grace` arrive IN the key (no behavioral constants in the library). Date rules that the specification's J-fixtures pin: `usage_until` is inclusive (valid until the UTC midnight that FOLLOWS it), the notice window is `notice > 0 && daysRemaining <= notice` with days counted UTC-midnight to UTC-midnight (60 at the window's open, 0 on the last licensed day), the hard stop is expiry + 1 day + `grace`, and `release_until` is compared to the build release date as TEXT (no clock, airgap-safe, fails OPEN when the build date is unavailable). Reading is STRICT about shape and LENIENT about vocabulary: an unknown product, capability token, flag or extra field is kept and ignored, never an error, or every token added on the issuing side would break builds already in the field. A key that grants another product but not `handsontable` is not a Handsontable license — it messages as invalid, and it names no tier (`tiers: null`). The `tiers` answer is uniform across key families: legacy/missing/invalid keys resolve to `tiers: null` (everything on), so capability gating can never take a feature away from an existing customer. **So does an entitlement key whose Handsontable entry names no tier** (`tiers: null`). Every key issued before tiers lists only `core` or feature ids, and the reader's `hasCapability()` answers `false` for every token an entry does not list, so a gate that read the reader's grants would turn off every paid feature of every customer. The rule lives in `mixed.ts` and `licenseCapabilities/tiers.ts`, never in the reader port, which stays byte-compatible with the canonical reader (whose own `AGENTS.md` says the same). The gate built on it is `src/utils/licenseCapabilities/` (resolve, check, report) plus the message half in `licenseNotification.ts`; its rules are in a bullet of their own below. The branding UI is a MODULE CATALOG (`src/utils/licenseBranding/`: `index.ts` = state routing (read once at init), `content.ts` = copy, `badge.ts` = corner badge + popover, `lockScreen.ts` = the blocking lock screen) — a core util, NOT a plugin (plugins can be absent or disabled; license UI must not be). The corner badge + popover render for TRIAL states ONLY (`POPOVER_CONTENT` in `content.ts` holds exactly `trial_valid`, `trial_notice`, `trial_soft_stop`). Every other state — expired legacy, a running or lapsed subscription, a perpetual license (and the two blocking states, which show the modal instead) — shows NO badge; its console message and any bottom bar still come from `initLicenseNotification`/`_injectProductInfo` (the legacy console/bar messaging stays untouched, and `_classifyLegacyKey` in `mixed.ts` mirrors the frozen checks read-only). The two silencing flags are per product and resolved once into `descriptor.channels`: `no-console-warns` closes the console, `no-ui-warns` closes every WARNING surface (badge, popover and bar) — that is what keeps license copy away from the end users of a customer's SaaS app, so never render a license *warning* without checking `channels.ui`. **The `badge` flag (`BADGE_FLAG`) is not a channel, and no channel closes it:** it says the licensee agreed to show the "Powered by Handsontable DataGrid" bar (a sponsored license's term), which is branding, not a warning, so the bar renders outside the `channels.ui` gate, with or without `no-ui-warns`. The reader only keeps the flag in the entry's `flags`; `resolveChannels` ignores it, and the surface that shows the bar (DEV-3413) reads it from the entry itself. A key issued for external use carries `no-ui-warns` AND `badge` (fixture `SPONSORED_BADGE_EXTERNAL_KEY`), which is exactly the case the flag exists for. Do not confuse it with the trial corner badge, which `no-ui-warns` does close. **It does NOT close the LOCK (DEV-2709).** The flag covers UI *warnings*; the hard stop is the *enforcement* of a license that has stopped — so `mountBrandingSurface` routes `LOCK_CONTENT` BEFORE the channel gate, and only the badge sits behind it. What this fixed is external/SaaS **trials**: they are the only externally-issued keys that can be blocked at all (a lapsed subscription `usage_hard_stop` has no `LOCK_CONTENT` entry and blocks nothing, and `release_expired` never blocks). Only `trial_hard_stop` changes in practice — `invalid` and `missing` describe keys whose flags could not be read, so both always resolve to open channels and reached the lock either way. **This is a product decision, not a reading the specification states:** §4.1 heads its behavior column "Behaviour (unless `silent`)" over a hard-stop row reading "Trial: block", which read literally puts the block inside the silenced set, while §2.3's `trial` row separates "Trial messages" from "hard-stop block". The spec still needs amending to record the split — do not revert this from §4.1 alone. The same caveat is repeated at `NO_UI_WARNS_FLAG` (`entitlementLicenseKey/constants.ts`) and on `LicenseChannels` (`types.ts`), because those are the definition sites a maintainer reads first. The corner badge is click-through (`pointer-events: none`) so the corner header keeps its native select-all — hover is detected by delegation (`is-corner-hover` class), and the glyph itself is pure CSS - an `::after` inside the corner header cell, gated by BOTH `ht-license-badge-on` (on the root element) and `ht-license-badge-corner` (a class JS stamps on THIS grid's own corner-clone table, resolved via the Walkontable overlay); the glyph CSS keys off that marker, NEVER the structural `.ht_clone_top_inline_start_corner` class, which also matches a nested grid's corner clone and would paint a stray badge there. So it can never overflow or drift out of the corner; never rebuild it as a measured overlay (the overlay version broke visual tests with misaligned badges) - JS measurement exists only to anchor the popover. The mask carries the whole logomark (the "H" and its dot) in one color, in the corner glyph and in the lock-screen strip alike; the lock box has the mark's own 11.1415:16 proportions so its "H" starts at the start padding in RTL too. Only the corner glyph paints the blue dot, as a second `background-image` layer (`$license-badge-dot` in `_license-branding.scss`) drawn in the same viewBox, so both sized `contain` and centered land on each other - draw any new layer in that viewBox, keep `background-position: center`, and keep the brand blue inside the image. The popover is a PURELY VISUAL floating element: no focus scope, no shortcuts, badge/link/close all `tabindex="-1"`, visibility is pointer-only, close is mouse-click only (the info is duplicated in the console + bottom bar). The hard stop renders the CORE-OWNED lock screen (`lockScreen.ts`) — NEVER the Dialog plugin (a shared surface an app legitimately uses: any `show` would replace the lock, any hide would look like a dismissal, and `dialog: true` setups would never tear it down); the lock instead REUSES the confirm-dialog CSS by wearing its class names (`ht-dialog ht-dialog--confirm handsontable ...` — the stylesheet always ships in full, so styling is inherited without importing the plugin) and copies its width sizing (pin `style.width` to the table workspace width on `afterViewRender`, or the `.ht-dialog` box spans the whole root wrapper, not the grid). The lock DOES use the focus manager (modal scope) + shortcut manager (Tab trap only - the lock is non-dismissable, so there is no Escape/close). THREE states render the lock, and `LOCK_CONTENT` in `content.ts` IS that routing — adding a state to that table is what makes it block: `trial_hard_stop`, `invalid`, and `missing`. The last two are the specification's §4.5 shape, whose message text was answered by the product owner as 'the sentences the bottom bar used to carry', so those two states now show the modal INSTEAD of a bar (`_rendersBlockingModal`/`_BLOCKING_MODAL_STATES` in `mixed.ts` withhold the bar in both emitters; the console message is untouched, and the two locks point at support@ rather than sales@ because both are install faults, and carry the bar's documentation link as a real anchor inside the description). A hard-stopped subscription (`usage_hard_stop`) still blocks nothing and shows nothing: it repeats its soft-stop console error and that is all (18.1 never blocks a paying customer). **The soft-stopped trial deliberately shows BOTH a bar and its auto-opening popover, carrying the same two sentences — do not "de-duplicate" it (tried and reverted under DEV-2709).** The bar is the only license surface with a focusable link and a registered focus scope (`licenseNotification.ts`), while the popover is pointer-only by design (`tabIndex = -1` throughout, no focus scope, no `aria-live`); and the bar is the only surface that survives dismissal — on a grid with no corner cell, `is-cornerless` kills the hover path and every CSS rule that reopens the popover, so once the X is clicked the message is gone for the instance's life. Removing the bar there needs the popover to become keyboard-reachable and re-openable first. **Consequence for tests: a grid built with no `licenseKey` is now BLOCKED** — the lock deselects the cell and takes the keyboard, so every test grid must declare a key (the Jasmine helper injects `TEST_LICENSE_KEY` from `test/helpers/licenseKey.js` already; jsdom unit tests that call `new Handsontable` directly must import it and set it themselves, or selection-dependent assertions fail for no visible reason). Each suite reads its key from one place: `test/helpers/licenseKey.js` here, `tests/fixtures/demo/test-license-key.js` (`window.htTestLicenseKey`) in the Playwright fixtures, and a `licenseKey.ts` or `license-key.ts` in each wrapper's tests. Only a test of the license behavior itself writes a key out, and `scripts/__tests__/test-license-key.test.mjs` (root `test:tooling`) fails on a literal key in any other test file. The license key is read ONCE at init (like the console message and the bottom bar) — `updateSettings({licenseKey})` does NOT re-brand; applying a new key needs a fresh instance. Expiry compares against the build's release date, read BARE as `process.env.HOT_RELEASE_DATE` (in `licenseNotification.ts` and `licenseBranding/index.ts`) — the bundler (rspack DefinePlugin for `dist/`, SWC `inlineEnvVars` for `tmp/`) replaces it with a string literal, so NEVER wrap it in a `typeof process` guard: the guard is not inlined, compiles to `false` in browser bundles, blanks the date, and silently disables expired-key detection (an 18.0.0 regression). The badge reads its corner clone through the Walkontable API (`getOverlayByName`), NEVER a CSS `querySelector` on the root subtree (a nested grid — handsontable cell type — has its own corner clone earlier in document order that a selector would wrongly match). `extractEntitlementKeyData` memoizes on the key string (it is read twice per init) and returns frozen data, as the canonical reader does - copy an array before sorting or changing it. User-facing sentences repeated across surfaces (bar, popover, lock) live once as constants in `mixed.ts` (e.g. `_LICENSE_EXPIRED_TITLE`; every license symbol there is underscore-prefixed, because `index.ts` copies each non-underscore export of that module onto the public `Handsontable.helper`) — edit the constant, not each surface; every message is transcribed from the license specification, so reword it there first. Dates print as bare `YYYY-MM-DD`, with the `(UTC)` marker on console messages for `usage_until` and none on `release_until` (no clock takes part) or on the end-user-facing UI. The state-keyed tables (console/DOM notifications in `mixed.ts`, badge/lock content in `content.ts`) are typed `Partial<Record<LicenseStateKey, …>>`, NOT `Record<string, …>` — a typoed or unknown state key is then a compile error instead of a silently dropped entry. Test fixtures: real generator-produced keys in `src/utils/entitlementLicenseKey/__tests__/fixtures.js` (one per worked example of the specification) plus a test-only key builder (`buildTestKey.js`) for the shapes the generator refuses to produce; it must never be imported from `src/`.
- **The capability gate (`src/utils/licenseCapabilities/`, DEV-3658).** A key that names tiers (the first bullet) unlocks every REGISTERED plugin whose static `LICENSE.tiers` lists one of them: the tiers come from each plugin class's `LICENSE` (generated from its `feature.json`, see `../../featureManifest/AGENTS.md`), never from a global table, so moving a feature between tiers is a manifest edit and an unregistered plugin adds nothing. There is no `implies` at run time and no `<namespace>:all`: the generator already refuses a tier that includes a feature without what it requires. The result is cached per key string AND the registered plugin count, because a plugin registered later changes the answer; the count comes from `countRegisteredPlugins()` (`plugins/registry.ts`), never `getPluginsNames().length`, which copies and sorts the registry on every check (every plugin asks on every `updateSettings()`, and CheckboxHeader on every render). A nested grid (menus, the Filters value list, a grid inside a cell) is never checked (`isRootInstance`). Three places check it: `BasePlugin#isLicenseBlocked()` for `gate: 'enable'` plugins, at the init turn, in `onUpdateSettings` and in the `enablePlugin()` lifecycle wrapper, so a direct call from an app is checked too (the rules, and why a plugin the key keeps off blocks no hard-conflict partner, are in `../../plugins/base/AGENTS.md`), `assertLicensedCall()` at the top of the public methods of the `gate: 'call'` plugins that are on in every grid (ExportFile, ImportFile, ViewState: report, write the message, then THROW the same text; an async method rejects), and `isLicensedUse()` where a check runs during a render and must not throw (CheckboxHeader's `hasHeaderCheckbox()`). **The message is batched, never written per plugin.** A check records the feature (`reportMissingCapability()`, per root grid and key). A plugin the key keeps off at enable passes a check of its own (option still on, plugin still not running), and `pruneMissingCapabilities()` drops it from the list once that fails, so turning the option off takes it out of the bar; a feature refused on a call stays, because the key still leaves it out. `flushMissingCapabilities()` in `licenseNotification.ts` writes the list: from an `init` listener that `initLicenseNotification` adds (after every plugin's init turn during `beforeInit` and its ready step, before the first render), from an `afterUpdateSettings` listener at order index 1000 (after every plugin's own default-order listener, so one `updateSettings()` gives one message), at once from a throwing call gate, and from a microtask after a render. It does nothing before that `init` listener ran (`readyGrids`), whatever asked for it: a gated call from an `afterLoadData` listener runs during init, before the lifecycle bar, and a bar mounted there registered the focus scope that the lifecycle bar then registered again, which throws; and a user `init` listener (added before this one) that calls `updateSettings()` or a gated method would print a short list. The `init` write names everything reported until then. **A feature checked during a render is reported from the settings before it**: CheckboxHeader's `hasHeaderCheckbox()` runs in the header render, which draws only the columns in view and draws nothing in a hidden grid, so the plugin checks every column from its ready step and on `afterUpdateSettings` (`#reportUnlicensedColumns()`, skipped when the key covers the feature); a check only from the render printed a second, longer error once the header was drawn. The bar mounts after `initLicenseBranding`'s height pass, so core reserves the bottom slot's new height right after the `init` hook and before the first render (`reserveSlotsChangedAtInit` in `core.ts`: `reapplyPixelRootHeight()` and the slot observer's seed), and once more after the first render, which sets the slot to the table's width and can wrap the bar onto more lines (rendering again only when the height moved; both before `afterInit`); without it the first render and a pixel `height` read right after the constructor counted the bar's room as grid until the slot observer rendered a frame later. Pinned by `tests/e2e/license-capabilities.spec.ts` and `__tests__/callGates.unit.js` in `../licenseCapabilities/`. The record compares the set of tokens it last wrote, not a count, because one pass can drop one feature and add another. The list is sorted by display name, because the bar shows names only; every new feature prints the whole current list again, so the latest error alone names everything the key leaves out. The console error prints once per page per key and set of features (`printedMissingFeatures`), and only when the list gained a feature (a shorter list updates the bar alone); and `no-console-warns` / `no-ui-warns` close their surface only: the feature stays off. **One bar per grid.** The text goes into the grid's one `.hot-display-license-info` element as a second `_inner` block (`hot-display-license-info_missing-features`) when a lifecycle message already holds the bar (a perpetual key that names tiers, past its maintenance date), and a grid with no bar gets one through `mountBottomLicenseBar()`; never mount a second bar, because `getNotificationElement()` reads the first and the focus scope is one per grid. Build the bar and its blocks with `_createLicenseBar()` and `_createLicenseBarBlock()` (`mixed.ts`); the frozen legacy emitter keeps its own inline copy of the same shape. A key passed later that leaves nothing out takes the block away (and the bar, when it holds no lifecycle message), and forgets the list, so a later restricting key shows it again. The bar the gate built is kept per grid (`ownBars`) and put back rather than built again: its focus scope is registered once, and `registerScope()` throws on the same id twice. The sales address is a `mailto:` link, which is what the bar's focus scope lands on from the keyboard. **The gate never writes the plugin's setting** (unlike a hard conflict at init), so `getSettings()` keeps what the user wrote and a later key whose tiers include the feature turns it on. The cost is that a blocked plugin's `isEnabled()` answers `true`, so code that asks another plugin whether it RUNS reads `.enabled`, everywhere in `src/`: `test/__tests__/crossPluginIsEnabled.unit.js` fails on any `.isEnabled()` call whose receiver is not `this` or `super`, and its allowlist holds the one read that means the option (Loading's `enablePlugin()` switching the Dialog option on). The reads it replaced were not harmless: an XLSX export threw on a blocked ColumnSummary (no endpoints, like MergeCells' missing collection), an import wrote live formulas and `'`-escaped text for a blocked Formulas, and ManualRowResize kept a resized row at its declared height for a blocked AutoRowSize. **A blocked plugin's public methods are not checked**, and they behave exactly as the methods of a plugin turned off by its option, because neither ran `enablePlugin()`: measured on 2026-11-02 over 17 calls in 10 plugins, every result matched, and the ones that throw a bare `TypeError` (MergeCells `merge()`, HiddenRows `hideRow()`, ColumnSorting `sort()`, NestedRows `collapsingUI`) throw it with the option off too. The gate adds no new failure, but an app that set the option expects the methods to work; the license guide tells it not to call them. Checking every method of the 45 `gate: 'enable'` plugins would be a change of its own. Cell types are not checked (`gate: "report"`; they are sold in every tier). Message copy: `_buildMissingFeaturesMessage()` in `mixed.ts`, transcribed from the specification (rev 6, section 10.4). It returns two forms of the list: the console text, which is also what a refused call throws, names each feature as `<display name> (<token>)` for the developer, and the bar names it by display name only, because the bar can reach the end users of an app; keep tokens out of anything rendered in the grid. Fixtures: tier keys from the helpers in the second bullet. The three flagged keys left in `__tests__/fixtures.js` (license-key 6.2.0: `FLAGGED_BASE_KEY`, `FLAGGED_FEAT_ALL_KEY`, `UNFLAGGED_WITH_TOKENS_KEY`) stay only to prove that the retired flag and per-feature ids change nothing (`licenseCapabilities/__tests__/resolveLicenseCapabilities.unit.js`). The E2E demo page `tests/fixtures/demo/license-capabilities.html` applies made-up tiers by redefining each sold plugin's static `LICENSE` getter (`tests/AGENTS.md`).
- **The "Powered by Handsontable DataGrid" bar (`src/utils/licenseBranding/poweredByBar.ts`, DEV-3413).** `initLicenseBranding` mounts it when the Handsontable entry is a trial (`lifecycle.isTrial`, every trial state) or carries the `badge` flag (`LicenseStateDescriptor.badge`, set by `_getLicenseState` from `BADGE_FLAG`; `false` for every key outside the format, an unreadable one, and under the `*.handsontable.com` bypass). Five rules. (1) **It is branding, not a warning**, so it is mounted BEFORE the lock and outside the `channels.ui` gate: `no-ui-warns` keeps it, which also means an external trial now shows it (a product decision taken in DEV-3413). No option turns it off. (2) **It is its own element (`.ht-license-powered-by`), never a block of the warning bar (`.hot-display-license-info`)**: the warning bar is a `no-ui-warns` surface, its `_inner` blocks and `hideMissingFeaturesInBar()` would treat it as a message, and the specs assert "no warning bar" for a running trial. Like the warning bar it is a foreign node of the bottom slot (never registered with the `LayoutManager`, so the `layout` setting cannot remove it) with a focus scope of its own (`licensePoweredBy`); the warning bar's `appendBarLast()` inserts in FRONT of it, so the branding stays the last line whichever mounts later. (3) **The link's rules are scoped under the bar** (`.ht-license-powered-by .ht-license-powered-by__link`): the bar carries the `handsontable` class, and `.handsontable a` / `a:hover` would otherwise paint the text and the "H" in the link color and underline them. Figma (`JXZaX61arXLhlAi0WK3YNj`, node 1424:19574) draws no hover state for the bar, the text in the bar's color and the "H" in the brand's black (`light-dark(#000, #fff)`, a fixed logo color like the blue dot, not a token). (4) **A license bar mounted at init must be counted against a pixel `height`.** `updateSettings()` writes the height while the slots are empty, the bars mount after it, and the slot observer is seeded with the height they leave, so it never re-applied: the grid grew past its declared height by the bar (35px on the main theme). `core.ts` re-applies the height once after `initLicenseBranding` when the license UI changed the slots' height; this covers the lifecycle warning bar too. The missing-features block is written later, on the `init` hook, and core reserves it again right after that hook and after the first render (`reserveSlotsChangedAtInit`). (5) The bar's geometry follows the license tokens (8px x 16px padding and 12px / 18px text at the default density, 4px x 8px and 11px / 16px on classic), and the logomark is centered on the FIRST line, so a grid narrower than the text wraps it without the mark drifting.
