# Handsontable Core Package

This is the core data grid package. **TypeScript** - source files in `src/` are `.ts`. Type declarations are **auto-generated** by `tsc --emitDeclarationOnly` (`npm run build:types`, task defined in `scripts/tasks.json`) into `tmp/*.d.ts` — do not hand-edit them. The `types/` directory has been **deleted** — do not recreate it. Walkontable (`src/3rdparty/walkontable/src/`) is also TypeScript and is now type-checked by the main `tsconfig.json` — it still has its own separate build (rspack) and test (Puppeteer) pipeline.

## Critical Rules

- Use `throwWithCause()` from `src/helpers/errors.ts`, never `throw new Error()`
- No barrel imports from `plugins/index`, `editors/index`, `renderers/index`, `validators/index`, `cellTypes/index`, `i18n/index` - import from specific submodule paths. Only exception: `src/registry.ts`
- **Every plugin, cell type, editor, renderer, and validator has a feature manifest entry**: `feature.json` in the plugin's folder, or the registry folder's `features.json` (`src/cellTypes/`, `src/editors/`, `src/renderers/`, `src/validators/`). A new one is not complete without it, and the unit suite fails until it exists. A plugin's `PLUGIN_DEPS` is declared there (`requires.allOf` plus `"enforceAtInit": true`) and generated into `feature.generated.ts`, and so is the license token (`LICENSE`) of every sold plugin, with the tiers that include it – never write either in the class, and never edit the generated file. The XLSX license token lists are generated the same way, into `src/utils/xlsxEngine/licenseCapabilities.generated.ts`. After changing a manifest file run `npm run generate:feature-manifest` and commit what it writes. The files also build `dist/manifest.json`, which maps each feature to the tiers that include it (a license key names tiers, not features), so a token, once merged, is never removed or renamed. Rules: `src/featureManifest/AGENTS.md`.
- No global `window`, `document`, `console` - use `this.hot.rootWindow`, `this.hot.rootDocument`, and helpers from `src/helpers/console.ts`
- **Shadow DOM / sandboxed hosts:** never decide "is the focus / this click inside the grid" from raw `document.activeElement` or a `parentNode` walk — both lie when the grid renders inside a shadow root, and Salesforce Lightning Web Security additionally filters `composedPath()` down to the host chain and collapses `activeElement` to the outermost shadow host. Use `getDeepActiveElement()` and `getShadowHostChain()` from `src/helpers/dom/element.ts`, `event.composedPath()` (checking for `ShadowRoot` entries to detect a filtered path), and `getFocusManager().hasBrowserFocus()` / `.isForeignFocusTarget()` — see `tableView.ts` outside-click handling and the `focusManager` for the reference patterns. The same lie reaches any listener bound above the shadow root: `event.target` is **retargeted** to the host, so `eventTargetEl(event)` reports the host and every attribute, dataset flag or containment test then describes the wrong element. A grid inside a shadow root selected no cell on Tab because of that, and through two independent failures at once: the focus catcher's `data-ht-focus-source` was read off the host, so the source degraded to `unknown`; and the host is an *ancestor* of the scope container, so containment answered `false` whatever the source (DEV-2886). Resolve such a target with `getComposedEventTargetEl(event)` instead: it returns `composedPath()[0]` only when that node is rendered inside the retargeted target's own shadow tree, so a collapsed LWS path falls back to `event.target` unchanged. **Containment is the other half, and it needs its own walk.** A scope answers with `Node.contains()`, which stops at a shadow root, so a target resolved from inside a shadow tree the container merely *hosts* — a web component rendered in a cell — reads as outside the grid: the scope deactivates and the grid unlistens on an interaction that never left it. `scopeContains()` in `focusManager/scopeManager.ts` falls back to `getShadowHostChain()`, asking the scope about the elements its container can actually see, and **both** call sites use it — the focus/click path and the Tab-time catcher update, whose `getDeepActiveElement()` descends into those same shadow trees. Split them again and the catchers get re-armed under a focused widget, trapping the next Tab inside the grid.
- Private fields use `#` prefix, not `@private` JSDoc
- JSDoc cross-references use the inline `link` tag in qualified `Class#member` form (`{@link Core#getCellMeta}`) — **never** TypeDoc's `[[Target]]`. The API reference is generated by `jsdoc-to-markdown` + `dmd`, not TypeDoc, so `[[Target]]` reaches the published page as literal text (DEV-2728 shipped that on 10 pages). Use inline code for anything the API reference does not document — an unresolvable link tag silently points at a page that does not exist. `@fires` and `@throws` take a bare target instead (`@fires Hooks#afterChange`, `@throws {Error}`). Enforced by `test/__tests__/jsdocLinkSyntax.unit.js`, which also scans `docs/content`.
- **Required**: Plugin hook callbacks must be arrow function class fields — `#onAfterX = (arg1, arg2) => { ... }` — and passed directly: `this.addHook('afterX', this.#onAfterX)`. Never wrap in `(args) => this.#onX(args)` or use `.bind(this)`.
- Cognitive complexity: keep each function at 15 or below
- Optional chaining `?.` only when value is genuinely optional by design
- No hardcoded user-visible strings in source - add constants to `src/i18n/constants.ts` and update all language files in `src/i18n/languages/`
- No direct cross-plugin imports - use hooks for inter-plugin communication, or `hot.getPlugin('Name')` if API access is required
- Never use raw `setTimeout` - use `this.hot._registerTimeout(fn, delay)` instead; it auto-clears on `hot.destroy()`, preventing memory leaks
- DRY: reuse existing helpers and mixins; if code repeats, extract a generic helper rather than duplicating
- Method ordering: public methods first, then private listeners
- In text and comments, always write `Handsontable`, never `HOT` (a `hot` variable holding an instance is fine)
- Never call `String.prototype.toLocaleLowerCase`/`toLocaleUpperCase` directly — use `localeLowerCase()` from `helpers/string` (faster, locale-correct, crash-safe). Enforced by `no-restricted-syntax`. See `.ai/CONVENTIONS.md`.
- Never call a JavaScript method newer than `../browser-targets.js` (Chrome >= 130, Edge >= 130, Firefox >= 132, Safari >= 18.2, iOS >= 18.2 — the pinned Baseline 2024 set). swc lowers syntax only and adds no core-js polyfills, so such a call throws `X is not a function` on a supported browser. Two gates catch this: `tsconfig.json` pins `lib` to `ES_TARGET` (`es2024`) from `../browser-targets.js`, so an above-floor built-in is a type error in `.ts` files; `no-restricted-syntax` covers the same methods plus the 12 remaining `.js` files in `src/` (`allowJs` is off). That rule bans one name, `with` → `arr.slice()` plus an index assignment, and it is above the floor on two engines at once: `core-js-compat` puts `Array#with` at Firefox 140 (against our 132) and `TypedArray#with` at Safari/iOS 26.0 (against our 18.2). Verify any new method's floor against `core-js-compat`'s `data.json` before using it, and add it to the rule when it sits above the floor.
- `throwWithCause()` assigns `cause` after construction instead of passing the constructor options bag. The options-bag overload is ES2022 (Chrome 94 / Firefox 91 / Safari 15.0) and now sits well inside the floor, so this is no longer a compatibility requirement — it is kept because an engine that accepts the options bag and drops it silently leaves `error.cause` undefined and breaks `error.cause?.handsontable === true` detection with no visible failure. Do not "simplify" it back to `new Error(msg, { cause })` without adding a test that would catch that.

## Plugin Lifecycle

```
isEnabled()      → return !!this.hot.getSettings()[PLUGIN_KEY]
enablePlugin()   → init state, create IndexMaps, register hooks. super.enablePlugin() AT END.
updatePlugin()   → this.disablePlugin(); this.enablePlugin(); super.updatePlugin();
onGridReady()    → optional: rows, hot.view, DOM, editor work. Core runs it once after every
                   enable/update, when all of them exist. Never guard on hot.view in enable/update.
disablePlugin()  → super.disablePlugin() FIRST. Then clean up.
destroy()        → null out fields. super.destroy() AT END.
```

Gold standard: `src/plugins/pagination/pagination.ts`

**Every `src/plugins/<name>/` directory has its own `AGENTS.md` — read it before touching that plugin.** It
carries what the plugin owns, what it does not, and the traps specific to it. Two of them are not features
and are worth knowing by name: `src/plugins/base/AGENTS.md` holds the plugin contract itself (the five
statics, the `onUpdateSettings` state machine, hard conflicts, and the full `PLUGIN_PRIORITY` table with
its load-bearing orderings), `src/utils/manualResize/AGENTS.md` holds the drag gesture and helpers the
two resize plugins share, and `src/utils/menu/AGENTS.md` holds the menu library (`Menu`, `ItemsFactory`,
`registerMenuEntries()`) that ContextMenu, DropdownMenu, and the plugins adding menu items share. When a plugin-specific rule is discovered, it belongs in that plugin's file, not here.

## Three Coordinate Systems

| Type | Description | Use for |
|------|-------------|---------|
| Physical | Position in source data array | Data access, persistence |
| Visual | Position after trimming (DataMap) | User-facing display logic |
| Renderable | Position after hiding (DOM) | DOM operations |

Translate with `hot.rowIndexMapper` / `hot.columnIndexMapper`.
Gotcha: Filters `conditionCollection` uses physical indexes, `getDataAtCol()` uses visual.

## Testing

| Type | Pattern | Framework | Run |
|------|---------|-----------|-----|
| Unit | `*.unit.js`, `*.unit.ts` | Jest (jsdom) | `npm run test:unit` |
| E2E (legacy, frozen) | `*.spec.js` | Jasmine (Puppeteer) | `npm run test:e2e` |
| E2E (new) | `tests/e2e/*.spec.ts` | Playwright | `cd tests && npm test` |

**New E2E is Playwright** in `tests/e2e/` (skill: `handsontable-playwright-e2e`). The Jasmine `*.spec.js` suite is frozen — edit existing specs, but add no new ones, and migrate broken ones to Playwright. What to test in which framework, and when a test is even required, is machine-enforced by the presence gate; the decision rules are in `.ai/TESTING.md`.

- ALL `it()` callbacks in spec files MUST be `async`
- HOT API calls MUST be `await`-ed
- E2E helpers are globals (no imports): `handsontable()`, `selectCell()`, `getDataAtCell()`, `createSpreadsheetData()`
- Targeted unit: `npm run test:unit --testPathPattern=<regex>` or `npm run test:unit -- --testPathPattern=<regex>` (regex matched against file paths, e.g. `filters`, `ghostTable.unit`)
- Targeted e2e: `npm run test:e2e --testPathPattern=<regex>` or `npm run test:e2e -- --testPathPattern=<regex>` (e.g. `collapsibleColumns`, `textEditor`, `nestedHeaders/__tests__/hidingColumns`)
- E2E with theme: `npm run test:e2e --testPathPattern=<regex> --theme=horizon` (themes: `classic`, `main`, `horizon`; default: `main`)
- Re-run one spec file alone against an existing dump: `npm run test:e2e.puppeteer -- --specFile=<path-pattern>` (files only; `--spec=<pattern>` must match the spec names too, because Jasmine's boot reads it as a name filter)
- **Rebuild before E2E:** E2E runner loads `dist/handsontable.js` - rebuild after changing `src/`
- Verify no exceptions appear in the console during tests
- **A red Puppeteer run reports its failed specs as data, not only as a log.** `test/scripts/run-puppeteer.mjs` receives every Jasmine result through the page bridge. On a red run it re-runs each failing spec file alone (up to 5, `ISOLATION_PROBE_MAX_FILES`), then writes `test/e2e-results/failed-specs-<runId>.json` (uploaded as an artifact and collected across runs by `.github/workflows/test-health.yml`), prints one `::error` annotation per failed spec on GitHub Actions (attached to the spec file), and appends a step-summary block. A file that **passes alone** failed because of the specs that ran before it; one that **fails alone** is broken on its own. The spec file is known because `test/e2e/index.js` records which `require.context` key added each top-level suite (`window.__hotSpecFiles`) and the bridge reporter stamps it on every result as `filePath` — a top-level `it()` outside any `describe`, and `MemoryLeakTest`, have none. The pure helpers live in `test/scripts/lib/failed-specs.mjs` (node:test, part of the root `test:tooling`). Details: `.ai/TESTING.md`, "What a red run leaves behind".
- **CI runs the Unit job only for a change the scope router routes to it.** `test-handsontable-unit` in `.github/workflows/checks.yml` must cover every file the Jest run loads, and `.github/scripts/__tests__/unit-scope.test.mjs` fails when it does not. A Jest test that reads a file as data, such as a docs page or a workflow, still skips a pull request that changes only that file, so a pin like that belongs in the root tooling suite. Details: the root `.ai/CI.md`.

## Common Pitfalls

- **Wrapper UI placement**: The root wrapper has `ht-slot-top`, `ht-grid` (grid + empty-data-state), `ht-slot-bottom`, `ht-overlay` (last). Add plugin UI to a user-orderable edge slot via `hot.getLayoutManager().register(key, element, { side: 'top'|'bottom', weight })` and `unregister(key, side)` on teardown — `register` owns the DOM placement, so do NOT `appendChild` into the slot elements yourself. `getLayoutManager()` throws on non-root instances, so guard slot calls with `isRootInstance(this.hot)`. Edge-slot order is user-overridable through the `layout` setting (`top`/`bottom`). The slot registry is data-driven from `LAYOUT_SLOTS` (`src/core/layout/constants.ts`) — `register`/`getSlot`/`applyConfig`/the manager constructor all derive from it, so adding a slot (e.g. `start`/`end`) means extending `LAYOUT_SLOTS` + wiring its element + CSS. `ht-grid` and `ht-overlay` are fixed internal elements (NOT slots, not orderable); a plugin needing the overlays layer (e.g. Dialog, Notification) appends into `hot.rootOverlaysElement` directly. `LayoutManager.destroy()` keeps its slot map (only clears contents) so a plugin's `disablePlugin` running after core destroy stays safe. See `src/core/layout/`. **Slot sizing is core's job, never a plugin's.** Three rules, all in core (DEV-2848). (1) The engine subtracts the height of the slots that live INSIDE the vertical axis owner through the `layoutReservedHeight` Walkontable setting (`TableView#getReservedSlotHeight`, memoized per render); with an explicit pixel `height` the root element owns the axis and contains no slot, so core subtracts the slots from the pixel height it writes on the root instead (`calc(<height> - <slots>px)`, `reserveEdgeSlotsHeight` in `core/rootSize.ts`) — that used to be Pagination's own `beforeHeightChange` hook, which left a sheets bar 38px past the declared height; the hook stays public but no plugin should reserve again. (2) When the grid's height is content-driven — the window owns the vertical axis, or `height: 'auto'` — the wrapper carries `ht-grid-follows-content` and the stylesheet stops the `.ht-grid` flex item from shrinking to a CSS-sized container (`flex-shrink: 0`), so a bar lands after the last row and not over one. **The wrapper itself keeps `height: 100%`**: the overlays layer (`.ht-overlay`: dialog, notification) sizes against it and must stay at the container's height, and nothing then resizes the wrapper on a content change. (3) `syncEdgeSlotsWidth` clamps a slot to the wrapper's `clientWidth` only when the window owns the horizontal axis (an explicit `width` wider than its container keeps the bar as wide as the grid box); in a shrink-to-fit host the wrapper sizes to its children, but the slot is never written wider than the table, so the clamp tracks the table downwards. While the window owns the horizontal axis, a table with no rendered columns (an empty sheet, every column hidden) is the exception: it is only as wide as its row header, so the slot takes the wrapper width instead, or the sheet tabs and the pagination bar get squeezed into that strip; a narrow table that has columns still gets a narrow slot. An explicit `width` keeps the slot at the grid box with no columns too. In a shrink-to-fit host the wrapper's width there comes from the slot itself, so an empty sheet keeps the width the previous sheet left. A slot's height feeds both (1) paths and nothing else observes it, so core watches `rootSlotTopElement`/`rootSlotBottomElement` with a `ResizeObserver` (`slotsResizeObserver`) that re-applies the pixel height (`reapplyPixelRootHeight`) and renders on a real change — a bar that mounts after init, wraps after a locale switch, or grows a scrollbar once its width is clamped. Pinned by `tests/e2e/bottom-slot-sizing.spec.ts` and `src/__tests__/core/layoutSlotReservation.unit.js`.
- **`afterSetDataAtCell` carries VISUAL rows while `afterSetSourceDataAtCell` carries PHYSICAL ones** (`core.ts` `setSourceDataAtCell`), and only `setDataAtCell` writes are validated by the Core — `setSourceDataAtCell` runs `sourceDataValidator` (`dataMap/sourceDataValidator.ts`), a separate mechanism that never touches the `valid` flag. Any listener on both hooks must handle the two coordinate spaces and the two validation paths separately. `prop` needs no such care: `propToCol()` returns a visual column on both paths. Undo/redo deliberately bypasses the Formulas plugin's change listeners; the full per-action rules are in `src/plugins/formulas/AGENTS.md` and `src/plugins/undoRedo/AGENTS.md`.
- **An index-mapper cache update must invalidate the axis size cache whenever the mapping changed.** `onIndexMapperCacheUpdate(state, axis)` in `core.ts` calls `view.invalidateRowHeightCache()` / `view.invalidateColumnWidthCache()` when **any** of the three change flags is set. Do not narrow that to `indexesSequenceChanged`, and do not widen it to unconditional. The engine's `PositionCache` re-checks only the item **COUNT**, so a sort, a row/column move, or a trim/hide swap that changes *which* indexes are excluded but not *how many* leaves it serving the previous layout's offsets — the grid then renders short and leaves blank space past the last rendered track (DEV-2823, an 18.1.0 regression). Narrowing to the sequence flag was the first fix and still missed the same-count case — that one is a correctness bug, and each flag needs its own test or a dropped flag ships green. Dropping the gate entirely is only untidy, not slow: it makes every forced no-op `updateCache` pay a cache and layout drop that cannot change anything (the timeout once blamed on it did not reproduce — the full unit suite passes either way). The caches are keyed by RENDER index while the sizes behind them resolve per PHYSICAL index, which is why nothing else notices. Full mechanics, and the second reorder-blind cache (`oversizedRows`), in `src/3rdparty/walkontable/AGENTS.md`.
- **Raw versus effective frozen counts (`limitFixedToViewport`, #4259).** With the option on, `TableView` holds a memo of the counts the grid really draws (`_effectiveFixed`, visual counts with hidden tracks included), resolved in `render()` before `_wt.draw` and refreshed on full renders only. Scroll-only draws keep it. After a full draw it measures once more and draws once more if the answer moved (a row that was never drawn counted at the default height, or a horizontal scrollbar took room from the rows); there is never a third pass, and `beforeViewRender`/`afterViewRender` fire twice on such a render. The pre-draw measure reads engine values only. The post-draw one also reads the rendered height of each row (`getFrozenTrackSize(…, true)`), because the engine records the height of a content-tall row only for the rows the master renders, so a tall frozen row reads as the default height there. That DOM read is only safe after a draw: before one the row filter can be stale and `getCell` throws. The heights the post-draw pass read are kept (`#drawnRowHeights`, by physical row), so the next measure starts from them and a render of unchanged content draws once, not twice. The row read uses the first column the master renders, not the row header, whose row in the header clone is not always as tall as the content row. Each axis keeps the configured counts when its holder has no client size (a hidden grid, a closed tab, a grid never drawn), because clamping against 0 would collapse every band and `measureWorkspaceHeight()` falls back to the window height for a hidden grid, so it cannot be the test. The room is the workspace minus the headers AND the holder's own scrollbars (`offsetWidth - clientWidth`), because the workspace measure is the client size of the root, which still contains them; without it classic scrollbars of 15 to 17 px would leave a strip near 25 px, not the 40 px the docs promise. A grid the window scrolls keeps its root size when the window is resized, so `refreshDimensions()` finds no change and does not render: `Core#refreshDimensions()` measures once more (`TableView#renderWhenWindowResizeMovedFixed`) and renders when the counts moved. It does so only after `beforeRefreshDimensions` let the resize through, so a blocked resize stays blocked. `getFrozenTrackSize()` reads the DOM only when rendering is not suspended and only for a cell that is the row's own (a cell covered by a vertical merge resolves to the block origin, whose row is another row), and the drawn heights are dropped with the size caches (`invalidateRowHeightCache()`), because they are keyed by physical row. Changed counts mark every cell changed (`#setEffectiveFixed`), because a merged block that crosses a moved freeze line must repaint under `renderMode: 'onChange'`. With the option off the memo is `null` and every accessor returns exactly what it did before. The accessors are `countFixedColumnsStart()`, `countFixedColumnsEnd()`, `countFixedRowsTop()` and `countFixedRowsBottom()`, and the `countNotHidden*` methods derive from them. They clamp the memo on every read against the configured counts and the current `countCols()`/`countRows()`, because a memo from the last render can outlive an `alter('remove_col')` or an `updateSettings` that lowered a count, and they ignore the memo when the option is off, so a toggle takes effect before the next render. **Anything that compares a position against the frozen band** (scrolling, editors, shortcuts, `manualColumnMove`, `manualRowMove`, `mergeCells`, `customBorders`, `collapsibleColumns`, `freezeBar`) reads those accessors. **Anything that describes what the data means** keeps the option: `alter()` and the filler guard, `columnSorting`, `filters`, Pagination's conflict, export and import, `undoRedo`, `sheetsBar` and the selection transformation that creates spare rows. `ManualColumnFreeze` is not on this list: unfreezing works on the drawn start band (`getStartBandCount()` in its `endBand.ts`), because the user sees that band, while freezing counts from the configured band and asks `TableView#canFreezeStartColumn()` whether the column fits (the drawn count is a memo of the last render, so two freezes before a render would read it stale). Every end-band check of the plugin (`isInEndBand()`, the unfreeze shift check) compares the configured end count (`getEndBandCount()`), because the drawn one is already clamped against the drawn start and a column in front of the configured band would be shifted into it. `manualColumnMove` reads the drawn start band, and the configured end band for the same reason. `collapsibleColumns` also keeps the configured counts for its group guards, because a group collapsed inside the configured band would land in the frozen band when the grid grows. Walkontable's `getSetting('fixed…')` follows for free, because the settings closures call the `countNotHidden*` methods. Three traps. (1) The measurement goes through `measureWorkspaceWidth/Height()` (`viewport/workspaceSize.ts`), never `Viewport#getWorkspaceWidth()`: in single-pass layout that goes through a snapshot whose calculators read the frozen counts, so asking it here recurses or freezes the draw on the old counts. (2) The walk is bounded (`resolveFittingFrozenCounts` in `utils/frozenAreaFit.ts` stops as soon as the sizes pass the viewport), so a `fixedRowsTop` of 100000 does not walk the axis. (3) `shouldRenderInlineStartOverlay`, `shouldRenderTopOverlay` and `shouldRenderBottomOverlay` still read the raw option on purpose: an enabled overlay with no tracks is an existing state, and toggling an overlay between draws is not. **The inline-end overlay is the exception.** Walkontable's default `shouldRenderInlineEndOverlay` reads the clamped, drawn `fixedColumnsEnd`, so the end overlay and both end corners toggle when the drawn count crosses 0 (the start band covers the viewport, or the grid shrinks). That is on purpose too: the default already tied that overlay to the clamped count so an end band the start band fully covers draws nothing, and a fourth gate on the raw option would keep an empty end clone over a grid that draws no end band. The memo is a plain `_effectiveFixed` property, not a `#` field, because the unit tests of the count accessors run them on `Object.create(TableView.prototype)`. A container sized by its own content does not redraw when only the outer element resizes, so the clamp may not update there until the next render. Pinned by `tests/e2e/limit-fixed-to-viewport.spec.ts` and `src/utils/__tests__/frozenAreaFit.unit.ts`.
- **`fixedColumnsEnd` freezes the LAST columns and is clamped against `fixedColumnsStart`, start first.** The clamp is `clampFixedColumnsEnd` in `3rdparty/walkontable/src/settings/fixedColumnsEnd.ts`, applied by the Walkontable Settings accessor; `TableView#countNotHiddenFixedColumnsEnd` feeds it the not-hidden count. `alter('remove_col')` decrements the option when removed columns fall in the end band (the mirror of `fixedRowsBottom` on `remove_row`). A reader of the raw option anywhere in core or a plugin sees the unclamped value, so use `TableView#countFixedColumnsEnd()` (visual band size over `hot.countCols()`, the total the renderer uses, capped by `maxCols`) instead of calling `clampFixedColumnsEnd` with a total of your own. `core.ts` `adjustRowsAndCols` creates no `minSpareCols` or `minCols` filler column while the option is set (a column appended after the band would take over the frozen slot; inserting before it is unsafe because the filler bookkeeping tracks a trailing run only and an `auto` insert skips the cell meta shift). An explicit insert does NOT move the band (`insert_col_*` leaves `fixedColumnsEnd` alone, the same as `insert_row_*` with `fixedRowsBottom`): a column inserted inside or after the band takes a band slot, and the caller raises the option in `afterCreateCol` to keep the same columns frozen (pinned by `src/__tests__/core/insertColFixedColumnsEnd.unit.js`). `TableView#countNotHiddenFixedColumnsEnd` floors the option the way `clampFixedColumnsEnd` does, so a fractional value cannot make the renderer draw no band while `countFixedColumnsEnd()` still reports one. `BaseEditor#getEditedCellRect` subtracts the end band (`inlineEndOverlay.getBandWidth()`, plus the gap to the last column when nothing scrolls horizontally, plus the freeze-line overlap below, so the editor's end border stays clear of the line) from `maxWidth` for every cell outside the end clones, because the end clones paint over the master editor. The first column of each end clone is rendered 1px wider and covers the inline-end border of the column before the band, so the clone's own first-cell border is the freeze line, on one pixel at every scroll offset (`TableRenderer#getFreezeLineOverlap`); only a band that covers every column leaves the line to the row header. Overlay traps: `3rdparty/walkontable/AGENTS.md`, "The inline-end overlay".
- **Never write an updated copy of a user's setting back into `getSettings()` (DEV-3968).** `getSettings()` returns the table meta, whose prototype is the global meta that `updateSettings()` writes, so an assignment on it is an own property that hides every later `updateSettings()` of that key (only the frozen counts drop such a shadow, see `dataMap/metaManager/AGENTS.md`). The React and Vue wrappers also compare a size prop with the LIVE setting (`COMPARED_AGAINST_LIVE_SETTINGS`), so a copy that differs from the prop makes them send the original array back on the next render. An array `colWidths` is therefore read through a column index map instead: `core/columnSizeSettings.ts` registers it while `colWidths` is an array, holding the entry index each physical column was declared at (`null` for a column inserted between others; a column appended after the last one takes the entry after the highest in use, so `minSpareCols` and writes past the last column still get the declared widths). The index mapper keeps it aligned on inserts and removals, UndoRedo snapshots it with the other maps (registering it drops the undo history, the way enabling a plugin does, so it is registered on `beforeInit` and `afterUpdateSettings`, never lazily), and the user's array is never touched, so an entry changed in place still applies to its column. A new array (a different reference) replaces the map with one registered under a new name (`colWidths.declaredIndex.<n>`), so UndoRedo, which compares map names, drops the steps recorded with the previous array's origins; undoing them read the new array through old origins. The same array passed again keeps the map and the history. Appends are spotted by the map's init function itself: while it runs, the map still has its length from before the insert, and the index it is called with is the one the column takes (`createCol()` passes the `'end'` mode, so `insert_col_end` on the last column is already shifted), so an index at or past that length takes the next unused entries when the column also ends the screen order (`endsScreenOrder()`; a column appended at the physical end after the columns were moved can sit between others on screen and takes none), and any other insert takes none. A sequence nobody reordered (`indexesSequence.isIdentity()`) skips that scan. The map is observed with `observeMapChange()` and drops the column width cache when it changes, because a restore can change the widths without changing the column count. A column outside the index mapper, and a header, keep the index they were given: the array and the function are read at that index. Only `loadData()` declares every column at its own index again (`updateData()` fits the map to the new length and keeps it), so the map keeps its values per data array and per `colWidths` array (a `WeakMap`) and puts them back once, on the next load of the same data array with as many columns, for the `colWidths` array the grid holds then: the sheets bar loads a sheet's own data array each time the sheet is shown, after it applied that sheet's settings, and without that a column inserted on a sheet lost its alignment after a round trip through another sheet, also when the sheets declare different arrays (`plugins/sheetsBar/__tests__/colWidths.unit.js`). Memory stays bounded: the origins of an array replaced while the same data stays shown wait in one slot (`#departing`), which the next replacement overwrites and the next load commits, so an app that builds a new array on each render keeps one copy, and a load drops everything kept for the data it shows, whose columns then live in the map. A data array shown earlier gets its alignment back on any `loadData()`, not only the sheets bar's, and the migration guide says so: core cannot tell a sheet switch from an app that switches arrays itself, and both want the widths on the columns inserted there. A settings update never restores them: the origins kept from an earlier visit would replace the ones the columns have now. One `updateSettings()` call that carries `data` and a new array merges the array into the settings before its data phase and fires `afterUpdateSettings` after it (the React, Vue and Angular wrappers send both keys together when both props change), so the map follows `colWidths` again at the start of every data load (`#onBeforeDataLoad`), and `getDeclaredIndex()` answers through the map only for the array it was built for. A load that writes back the origins the map already holds (a wrapper re-sends the same data on every render) skips the write, which would drop the column width cache. `#loading` is reset by a microtask as well as by `afterLoadData`, so a load that throws cannot leave it on. A duplicated sheet gets a copy of the data (`copySheetData()`), so it starts from the declared order. The lookup in `_getColWidthFromSettings()` goes through the map only for the grid-level array; a `columns[].width` and a function keep the physical index.

- **A focus scope that COVERS the grid should inherit its shortcuts, and a scope that REPLACES it must not.** A scope declaring `shortcutsContextName` switches the shortcut manager to that context, and the manager runs the active context only (`shortcuts/manager.ts`, `handleEventWithScope`) — the `scope: 'global'` path is no escape hatch, because both that context and `grid` are `table`-scoped. So an empty context kills every grid shortcut for as long as the scope is active; `emptyDataState` shipped that way and took undo, redo and select all down with it (DEV-53). An overlay that sits on top of the grid without replacing it therefore declares `fallbackShortcutsContextName: 'grid'` on `registerScope()`, and the manager walks that chain when it dispatches a key — so shortcuts added to the grid LATER work there with no change to the plugin. Listing keys in the plugin instead is what rots. A **modal** scope (`dialog`, the license lock screen) must leave it unset: letting grid shortcuts through a modal is the bug, not the feature. Three rules ride along. The chain is walked by the manager, **not** by the context: `hasShortcut()`/`getShortcuts()` stay own-only, because they are public API documented as answering for one context and `ShortcutManager#hasEventShortcut()` (which `comments` calls) depends on that. **The walk moves on only when NOTHING in the current context ran** — a shortcut whose `runOnlyIf` returned `true` stops it, whether or not its callback did anything, and a shortcut that is registered but declines does not shadow the fallback's answer for the same key. That distinction is the whole difference between overriding one key and silently killing it. And **inheriting is only safe because the grid's own guards are correct** — see the next bullet.
- **A shortcut that reads or writes cell CONTENT must call `canAccessCellContent(hot)`** (`shortcuts/guards.ts`), and it lives there rather than in `shortcuts/contexts/grid.ts` because `mergeCells` (`Ctrl`+`M`, which clears every cell of an un-merged range) and `checkboxRenderer` (space, enter, delete, backspace) register destructive shortcuts into the **same** grid context from their own files. It is **two** questions, and both were measured on DEV-2917. *Are cells drawn* — `countRenderedRows() > 0 && countRenderedCols() > 0`, exported as `hasRenderedCells()`; with every column hidden `Delete` blanked all 40 cells of the test grid. `countRenderedCols()` is a faithful proxy, reporting 0 with every column hidden even when `fixedColumnsStart` is set (the frozen clone has nothing to clone), and -1 before the first draw, so it fails closed. And *is something covering them* — `FocusScopeManager#isGridBodyCovered()`, true while any **enabled** scope declares `coversGridBody` (asked of every scope, not just the active one: an overlay is on screen whether or not it holds the keyboard). That second half is not theoretical: `emptyDataState` shows its overlay over a **fully rendered** grid while a DataProvider fetch is in flight — its own `#toggleEmptyDataState()` comment says so — and the drawing check alone answered `yes` there, so `Delete` wiped the data under the overlay. `Core#getFocusScopeManager()` throws on a non-root instance, so the covering check sits behind `isRootInstance()`. **Two write paths are outside this guard by construction and no shortcut guard can reach them**: `copyPaste` binds native `paste`/`cut` DOM listeners, and anything the host calls through the API. The `Core` methods keep guarding on the DATA counts, so `emptySelectedCells()` through the API still clears hidden columns — only the keystroke is gated. One gap deliberately left: the license lock screen declares neither `coversGridBody` nor an activated scope, so keyboard editing still works behind the lock. **`Tab` and every selection-moving shortcut take `canNavigateGrid()`** — `navigableHeaders` OR drawn cells, because moving a selection into a visible header is legitimate where writing to a hidden cell is not. Under a covering overlay it allows **moves between headers only**: the overlay covers the cells, not the headers above it. Blocking headers too broke 20 empty-data-state visual screenshots — those tests Tab from the corner to a column header and open its filter menu with `Alt`+`Shift`+`ArrowDown`, so the filter was never applied and the overlay showed "No data available" instead of the filter message. Moves among covered cells stay blocked, or `Tab` walks an invisible selection through the cells under the loading overlay instead of letting the user leave. **That last rule needs a second half, because `canNavigateGrid()` is an ENTRY check and only knows where the selection is, not where a key would take it.** Allowing a move to start from a header also allowed it to END on a covered cell: measured on DEV-2917, `ArrowDown` from column header `[-1, 2]` landed on `[0, 2]` under the loading overlay, and the user was then stranded, since the entry check fails for a non-header highlight so no arrow could bring the selection back. `keepCoveredCellsUnselectable()` (same file) wraps the whole grid commands pool and puts the selection back when a command moves it off the headers while the body is covered. It wraps the pool rather than the 17 movement commands one by one, and it keys off the selection rather than a command-name list, because importing the command factories into `guards.ts` would close an import cycle — `moveCellSelection/inlineEnd.ts` already imports `hasRenderedCells` from it. `Tab` answers the same question in its own `after()` by deselecting, which is right for a key that means "leave"; an arrow means "move", so this reverts instead.
- **The `GRID_TAB_NAVIGATION_GROUP` pair is bookkeeping and must stay UNGUARDED.** `before()` sets state that `after()` clears, and every guard worth having here can change its answer *during* the keystroke — the Tab move itself drops the selection. Guarding the pair therefore runs one half and skips the other, leaving `tabNavigation`'s `isTabOrShiftTabPressed` set so its `afterSelection` hook forces `preventScrolling` on a later, unrelated selection. The thing that actually needed gating is the `event.preventDefault()` inside `after()`, which claims the chord whenever the selection is still in range — unguarded, an overlay inheriting these shortcuts swallowed `Tab` and trapped the user. It is gated there, as `!canNavigateGrid(hot)` joining the existing deselect branch. Note there are **two** such pairs in the same context and group: this one and a second in `focusManager/scopes/grid.ts`. Both are bookkeeping; neither takes a guard.
- **Deactivating a focus scope rolls the shortcuts context back ONLY when the caller asks explicitly.** `deactivateScope(scopeId)` means "I am done, take the keyboard back" and restores what the scope displaced; a deactivation driven by a focus event means only "the user is elsewhere now" and leaves the context alone. The asymmetry is not tidiness — `sheetsBar` registers its scope with `runOnlyIf: () => !menus.isOpened()` so that the bar stands aside while its own menu is open, and a rollback on that path hands the keyboard to the grid and kills every command in the menu (it reddened all six Playwright legs). Two consequences follow. The implicit path **keeps** the displaced name rather than clearing it, because a context menu deactivates a scope before the plugin's own `#hide()` ever runs, and that explicit call must still find something to restore — so the explicit path restores even when the scope is no longer the active one (`restoreDisplacedShortcutsContext()` is still a no-op while ANOTHER scope is active, or once the context has moved off the scope's own — two scopes may share a context name, so the name alone never proves which one holds the keyboard). And a scope **never records its own context as displaced**: after standing aside it reads its own name back on re-activation, and recording that would make the later rollback a no-op that pins the plugin's context forever.
- **A Tab-source activation of the scope that is already active is a RE-ENTRY, not a repeat, so `activateScope()` must run it.** The focus catchers are disarmed (`tabIndex = -1`) while the focus is inside the active scope, and the Tab keydown that leaves the last cell runs `updateScopesFocusVisibilityState()` while the focus is still on the cell, so they stay disarmed. A Tab from the browser UI sends no keydown into the page. The catcher therefore takes the focus only once the focus has fallen to `body` and an in-page Tab has run, which re-arms them (the E2E spec builds that state with `blur()`). No `focusin` lands in the page meanwhile, so `processScopes()` never deactivates the scope and the grid stays `isListening()`. Without the re-run the catcher took the focus, no cell was selected and the next Tab left again, so a keyboard user could not get back in (DEV-3354). A Tab source on the active scope is not proof of that history: the notification region hands the focus on to the grid with `activateScope(GRID_SCOPE, TAB_FROM_ABOVE)`, which now re-selects the remembered cell too, and a custom scope's `onActivate` must be safe to run twice. `click` and `unknown` keep the early return, because those repeat on every interaction inside the scope. Do not widen the re-run to them, and do not deactivate the active scope first. The re-entry also leaves the shortcuts context and the displaced name alone, so an editor left open keeps Enter and Escape. The grid re-enters on the cell it remembers (`getTabReentryCoords()` in `focusManager/tabReentry.ts`, set by the grid focus scope and dropped on `afterLoadData`; a module-level `WeakMap`, so it stays off the public `getFocusManager()` type), not on its first cell. Pinned by `focusManager/__tests__/scopeManager.unit.ts` and `tests/e2e/focus-reentry-after-leaving-page.spec.ts`.
- **A group's options do NOT compose with a shortcut's own — they are skipped for any key the shortcut already declares.** `Context#addShortcuts(shortcuts, options)` copies each option onto a shortcut only `if (hasOwnProperty(shortcut, key) === false)`. So a shortcut carrying its own `runOnlyIf` silently opts OUT of the group's guard rather than being ANDed with it. That is how `Ctrl`+`Enter` bypassed the `GRID_GROUP` rendered-cells check while every neighbouring arrow key honoured it — the group guard reads like a floor and is not one. When a group-wide invariant must hold, put it inside each overriding shortcut's own `runOnlyIf` too, and verify by pressing the key rather than by reading the group options.
- **`adjustRowsAndCols()` only ever GROWS the grid; a lowered minimum is given back by `grid.removeSurplusRowsAndCols()`, which `updateSettings` runs just before it (DEV-2206).** Four rules, each with a measured defect behind it. (1) It removes **only** the rows and columns those four options appended: `DataMap` keeps a count of the trailing run each axis ends with (`#trailingFillerRows`, `#trailingFillerColumns`, read through `isTrailingFillerRow()`/`isTrailingFillerColumn()`), raised only by a create carrying `fillsMinimumSize: true` and reset by any insert that lands after the run. **Do not key this on `source === 'auto'`** — `applyChanges()` creates rows and columns with that source for any write past the last one, so a paste's rows would be given back as if an option had added them. A count rather than a set of row objects, because those options always APPEND: the rows they add are the physically last ones, a sort or a move reorders the visual space only, and a count needs no read of `dataSource` (which NestedRows remaps). A new `DataMap` — every `loadData`/`updateData` — starts at zero, and no `data`-in-the-same-call guard is needed, but not because nothing was created yet: the data phase runs `adjustRowsAndCols()` against the already-merged settings, so the new axis is sized to the new values before the removal runs and its surplus comes out 0. NestedRows' hand-built top-level inserts bypass the count, so there a lowering can take the user's new empty row instead of a filler (the count and the data stay right) — a known limit, recorded in `src/plugins/nestedRows/AGENTS.md`. (2) It removes down to what the new values require and no further (`countSurplusTrailingItems`, `core/minimumSizes.ts`): the surplus is `count - max(minimum, filled + spare)`, which can never exceed the empty items at the end, so a row holding data is unreachable. Do **not** also cap it by how much the value was lowered — with the filler gate in (1) that cap can never change the answer, and it under-removes on a grid whose earlier lowering was blocked. (3) **The removal is an ordinary one and the cell meta follows it.** An earlier version skipped `metaManager.removeRow`/`removeColumn` for the `auto` source, to mirror the create — and that silently LOST meta: the rows taken are the last ones on SCREEN, so after a sort a surviving row can sit physically after them, and its meta was left behind at an index the removal had renumbered (comments, `readOnly`, `className`, invalid flags, CustomBorders, MergeCells anchors, all of them). Shifting it also keeps `alter(…, 'auto')` behaving as it always did for callers. The cost is the mirror image, and it is the right trade: out-of-range meta shifts on a lowering but not on a raise. It is still **not** `alter()` — that lowers `fixedRowsBottom` and splices `colHeaders`, and the creation this reverses did neither. (4) The selection is repaired with `Selection#refresh()`, which clamps, not `shiftRows()`/`shiftColumns()`, which move a layer by the removed amount — right in the middle, wrong at the end — and only when a layer reached the removed part, because `refresh()` re-fires the selection hooks. It runs under the `shift` selection source, the one `alter()`'s removals use, because `refresh()` otherwise marks `refresh`, which is not in `afterSetRangeEnd`'s no-scroll list — a plain `updateSettings()` call would then scroll the viewport (and a window-scrolled page) to the clamped selection. An editor open on a removed row or column is closed without saving, but only once the removal has actually happened: a `beforeRemoveRow` veto would otherwise throw away what the user is typing into a row that then stays. **Deliberate limit:** while `maxRows`/`maxCols` hides part of an axis, that axis is left alone — the removal cannot address a capped row, so acting on the capped count took one out of the MIDDLE of the data set. A **trimming** map (Filters, TrimRows, a NestedRows collapse) is deliberately NOT skipped: the requirement is read from the visible rows, exactly the way `adjustRowsAndCols()` reads it when it fills, so a lowering gives back the visible surplus and a filler the trim hides stays. Measured both ways — with data rows trimmed the result equals a grid built with the lower value, and the grow side has always done the mirror image (with rows trimmed, `minRows` grows the source past the value and an untrim keeps the extra rows, with no `updateSettings()` involved). Neither side runs again when the trim changes; that is the known limit. Pagination hides rather than trims, so it does not change the count at all. Two rules about *when* it may read the grid at all. **Nothing is counted until the lowered check has passed**, the way `adjustRowsAndCols()` reads `minRows` before it reads `countRows()`: `updateSettings()` also runs from a plugin's `enablePlugin()`, and plugins are enabled BEFORE the first data load, so `datamap` is still undefined there and any count throws — `multiColumnSorting` turning itself off next to `columnSorting` is the in-tree caller that does it. And **`Infinity` is a real value, not a broken one**: `createRow`/`createCol` stop at `maxRows`/`maxCols`, so `minRows: Infinity` with a cap set is a working grid that fills to the cap, and `toSize()` therefore keeps it rather than folding it to `0` — folding it made a later finite value look like a raise and skipped the removal. Pinned by `src/__tests__/core/minimumSizesDecrease.unit.js` and the four `src/__tests__/settings/min*.spec.js` decrease specs.
- **A row can be longer than the grid, and a column created at the end is a block insert at the journal's index, never a push.** The grid width is `getInitialColumnCount()`: the first row's length, or the length of `dataSchema` or `columns` when one is set. `DataMap#createCol` takes the physical end from `columnIndexMapper.getNumberOfIndexes()`, not from `countSourceCols()`, which is only the first row's length. It inserts every new `null` of a create as one block at `firstNewPhysicalColumnIndex` in every row (`#insertColumnsIntoDataSource`), and a row shorter than that index gets them at its end. A longer row keeps its values in order, with the nulls in front of the values past the grid width, and the grid does not widen (DEV-485). The undo journal records `insertColumns` at that same physical index and replays it with `alter()` by index, so the data and the journal must agree. An earlier rule pushed the first column to the end of the row and spliced the rest at a fixed position, which put a `null` in the middle of a longer row with `minSpareCols`, and made undo remove real values. Pushing every column to the row end is not the fix either, because undo would then remove the values at the journal's index (a `trimRows` longer row lost two values). A value past the grid width stays out of a column added at the end, so a user who relied on it showing in the new column sees an empty one. Known limit: a row shorter than the insertion point is padded with `null` values and the journal does not record its length, so undo leaves the padding. No value is lost. - **Every mutator runs inside an operation, or undo records it wrong.** The core entry points (`setDataAtCell`, `alter`, `setCellMeta`, `batch`, `batchExecution`, `spliceCellsMeta`, ...) open one through `operationScope` (`src/core/operationScope.ts`), and plugins wrap each public mutator in `this.runOperation(name, fn)`. The outermost operation is one undo step; nested ones join it. A new mutator that writes data, cell meta or an index map outside an operation turns each inner call into a step of its own, and a write that must not become a step runs under `operationScope.suppress()`. An asynchronous continuation keeps the recording context of the call that started it through `operationScope.hold()` (a validator's answer, NestedRows' deferred re-collapse). The rules, the journal and the restore order: `src/plugins/undoRedo/AGENTS.md`.
- **A write to a row that does not exist yet is keyed by the physical index the row WILL take, not by its visual one (DEV-155).** A write past the last row is validated BEFORE `applyChanges()` creates the row, and the meta it reads and writes needs some physical row. A created row is appended after the last SOURCE record (`rowIndexMapper.getNumberOfIndexes() + k`), and `metaManager.createRow(null, n)` leaves meta stored beyond the dataset where it is. With a trimming map the source holds more records than the grid shows, so the old `physical = visual` guess wrote the validation result, and fed `populateFromArray()`'s `readOnly`/`skipRowOnPaste` reads and the `valueSetter` read, from a trimmed or unrelated record. `getCellMetaOfChange()` in `core.ts` resolves it for those three write-path reads, and `validateChanges()` drops the `valid` flag of a validated row that was never created (`maxRows` clamp, `allowInsertRow: false`), or a row appended later would inherit a mark nothing validated. **Do not move the resolution into `Core#getCellMeta`, `getCellMetaTransient` or `setCellMeta`.** A row index past the last visual row is also how a caller names a TRIMMED record by its physical index (ColumnSummary's `isLockedSummaryCell` relies on it, pinned by `columnSummary/__tests__/readOnlyLock.unit.js`), so the public fallback cannot tell a pending row from a trimmed record. The cost: a `beforeValidate`/`afterValidate` listener that calls `hot.getCellMeta(row, col)` for a created row still gets the trimmed record, not the object the validator wrote to - use `this` in the validator. Both counts come from the index mapper, so a long paste stays O(1) per cell (`countSourceRows()` walks the tree under NestedRows). The column axis is not covered: `toPhysicalColumn()` still falls back to the visual index. Pinned by `src/__tests__/core/validateChangesTrimmedRows.unit.js` and `tests/e2e/paste-validation-trim-rows.spec.ts`.
- **`Core#_applySettingsAndData(settings, data, source)` is the one private path that replaces settings and data together, and it runs them in three phases.** Configure (settings merged, plugins enable or update while `_isDataWorkDeferred()` answers `true`, and `applySettings()` skips the data phase, the late `columns` pass, the `cell` option, `afterCellMetaReset`, the `min*` sizing and the render), load (`applyLoadData()` with the new configuration in force), data ready (the held-back meta phase, then the source-data validators once, then each enabled plugin's `onDataReady()` in priority order, then one render, with rendering suspended for the whole call). The deferral is an explicit `defersDataWork` argument of `applySettings()`, which then returns a closure over its meta phase (`applyMetaPhase()`) instead of running it, plus a closure `dataWorkPhase` (`'configure'`, `'data'`, `'meta'` while the held meta phases run, or `null`) saved and restored around every call, never a boolean reset to `false`. `_isHeldMetaPhaseRunning()` answers for `'meta'` only, so a plugin that skips work the load already did (Formulas' resync) skips it for the call's own meta phase and not for a full `updateSettings()` a listener makes later in the call, which runs with the step set back to `'data'`. An update made in the configure step that carries `data` warns, because the call's load replaces it. The optional `cellOptionMetas` argument puts `cell`-option meta back by physical index in place of applying `settings.cell` by its coordinates, which a reordering or trimming map of the new settings changes during the load; `settings.cell` is still stored as given. The optional `keptCellMetas` argument puts back the meta set through `setCellMeta()` and the invalid marks, by physical index, before the `cell` option (a restated `cell` entry wins) and before `afterCellMetaReset`; entries past the loaded data or on a `min*` filler row or column are dropped. Details in `src/plugins/sheetsBar/AGENTS.md`. A public `updateSettings()` made in the configure step (ColumnSorting's `enablePlugin()` does on a sorting-plugin conflict) is deferred the same way, and its meta closure is queued (`heldMetaPhases`) and run after the outer one: applied in full it padded the departing rows to the arriving `min*` values, and one shared slot let it overwrite the outer meta phase. An update made later (an `afterLoadData` listener) applies in full. Three traps: the first-run source validators are skipped in phase 1 too, because a grid being built has no data map until the load (core's own init pass runs them); `replaceData()` skips its own validator run while `_isDataWorkDeferred()` answers `true`, because a `columns` function reaches the column meta only in the meta phase, and validating in the load blanked arriving values under the departing sheet's rules (for the same reason a `columns` value the early pass cannot apply, `null` or a function, resets the column meta BEFORE the load on this path, or the load validates and renders the arriving data with the departing columns' types); and the phase is restored in a `finally`, so a listener that throws cannot leave later updates deferred (a listener that destroys the grid in the configure step, `afterUpdateSettings` included, ends the call there: no load, no meta phase, and the `finally` resumes no render on the destroyed instance), while every plugin drops the work it recorded for the `onDataReady()` pass (`BasePlugin#dropDeferredDataWork()`), so that work cannot run on a later call against other data. `_isDataLoadPending()` answers `true` only in the configure step: work that needs the load itself (NestedRows, Formulas binding a sheet, MergeCells' pass) asks it, because `_isDataWorkDeferred()` stays `true` after the load and an enable from an `afterLoadData` listener then waited for a load that had already run. A grid still being built (`firstRun`) skips the call's validator run, because core's own init pass runs them. `_replaceInitPassSettings()` (callable from `beforeInit` only) lets a caller that applied settings there replace the hook callbacks and `cell` entries that init pass applies, so they are applied once by the pass instead of being undone by it and re-applied through `updateSettings()`. (2) A pure append or a pure truncation keeps the state, `isColumnLayoutKept()` in `core/columnLayout.ts`: the columns that remain hold their places, and `updateData()` has already fitted the mappers (a dropped trailing column takes its own state along, and a sort on it is not cleared). A removed `<HotColumn>` at the end must not wipe the other columns. Only the `columns` path tolerates it, because the strict `dataSchema` comparison is pinned by `tests/e2e/data-schema-update.spec.ts`. (3) `colToPropCache` is **sparse** under `columns` (a column without `data` leaves a hole), so both comparisons walk by index: `Array#every` skips holes and read a column that gained a property as unchanged. On rows that are arrays a hole reads the source column at its own index, so the `columns` path names it by that index (`readColumnLayout(…, fillIndexHoles)`): `[{ data: 0 }]` and `[{}]` are one layout. (4) A column without a `data` key has only an index, so a same-count reorder of such columns stays undetectable; that is a known limit, not a bug to chase. (5) The **function** form of `columns` is not compared (`isColumnsPayloadWithData()`, and the `dataSchema` leg of `readSettingsBaseline()` skips a payload whose `columns` is a function, so `{ data, dataSchema, columns: fn }` keeps the state as before): counting its columns calls the user's function once per source column, the same cost the two-pass bullet above keeps out of the early pass, and a wrapper writing it inline would pay it twice on every render. A function-form grid keeps the old behavior, state by physical index. (6) The previous count is read capped by the column mapper's length (`readColumnLayout(true)`): the React wrapper keeps `columns` as one mutable array (`context.columnsSettings`) and appends a `<HotColumn>` to it before it calls `updateSettings()`, so the grid already counts the new column while its mappers and property cache do not, and an uncapped read saw a hole at the new index and reset on every append. The cap is safe because the mappers are only ever longer than the layout (`minCols`/`minSpareCols` append columns), never shorter. Do not use the mapper length as the count itself: with `minSpareCols` it would exceed the new count on an unchanged layout. Angular forwards `data` with every `settings` change too (`ALWAYS_FORWARDED_SETTINGS` in `hot-table.component.ts`), so it takes this path as React does; Vue deletes `data` from the payload only while the array is the same reference as the last one it passed, and column modification is allowed or the source column count is unchanged (`wrappers/vue3/src/HotTable.vue`), so it sends `{ data, columns }` for a new array and in the other case. Pinned by `src/__tests__/core/columnsLayoutIndexState.unit.js`, `tests/e2e/columns-layout-update.spec.ts`, `wrappers/react-wrapper/test/columnsLayoutState.spec.tsx` and the Angular `hot-table-columns-layout-state.spec.ts`. Not covered, deliberately: the `hasExternalDataSource` branch reacts to `columns` only. Pinned by `tests/e2e/data-schema-update.spec.ts` and `src/core/__tests__/columnLayout.unit.ts`.

- **Cell `className` is `string | string[]` — never cast it to `string`, and never push into the value you were handed.** The union is declared on `CellMeta` (`src/settings.ts`) and documented with an array example in `metaSchema.ts`; `addClass()` accepts both forms. - **Build internal UI as a `TemplateSpec`, never as an HTML string, and clear elements with `empty()` or `replaceChildren()` — never `innerHTML = ''`.** Every HTML and XML parse entry point is a Trusted Types sink (`innerHTML`, `insertAdjacentHTML`, `DOMParser.parseFromString` for `text/html`, `application/xhtml+xml` *and* `text/xml`, `Document.parseHTMLUnsafe`, `Element.setHTMLUnsafe`, `Range.createContextualFragment`, `document.write`), so under a CSP carrying `require-trusted-types-for 'script'` a plain string is rejected and the grid dies where it writes. `createElement` / `textContent` / `setAttribute` are untouched, which is why `buildTemplate()` (`helpers/dom/template.ts`) exists and why the `html` tagged template it replaced is gone — only `toSingleLine` remains in `helpers/templateLiteralTag.ts`. Three consequences. (1) `innerHTML = ''` throws exactly like markup: an empty string is still a sink assignment, so clear through `empty()` (`helpers/dom/element.ts`) for the small child counts the grid actually clears, or `replaceChildren()` above roughly thirty children, where `empty()` measures slower. (2) An `<svg>` needs `ns: SVG_NS` on its root spec — built through `createElement` without a namespace it is an unknown HTML element and renders nothing, silently. Descendants inherit it. (3) Handsontable ships **no** Trusted Types policy and requires no entry in the application's `trusted-types` directive. Two sinks survive, and both are the user's own content. The user's own data through `fastInnerHTML` and the clipboard parse is the user's `sanitizer` to police - note `HTML_CHARACTERS` sends only content shaped like markup down the `innerHTML` path: a tag, a markup declaration or processing instruction, or a named or numeric character reference. Prose reading `Smith & Sons, Ltd.; est. 1920` takes the `textContent` path and needs no policy, so a header reaches the sink only when the user asked for it to be rendered as HTML. The second is the built-in `textExtractor` extraction (`utils/textExtractor.ts`), which is user content under the same gate: it tests the same `HTML_CHARACTERS` predicate on the same header content, runs the user's `sanitizer` first and only then parses the result in a `<template>`, and it is unreachable unless the user opts in with `textExtractor: true`. There is no third: **no markup Handsontable authors itself reaches a sink**. The last one that did was the context menu's check mark, which `markLabelAsSelected()` (`utils/menu/utils.ts`) and `markSelected()` (`plugins/customBorders/utils.ts`) baked into a menu item's label as `<span class="selected">` for `menuItemRenderer.ts` to write through `fastInnerHTML` - so a read-only selection, or a bordered one, took the whole menu down under enforcement. - **A trimming index map can strand the selection, and the repair is a protocol, not a clamp.** A hidden row keeps its place in the visual space; a TRIMMED one leaves it, so the highlight's visual coordinate can outlive the record it addressed, and a write through it makes `applyChanges()` APPEND records (a paste and a Ctrl+Enter commit both size themselves from the selection's corners, so a range's far corner strands the same way). `core.ts` therefore keeps `Selection` supplied with the highlight's PHYSICAL coordinates, captured whenever the selection is laid — they cannot be recovered later, because `IndexMapper#updateCache()` rebuilds every cache BEFORE it fires `cacheUpdated`. Four rules ride along, and each exists because breaking it produced a measured defect. (1) **Drop, never clamp** a stranded cell selection: clamping slides the highlight onto a neighboring record and the next paste overwrites it, which is the same defect class one step quieter. The exception is a HEADER-ANCHORED extent — a full column, a full row, select-all — whose far corner tracks the grid rather than naming records; that is clamped, and the anchor must be judged PER AXIS (a full-row selection is anchored in the row header, yet its row index still names one record). `isEntireColumnSelected()` cannot answer this: it compares the range height against the current row count, which the trim has already changed. **The same extent must GROW on an untrim** (a NestedRows expand, `untrimRows()`, `untrimAll()`; a cleared FILTER does not count, because `Filters#filter()` re-selects a single cell afterwards): every corner is still in range then, so the stranded test never fires, and before DEV-152 a full-column selection kept its pre-expand height and silently stopped being a whole column. `Selection#fitGridTrackingExtents()` re-pins the far corner of each layer `#spansWholeAxis()` accepted at `beforeCacheUpdate` (the `…ExtentSpansGrid` flag AND full coverage of the pre-update axis — the same rule the editor-open restore uses), so a column the user shrank with `Shift+Up` and a drag range that merely reached the last row do not grow. The coverage is measured only for an update that changes the trimmed indexes; any other update pushes a shared empty set. Five rules ride along. (a) It commits the way the shrink side does: through `refresh()` under the `shift` source, so `afterSelection`/`afterSelectionEnd` fire for the grow as for the shrink (a listener that keeps state per selection reads the grown range there; Enter and Tab build their merged-cell focus order from the live ranges on every press, `Selection#transformFocus`), the viewport stays put and the editor stays closed. With an editor open it commits directly instead, like the editor-open restore. (b) It is POSTPONED in two windows and applied when the last closes: an `alter()` scope (`resumeShifts()` applies it after the held shifts, so a consumer that untrims from `afterRemoveRow` still ends with a whole column — `alter()` alone only shifts), and a data replacement (`Core` wraps `replaceData()` in `suspendGridTrackingFits()`/`resumeGridTrackingFits()`, because `replaceData()` destroys the `DataMap` before `beforeUpdateData`, and a NestedRows untrim there committed highlights through it: `Cannot read properties of null (reading 'rowIndexMapper')`). A throwing replacement or `alter()` drops the postponed grows, and so does `deselect()`. `Core#destroy()` suspends the grow for good before its teardown: unregistering the trimming maps untrims, and a grow there ran the selection hooks against the already destroyed `EditorManager` (`Cannot read properties of null (reading 'getAtCell')`). (c) NestedRows holds the grow for its whole stash window (`collapsedRowsStash.stash()` → `applyStash()`), because its expand is transient and a removal re-collapses a tick AFTER the `alter()` scope has closed; growing onto that height painted highlights past the rows the re-collapse took away (`TR was expected to be rendered but is not`). See `src/plugins/nestedRows/AGENTS.md`. (d) The shrink side's `refresh()` in `deselectIfHighlightStranded()` runs under `shift` too when no caller named a source, for the same scroll reason: a trim or a collapse under a full-column selection jumped a scrolled grid to the top. A `shift` re-lay renders once, on the last layer (`afterSetRangeEnd` in `core.ts`), not once per layer. (e) The grow's snapshot is layer-keyed, so the editor-open restore re-indexes it with `#remapLayerSet()` like the other layer sets; and with an editor open, an untrim batched with a sort (which the restore refuses) is grown by the editor-open branch of `repairSelection()`. Pinned by the `grows …` / `does not grow …` / `does not scroll …` / `renders a clamp …` / `Enter walks …` cases in `tests/e2e/selection-trimmed-row.spec.ts`, the grid-tracking cases in `tests/e2e/editor-trimmed-row.spec.ts`, the add-child and removal cases in `tests/e2e/nested-rows-collapse-selection.spec.ts`, and the `updateData()` case in `tests/e2e/nested-rows-update-data.spec.ts`. (2) **Re-read the record on every path that KEEPS the selection**, including the editor-open exit — a tolerated trim still moves the record under the highlight, and a stale capture inverts the next verdict. (3) **Discriminate the change**: a structural insert/remove and a permutation (sort, move) both raise `trimmedIndexesChanged` exactly as a filter does, and both invalidate the capture rather than stranding the selection, so both re-read it instead of dropping — the physical index COUNT is what separates structural from the rest. A permutation must re-read and FALL THROUGH, because one `batch()` can carry it and a trim together. (4) **An editor that was open when the trim landed is sampled BEFORE the public hooks** (`EditorManager` discards a stranded editor inside them) and narrows the repair to coordinates that address nothing, because `EditorManager` deliberately keeps a still-addressable selection so the user can carry on typing. Known gaps, deliberately open: a trim ABOVE the highlight that leaves the coordinate in range, and a stranded corner in a non-active layer. `Selection#deselectIfHighlightStranded()` holds the rule; `tests/e2e/selection-trimmed-row.spec.ts` pins every case above except rule (4)'s two editor-open cases, which `tests/e2e/editor-trimmed-row.spec.ts` pins. **All four rules and both gaps describe the NO-EDITOR case only.** With an editor open the selection is not repaired by that test at all — it is REBASED: `core.ts` calls `Selection#capturePhysicalSelection()` from the mapper's `beforeCacheUpdate` and `restorePhysicalSelection()` from `cacheUpdated`, which puts every layer back on its surviving records, shrinks a partially trimmed range onto them rather than dropping it, and drops a non-active layer that lost its focus. Six rules ride along with THAT half, and each of them has a measured defect behind it. (1) An active layer that lost every record falls back to the same in-range test rule (1) above uses: it parks on its focus's pre-update slot when the trim left that slot in range (the editor is discarded, and the next keystroke re-prepares against the record now there), and the whole selection is cleared when the slot addresses nothing — never clamped inward onto a record the trim merely slid into view, and never replaced by promoting a bystander layer into the active slot. (2) A **trimming map does not only remove records**: `trimmedIndexesChanged` is raised by any trimming-map write, so clearing a filter or `untrimRow()` arrives here too, and a record it REVEALS between two corners lands inside the rectangle they describe. A `CellRange` cannot exclude it, so `#coversForeignRecords()` collapses the active layer onto its focus and drops a bystander, rather than letting `Ctrl+Enter` fill a row the user never selected. (3) Whether an extent **tracks the grid** (re-pin to the axis boundaries) or **names records** (shrink onto survivors) takes BOTH the layer's `…ExtentSpansGrid` flag and full coverage measured at capture time: the flag alone is sticky and survives a `Shift+Up` that shrunk the range, and the geometry alone re-pins a drag-selected range that merely reached both ends. Do **not** reach for `selectedByRowHeader` / `selectedByColumnHeader` here — they say whether a header should be highlighted, and `selectAll()` writes them only when a header is rendered. (4) The restore **re-indexes** the layers it keeps, so every layer-keyed set goes through `#remapLayerSet()` — the two header sets and the two extent sets — or a survivor inherits a dropped layer's flags. (5) A snapshot is a **stack per axis**, because `updateCache()` nests (see `.ai/INDEX-MAPPING.md`): one slot let an inner update's capture overwrite the outer's and its `afterCacheUpdate` discard clear it, leaving the outer restore a silent no-op. (6) A restore that drops the whole selection **owes an `afterDeselect`** and must not send it itself: `Core` answers that hook with `EditorManager#closeEditor()`, which SAVES, and the restore runs before the public cache-update hooks — so the debt is tagged with its axis and paid by `notifyDeferredDeselect()` after them, where the stranded editor is already discarded. A layer anchored in a header never reaches any of this: a header sentinel has no physical index, `#hasResolvedPhysicalRange()` rejects it, and the no-editor clamp above handles it instead. A pure trim is also the only shape accepted at all — a permutation can scatter one rectangle's records. That is what makes a `DropdownEditor` commit and a `Ctrl+Enter` fill (both of which read the selection, not the editor's own coordinates) land on the record the user typed into. Two consequences for anything that touches it. The physical capture is gated on `isEditorOpened()`, so the two policies never both run, and moving that gate hands trim repair to whichever of them the flags happen to select. The grid-tracking coverage `capturePhysicalSelection()` records BEFORE that gate is not part of the restore policy: it feeds the no-editor grow, so it is taken on every trimming update, editor or not — do not move it behind the gate. And the restore RE-INDEXES the layers it keeps, so every piece of layer-keyed state has to go through `#remapLayerSet()` — the two header-selection sets and the two `…ExtentSpansGrid` sets — or a surviving layer inherits a dropped one's flags and the clamp above fires on the wrong layer. A pure trim is the only shape the restore accepts: a permutation can scatter one rectangle's records, which `CellRange` cannot describe. `tests/e2e/editor-trimmed-row.spec.ts` pins the editor-open half.
- **A structural change repairs the selection LAST, so a nested `alter()` must compose with it — in the order the DATA CHANGES landed, not the order the calls nested.** `alter()` renumbers the index space in `datamap.removeRow()`/`createRow()` and only then calls `selection.shiftRows()`/`shiftColumns()`. Every hook the renumbering fires runs inside that window, on a selection that is stale for the change already made. An `alter()` fired from one of them used to repair that selection immediately, and its CLAMP back into the shortened grid did the outer call's job; the outer shift then applied on top and an open editor committed one record above the one it was typed into (DEV-2755). The clamp is not the thing to remove — it is what makes the ordinary "remove the selected last row" case work, where the selection really is out of range. `alter()` therefore wraps its run in `Selection#suspendShifts()`/`resumeShifts()`, and `shiftRows()`/`shiftColumns()` hold a shift back while an ENCLOSING scope owes a repair; the outermost scope folds them and clamps ONCE. `tests/e2e/editor-trimmed-row.spec.ts` pins every rule below, including a control where BOTH shifts are real and both must still apply. The second rule is the one that is easy to get wrong.
  - **(1) The scope closes on every exit**, `alter()`'s own early returns and a throwing hook included, which is why the action lives in `grid.runAlter()` and runs through `runInShiftScope()` (`core.ts`) behind a `try`/`finally` — a scope left open stops the selection repairing at all. On a throw the outermost close DROPS the held shifts (`resumeShifts(false)`) instead of writing them: writing runs `afterSelection`/`afterSelectionEnd`, and a consumer that throws there would replace the error already on its way out.
  - **(2) Order by when each change LANDED, not by nesting depth or by scope-open order.** A nested call fired from a `before*` hook (`beforeAlter`, `beforeCreateRow`, `beforeRemoveRow`) makes its change BEFORE the enclosing call makes its own, while one fired from an `after*` hook or a cache update makes it after — so depth does not imply order in either direction. `Selection#markStructuralIndexChange()`, called from the index mapper's `cacheUpdated` handler in `core.ts` *before* the public hook, stamps the open scope at the moment its change lands, and again for each group of a multi-group removal. **The stamp must come from a change the scope OWNS — timing cannot decide it.** The handler also fires for count changes no `alter()` makes (the spare rows and columns `adjustRowsAndCols()` appends, and the rows `applyChanges()` creates for a write past the last one), and a `before*` hook runs inside the same `datamap` call as the enclosing change, so such an append can land on either side of it. Stamped from after the landing, it sorted the outer shift behind a nested one that landed later; stamped from a `before*` hook, it made the outer scope look landed, so a nested call there was held and folded after it. Both paths therefore run in a scope that does not own its changes (`runInShiftScope(action, false)` in `core.ts`, `ownsIndexChange: false`), which is never stamped and never holds anything; an `alter()` fired inside one opens its own scope as usual. A scope that never changes anything (an amount-0 `alter()`) is stamped when it asks for its shift instead.
  - **(3) Nothing is held while the enclosing scope has not changed data yet**, so `before*` nesting behaves exactly as it did before the scopes existed.
  - **(4) Every flush takes and clears BOTH axes before writing either** — the outermost close, `flushHeldShifts()`, and the immediate path of `shiftRows()`/`shiftColumns()` alike. `setRangeEnd()` runs `afterSelectionEnd`, and a consumer that throws would otherwise strand the other axis for the next `alter()`; and the write lays a new selection, which drops whatever is still held (rule 5), so a column shift held behind the outer row shift would be lost.
  - **(5) A held shift belongs to the selection it was recorded for.** `setRangeStart()` drops every held shift, so a `selectCell()` made from a hook while one is held is not moved by it. The shifts' own writes are safe only because rule (4) empties the queues first.
  - **(6) Two repairs are not shifts.** An EMPTY flush is a no-op: the corner branch of `#applyRowShifts()`/`#applyColumnShifts()` re-selects the whole grid and fires the selection hooks whether or not anything moved, so without the guard every `alter()` after a select-all fired `afterSelectionEnd` twice more. And the two ContextMenu sources (`ContextMenu.removeRow`, `ContextMenu.removeColumn`) repair by `refresh()`, which clamps against the grid every nested removal has already shortened, so they call `Selection#flushHeldShifts()` BEFORE it — a held shift written after the refresh moved the selection one record past the clamp.
  - **Still open.** A ContextMenu removal nested inside another `alter()` whose change already landed keeps its shifts held, and its `refresh()` then drops them (rule 5). The count changes NestedRows makes through `rowIndexMapper.insertIndexes()` directly (`nestedRows/data/dataManager.ts`), and a data load's `fitToLength()`, run in no scope, so one made from a `before*` hook still stamps the enclosing scope. Inside `batch()` an amount-0 nested `alter()` loses the selection — `develop` does the same. A nested removal at the edited row closes the editor, because it reads the highlight before the outer shift has moved it — also as on `develop`.
- **`grid.runAlter()` ends with a FULL render, and a hook that renders inside `alter()` is why.** `afterCreateCol` and `afterRemoveCol` fire before `alter()` splices the array `colHeaders` (and rewrites the fixed counts), and the index mapper's cache update has already raised `forceFullRender`. A `hot.render()` from such a hook consumes that flag and paints the headers from the half-written array, and the closing render, left a fast draw, kept that paint: every label sat over another column, so a header click selected a column the label did not name. The same render rebuilds the column width cache from the half-updated column state, and `PositionCache#isCurrent()` only compares the item count, so the offsets stay stale too (`getFirstFullyVisibleColumn()` at the end of the scroll range is off). `runAlter()` therefore sets `forceFullRender` and calls `invalidateColumnWidthCache()` in its `finally`, before the closing `view.render()`, so a hook that throws after the arrays were written leaves the next draw a full one as well. In the ordinary path the flag is already `true` and the cache already dropped there, so nothing changes; only a render made inside the call, and an `alter()` that changed no indexes or was vetoed (which now makes its next draw a full one), differ. Do not "optimize" the line away as redundant. The row axis is not affected, because `alter()` never rewrites a `rowHeaders` array. Pinned by `tests/e2e/alter-render-in-hook-headers.spec.ts`; the CustomBorders side of the same rule is in `src/plugins/customBorders/AGENTS.md`.
- **The root's inline `height`, `width`, and `overflow*` have one writer: `src/core/rootSize.ts`.** Nothing else may write those properties on `rootElement`. `overflow` is the contract Walkontable reads to pick the owner of each scroll axis: a sized height (a length, `%`, viewport units) writes both `overflow-x: clip` and `overflow-y: clip` (which a browser serializes back as `overflow: clip`); a free height (`'auto'` or unset) with a definite width writes `overflow-x: clip` only, so the root scrolls the columns and the page scrolls the rows; a free height with a free or container-driven width (`%`, viewport and container-query units, `var()`, `env()`) writes nothing, unless a root instance has `preventOverflow: 'horizontal'`, which writes `overflow-x: clip` as well (the option moves the horizontal owner to the root, and an unclipped root lets the scroll spacer widen the page). The overflow is re-written whenever `preventOverflow` is in the payload, `undefined` included, and never on a nested grid. Never clip a container-driven width: the columns past it would be hidden with no scrollbar. **Only a longhand this module owns — `clip`, or unset — is ever written, on every path including the sized one.** An `overflow-x`/`overflow-y` already on the root element is not this module's: it clips too, and replacing it with `clip` takes away a scroll port that is still programmatically scrollable. The check is per axis and per path, and the sized path skipped it at first. Two states reach it, and neither is the obvious one: **a root instance's `rootElement` is a fresh `<div>`** (`core.ts:459`), so a container the host page styled inline is its *parent* and can never be stomped. What can is a **nested** grid, whose `rootElement` *is* the container it was handed, and the **`height: null` restore**, which copies the initial `overflow` back onto the element — after which any later payload took it away again, including a `width`-only one, on every wrapper commit since React and Angular re-send unchanged settings. Read the value through `inlineOverflow()`, never the longhand alone: jsdom records `overflow: hidden` on the shorthand and leaves both longhands empty, so a longhand-only read called the axis unset *in every unit test* while a browser expanded it. Option values go through `resolveRootSize()` in `src/utils/rootSize.ts` (grammar first, `CSS.supports` as the tail oracle, so jsdom resolves the documented forms without it); an unreadable value is ignored with a `warnOnce` keyed on option and value, and `updateSettings` puts the previous value back into the stored settings (`ignoredAxes`), so neither `getSettings()` nor the slot observer's `reapplyPixelRootHeight` reads a size the grid never used. `null` restores its own property from `dataset.initialstyle`, never the whole attribute, and is part of the option's public type on both axes. Two traps that shipped while writing it: jsdom keeps the `overflow` shorthand and its longhands apart, so write and read the longhands only; and `NonNullable<GridSettings['height']>` collapses the `'auto'` literal into `(string & {})` in a type test, so pin it through `Exclude<…, undefined>`. One thing this module does **not** own: a `width` in `columns`/`cells`/`cell` is a **column** width, read by `Core#_getColWidthFromSettings`, which honors it whatever the grid-level `width` is (a column width equal to it used to be discarded, DEV-270; column meta isolates `width` through `COLUMNS_PROPS_CONFLICTS`, so no cell inherits the grid value) — so the option's `@configScope` is `grid columns cells cell`, and narrowing it to `grid` documents away a working feature.
- **Row identity (`rowId`, `getRowId()`, `getVisualRowById()`, `getPhysicalRowById()`) lives in `src/core/rowIdentity/`, owned by Core, and it reads `dataProvider.rowId` straight from the settings (it wins over `rowId`), never through `getPlugin()`.** A key (string path or function) is read from the RAW source row (`DataSource#modifyRowData`, not `getSourceDataAtRow()`, which copies the row on every call), so it needs no storage: sorting, filtering, moving and trimming never touch row data, and undo of a removal rebuilds the row from the journal. (1) **The generated map is opt-in.** Always on, every grid would pay a full-length map plus a dense `deepClone` copy of it in every structural undo step (`captureValueMap()` in `translations/indexMapperSnapshot.ts`). (2) **Register it on `beforeInit`/`afterUpdateSettings` only, never lazily on a lookup**: UndoRedo drops its whole history whenever the set of index map names changes, so a lookup would wipe it at an arbitrary moment (turning the option on drops it too, like enabling a plugin). Do not add `rowId` to `DERIVED_INDEX_MAP_NAMES`, or undo of a removal brings rows back with new ids. The map is a `GeneratedRowIdsMap`, whose `init()` keeps the ids unless `loadData()` is running (`beforeLoadData`/`afterLoadData`) or the row count changed: `updateSettings()` re-initializes every row index map on a `columns` payload without `data` (the Vue wrapper sends exactly that whenever the columns change; React and Angular send `data` along, and a column change then restarts only the column mapper), and a plain map would hand out new ids each time. (3) **The reverse lookup is a cache that verifies every hit** (the row's current id must still equal the asked one) and rebuilds on a mismatch; a miss in a clean cache answers `null` at once. A change marks it stale instead of dropping it, so a lookup between two writes (the async-result loop: look up, write, look up) stays O(1) rather than reading every row; a miss in a stale cache rebuilds. It is marked stale from `afterChange`, `afterSetSourceDataAtCell` and the create/remove/load/update hooks (key mode only, registered and removed with the option: `setSourceDataAtCell()` skips building its hook payload while nothing listens to `afterSetSourceDataAtCell`, so an always-on listener costs every grid), and from the generated map's `change` hook. A new data write path that fires none of those leaves a newly written id unfindable until the next tracked change. (4) **`afterRowIdsRemoved` is a diff reported in a microtask, never from `afterRemoveRow`.** The first `beforeRemoveRow` (registered at `orderIndex: Number.MAX_SAFE_INTEGER`, so an earlier veto arrives as `false`) or `beforeLoadData`/`beforeUpdateData` of a call snapshots every id, and a `_registerMicrotask` callback reports the ids no row holds once the call has finished. Reporting from `afterRemoveRow` was the first cut and was wrong twice: a NestedRows detach fires `afterRemoveRow` for a subtree it adds back right after (so it reported live rows), and an UndoRedo restore of a reshaped source asks `beforeRemoveRow` for every change before it makes any (so ids read per removal came from indexes that only made sense after the earlier changes, and a vetoed restore left captures behind). The diff has none of those problems, and an empty diff is how a vetoed restore ends. A data load on a grid with an external data source (`hasExternalDataSource`, the DataProvider plugin) is not tracked: every page, sort and filter goes through `loadData()` and the rows it drops still exist on the server. The snapshot is taken only while the hook has listeners (`hasHook`), so a grid without one never reads its ids for it. DataProvider removes rows on the server and reloads the page (its `beforeAlter` takes over `remove_row`, so no `beforeRemoveRow` fires), so its removals are reported from `afterRowsMutation('remove')` with the ids of the payload. `Core#_registerMicrotask` drops an entry once it has run: it used to keep every entry until `destroy()`, so each validated edit and each data load grew `instance.microtasks` for the life of the grid. `afterRowIdsReset` fires when the effective key changes while rows had ids; an inline `rowId` function counts as a new key on every wrapper commit. Generated ids do not follow a NestedRows move or detach (the plugin rewrites the source tree instead of moving indexes), so that combination warns once. Pinned by `src/core/rowIdentity/__tests__/rowIdentity.unit.js` and the `rowId` specs of the React and Vue wrappers (only Vue reaches the `columns`-only re-init).

- **The held-modifier-key state is re-synced from every key event, and the event wins.** `shortcuts/recorder.ts` tracks Ctrl/Cmd/Alt/Shift in a module-level observer that `ShortcutManager#isCtrlPressed()` reads, and `Selection#setRangeStart()` consults whenever the caller does not state whether the selection is additive (arrow-key navigation is such a caller). Tracking presses on `keydown` and releases on `keyup` alone is not enough: the OS can consume a modifier's `keyup` — the macOS `Cmd+Shift+4` screenshot is the reported case (#6012) — and the key then stays held forever, so every arrow key adds a selection layer instead of moving the selection. `syncModifierKeysState()` therefore rewrites all four keys from `event.altKey`/`ctrlKey`/`metaKey`/`shiftKey` on **both** handlers before either touches the named key. Three consequences. (1) The sync must stay **before** the named-key press, which is a correction for browsers that do not set the flag on a modifier key's own `keydown` — reorder them and such a modifier can never be marked pressed. (2) A **synthetic** key event dispatched without those flags (a virtual-keyboard widget, a jQuery `trigger('keydown')`, an automation harness) now *releases* the modifier keys; that is the deliberate cost of making the event authoritative. (3) In tests, `test/helpers/keyboardEvents.js` rebuilds all four flags **per call** from only that call's keys, so holding a modifier in one `keyDown()` and pressing another key in a separate call without re-listing it drops the modifier — pass the whole combination in one call (`keyDownUp(['control/meta', 'b'])`). - **The focus does not always sit on the last selection layer — read it from `getActiveSelectedRange()`.** `SelectionRange#current()` and `#previous()` name the newest layers, which is *not* the same thing as the focused one: `setRangeFocus(coords, layerIndex)` records an active layer index without reordering `ranges`, and `#chooseNextSelectionLayer()`/`#choosePreviousSelectionLayer()` in `selection/transformation/_base.ts` rotate that index whenever Tab/Enter wraps past a layer's end with `autoWrapRow`/`autoWrapCol` and more than one layer. - **Never key selection or editing behavior on `event.detail`, and know that neither test suite can catch it if you do.** `detail` counts the clicks in the current sequence, so it separates a double-click's second click from a lone click — but *not* from a user deliberately clicking twice quickly, and the boundary between them is the OS double-click threshold, which the user configures. A rule that reads it therefore changes with click speed: DEV-2761 shipped a `detail > 1` guard for one review round, and it made "two Ctrl+clicks deselect a cell" silently stop working when the two clicks were fast, because the second one reported `detail: 2` and skipped the toggle. Both suites are blind to this. The legacy Jasmine helpers (`test/helpers/mouseEvents.js`) build events through jQuery's `$.Event(type)`, which never sets `detail`, so `jquery.simulate.js` passes its own default of **0** to `initMouseEvent` — `mouseDoubleClick` is two plain click pairs, indistinguishable from two separate clicks. Playwright covers only half of it: `locator.click()` pins `clickCount` to 1, so two of them always report `detail: 1` however fast they land, while `locator.dblclick()` does escalate — measured on 1.62.1, two clicks give `[1, 1]` and a dblclick gives `[1, 2]`. So a cadence-dependent rule needs **both** gestures to be exercised, and `dblclick()` is enough to produce the second click a real user's fast pair sends (a hand-rolled `page.mouse.down/up({ clickCount })` emits the identical sequence, so it buys nothing). `tests/e2e/ctrl-click-highlight.spec.ts` pins both cadences reaching the same state.
- **`blur` does not bubble, so a listener for it on the `documentElement` is dead code.** `recorder.ts` still registers its `onblur` net that way (bubble phase, `documentElement`), and it has never fired since #9878 (commit `6522285363`) moved it off the `window`: a real window-level blur is dispatched on the `window` itself and an element blur does not propagate upward. - **Writes to one cell that wait on a validator land in write order, through `core/writeLedger.ts` (DEV-3540).** Each `validateChanges()` call opens a ledger call (a sequence number) and registers the changes whose cell has a validator, keyed by VISUAL row and prop (`getCellWriteKey()`: the key names the cell `applyChanges()` writes through; a data accessor function is keyed by the function itself, so a column move between two writes cannot make two accessor columns share a key, and an unbound column falls back to the visual column). When the queue drains, `claim()` drops a change if a NEWER call has already applied a write to that cell, `settle()` marks the surviving ones applied only after `callback()` returned, and `release()` runs in the `finally`. Five rules. (1) Only an APPLIED newer write overtakes an older one, never a merely queued one: skipping on a queued write would lose the older value when the newer is rejected under `allowInvalid: false`. (2) A call whose source ends with `'Validator'` (`isValidatorCorrection()`) opens no ledger call: its write is the correction of the parent change, which must still apply and fire its own `afterChange`. (3) The cell meta is shared by every write to the cell, so it holds whatever the LAST validator to answer wrote. Each change therefore records its own answer (`answered()`, called from the `validateCell` callback in `queueValidators()`, after `afterValidate` has adjusted it), and `claim()` gives the cell the validity of the write that lands on it through `restoreValidity()`: an applied change gets its own answer, an overtaken one gets the answer the newer write left (`entry.valid`). Reading `cellMeta.valid` at `settle()` instead was the first cut and recorded the wrong write's result. `afterValidate` still fires for a dropped value, and so do `beforeChange` and `afterSetDataAtCell`, but `afterChange` does not. (4) An entry lives only while a call holds a write to the cell, so nothing needs cleaning on `destroy()`; a validator that never answers keeps its entry for the life of the grid, the same as it keeps the call hanging. (5) The rejection in `queueValidators()` removes the change from `changes` by identity, never by loop index (`lastIndexOf(change, index)`: a change only moves left, so a sync validator, which answers from the highest index down, finds it in one step): an earlier rejection shifts the list, so an index taken at registration points at the wrong change once a lower-index change has been rejected first. Known limit: a correction that a STALE validator writes late through a nested `setDataAtCell(..., 'xValidator')` is unledgered and lands after the newer value. - **Validator corrections via `setDataAtCell`**: If a validator calls `setDataAtCell` to write a corrected value (e.g. `correctFormat`), the source string **must end with `'Validator'`** (e.g. `'myCustomValidator'`). The suffix folds the correction into the change that triggered it, so that change still applies (with the corrected value) and fires `afterChange` as `edit`. Without the suffix the correction is a write of its own, made after the triggering change: it wins, and the triggering change is dropped without an `afterChange` (see the write-order bullet above; before DEV-3540 the original value overwrote it when the batch held async validators). - **A change waiting for a validator is dropped when `loadData()` replaces the data before the last validator answers.** Every validator answers in a microtask, so this covers a synchronous validator, a cell type's validator and `maxLength` too: `setDataAtCell(); loadData()` in one task drops the change. `setDataAtCell()` and `setDataAtRowProp()` capture `validationLoadGeneration` at their top, before `processChanges()` runs `beforeChange` and before `afterSetDataAtCell`, so a `loadData()` from a listener of the change itself drops it too, and `validateAndApplyChanges` (`core.ts`) skips `applyChanges()` when the generation moved: written, the change landed in the loaded rows at the same coordinates, usually another record. Only `applyLoadData()` advances it (so `_applySettingsAndData()` and the sheets bar's switch and workbook rebuild count too). The validation hooks still fire for a set the load overtook while its validators ran, `afterChange` does not, also when the load brings the same records back: the drop does not compare the data. A set whose generation is already stale when validation starts (a load from its own `beforeChange` or `afterSetDataAtCell`, or a stale correction) runs no validator at all: `validateChanges()` hands the set's generation to `queueValidators()`, whose loop checks it, so nothing marks a loaded record, counts in `_hasPendingValidation()`, or answers a later editor wait. A correction a validator writes (`*Validator` source) takes the generation of the validator call that writes it (read by `getChangeLoadGeneration()`), because the validator runs in a microtask, after a `loadData()` made in the same task, and the correction otherwise read the new generation, was validated against the loaded record, and was written into the loaded rows. A correction written while the validator runs takes `runningValidatorLoadGeneration` (set around the validator in `validateCell`). One written later, before the callback (after a timer or a request), is past that window, so `validateCell` also records the generation of every unanswered call made for a change, by the cell it validates, counted or not (a call a `beforeValidate` load overtook is not counted, yet its validator still runs and can still correct) (`unansweredValidatorGenerations`, property then visual row, released when the call answers or throws), and the correction takes the oldest unanswered call on the cells it writes: with calls from before and after a load on one cell, dropping a newer call's correction by mistake loses a correction, while taking the newer generation would write the older one's into the loaded rows. (3) `_endValidationWait()` does not run the editor's close callbacks: it returns them, and `applyLoadData()` runs them with `false` after `replaceData()`. Run inside the load with `true`, `EditorManager#prepareEditor()`'s callback prepared the editor against the replaced data. An `updateData()` that brings other records still gets the edit written into them. Code that must keep the edit rather than lose it (the sheets bar) asks the `@private` `_hasPendingValidation()` first and refuses to run while it answers `true`. The count behind it is per validator call in `validateCell` made for a change (`validateChanges` sets `isValidatingChange` around the call; `validateCells()` and its siblings hold no change and are not counted), released right before the answer writes its change (so an `afterChange` listener of the last answer reads `false`) or when the validator throws, never per `validateChanges` queue: a queue whose validator throws never drains, and counting queues left the count up for the grid's life. AutoRowSize listens at `FONT_REMEASURE_ROWS_ORDER_INDEX` (11), after AutoColumnSize, because the rows wrap in the columns' widths and the enable order does not hold: a plugin turned off and on again registers its listeners last. It also asks `isReMeasurePending()` rather than `inProgress`, so a column re-measure owed to the next render counts as running. Walkontable's oversized-row records are deliberately **kept**: without AutoRowSize nothing else knows the height of a row outside the rendered band, and `resetAllOversizedRows()` would draw every such row above the viewport at the default height, the same jump. Both auto-size plugins measure nothing while the grid is hidden, and a later draw measures only columns without a width, so on a hidden grid the handler waits for it to be shown (`fontRefreshVisibilityObserver`, an `observeVisibilityChangeOnce()` disconnected in `destroy()`; it fires when the grid enters the viewport). **The handler checks visibility again after the hook**: a listener can hide the grid (a tab switch), and the forced render then measured the on-screen columns inside the hidden root and wrote the minimum width for each, which no later draw repaired (a forced `render()` on a hidden grid does that on 18.1.2 as well); it skips the render and runs the whole re-measure again once the grid is shown. A grid with a box that is merely scrolled out of view is visible to `isVisible()` (`checkVisibility()`) and re-measures at once. It runs for every font the document loads, used by the grid or not, and for nested instances (an editor's sub-grid, the Filters value list) too. Filtering by the root's computed `font-family` was proposed and rejected: a font set on single cells through `className` or a renderer (the E2E fixture does exactly that) would never re-measure; the cheap re-measure above keeps an unrelated load affordable. Known gap: an open editor is not repositioned. jsdom has no `document.fonts`, so unit-built grids watch nothing. Pinned by `src/core/__tests__/fontLoad.unit.ts` and `tests/e2e/web-font-load.spec.ts` (a local system font with `size-adjust: 200%`, so no network). A test of the NestedHeaders handler has a trap of its own (`src/plugins/nestedHeaders/AGENTS.md`). A test of what the first chunk measures needs a grid whose on-screen columns have no cached samples when the font loads: the resize that follows the first draw of a grid without a fixed `height`, and the idle part of an init sweep past 50 columns, both force a render that re-walks and caches them (the `&wide=1&height=1` variant of the fixture).
- **A native date input reports `''` for an INCOMPLETE date, the same as for a cleared one, so `DateEditor#finishEditing()` restores the cell instead of committing it.** `getValue()` reads the input's value, and a half-cleared date (Chromium, WebKit: `validity.badInput`) or an editor opened by typing a digit (the input cannot take the character, and Firefox reports `badInput === false`) both read `''`, which the validator accepts, so the cell was erased. `#isIncomplete()` keys on `badInput`, or on an input that was never seeded with a date (`#dateSeeded`, set in `setValue()`; a quick-edit open, also after F2 switches to full edit) with no `input` event (`#inputEventFired`). Both flags reset in `beginEditing()` while the editor is VIRGIN, not in `prepare()`: Escape closes the editor without moving the selection, so the next keystroke on the same cell opens a new session without a `prepare()`. A deliberate full clear still clears the cell. `allowEmpty: false` with `allowInvalid: false` leaves the decision to the validator, which keeps the editor open; with the default `allowInvalid` the empty value would be saved and marked invalid, so the date is restored. Every way out of the editor (Enter, click, Tab, Ctrl+Enter) restores the date, and a Ctrl+Enter fill writes nothing. An empty edited cell has no date to keep, so only a `badInput` input counts there, and only for Ctrl+Enter; an untouched empty cell still fills the selection. Known gaps: a partial clear in Firefox has no signal and still commits `''` (headless Firefox would not clear a segment, and Firefox could not be launched locally, so the Firefox leg of the spec is unverified outside CI); a clear made through the editor API in quick-edit mode (`TEXTAREA.value = ''` with no `input` event) keeps the old date. Pinned by `tests/e2e/date-editor-incomplete-input.spec.ts`; the segment-clearing cases are Chromium-only.
- **`DateEditor#focus()` must call `focus()` before `select()`: Firefox does not move the focus on `select()` for `type="date"`.** Chromium and WebKit do, which hid it. Without the focus call `document.activeElement` stays on the cell and the typed digits are dropped. `preventScroll` keeps the page from jumping. `TimeEditor#focus()` and `IntlDatetimeEditor#focus()` do the same. The `imeFastEdit` refocus (`FocusGridManager#refocusToEditorTextarea()`) is a separate path with the same rule, because it moves the focus without opening the editor and so never reaches an editor's `focus()`: it calls `focusElement()` before `select()`, and calls `select()` only when the refocus element has one (a `setRefocusElementGetter()` element need not). Pinned by `tests/e2e/intl-date-editor-ime-fast-edit.spec.ts` (Firefox leg) and the `refocusToEditorTextarea` cases in `src/__tests__/focusManager.spec.js`. `close()` of all three editors calls `hideNativePicker()` (`editors/utils/showNativePicker.ts`), which blurs the input after the base `close()` while the picker is open, because Firefox keeps the picker open otherwise, then puts the focus back on the highlighted cell. The picker state comes from `:open` (Firefox 136, Chrome 133); older engines throw on it and are treated as open. A double-click is the path that leaves a picker to close. Pinned by `tests/e2e/date-editor-keyboard-focus.spec.ts` (date) and `tests/e2e/native-picker-editor-keyboard.spec.ts` (all three), whose Firefox legs run in CI.
- **The date, time, and datetime editors show their native picker only for a pointer open or an open with no event (`showNativePicker()` in `editors/utils/`); a keyboard open (Enter, F2, typing) leaves it closed.** While Chromium shows a picker it takes the keys: a capture-phase `keydown` on the window gets no Tab, so Tab after Enter left the selection on the cell. `open(event)` reads `event.type` (`key*`), not `instanceof KeyboardEvent`, so an event from an iframe counts. The API open with no event keeps the picker. The keyboard way to show it is the browser's own (Alt+ArrowDown in Chromium, pinned in `tests/e2e/native-picker-editor-keyboard.spec.ts`; the Firefox and WebKit key was not measured). Any spec or capture that needs the picker shown must open by double-click: `visual-tests/tests/js-only/complex-demo/rtl/open-date-editor.spec.ts` does, and its goldens change only if the picker's look does.

## Accessibility

The bar is WCAG 2.2 Level A and AA, the target level (the published conformance report states conformance per criterion), and the `handsontable-a11y` skill is the workflow: an accessibility plan before the code, the build rules, the proof, and the fix loop for a scan finding. The rules a core change must not get wrong:

- **Roles and ARIA attributes go through `src/helpers/a11y.ts`**, written with `setAttribute(element, [A11Y_…()])` from `helpers/dom/element`. A missing attribute gets a helper there, not a string literal at the call site.
- **A role keeps its required parents and children.** Menus and lists are Handsontable grids, so a widget role on a `td` needs `role="presentation"` on the `table`, `tbody` and `tr` around it; the baseline's `menu-roles`, `menu-separators` and `filters-listbox` issues are what skipping it looks like.
- **Names and announcements are i18n phrases** (`src/i18n/constants.ts`), like every user-visible string. A change without a focus move is announced with `announce()` from `src/utils/a11yAnnouncer.ts`, which defaults to `'assertive'`: a status message passes `'polite'`, and `assertive` is for errors.
- **Keys go through a shortcut context and focus through a focus scope** (the focus-scope bullets in Common Pitfalls above). A surface that takes focus returns it to the cell or its opener on close.
- **`ariaTags: false` turns off the ARIA roles and attributes, and what is set alongside them.** The `tabindex="-1"` on cells, headers, and menu items is written only while ARIA is on (`src/3rdparty/walkontable/src/render/cells.ts`, `columnHeaders.ts`, `rowHeaders.ts`, `src/utils/menu/menu/menu.ts`), so with the option off browser focus no longer moves onto them, and the menu styles keyed on `aria-expanded` (`src/styles/components/plugins/_dropdown-menu.scss`, `src/styles/components/editors/_dropdown-editor.scss`) stop distinguishing an open submenu. No JavaScript reads an `aria-*` attribute back to decide behavior; the option's JSDoc in `metaSchema.ts` says the same.
- **A new plugin or editor is accounted for in the scan.** It adds its entry to `tests/a11y/coverage.mjs` (the scanned pages, why it draws nothing, or a counted gap), and the root `test:tooling` fails until it does; a plugin with UI adds a page to `tests/a11y/pages.mjs`.

## Performance

- Batch scroll updates with `requestAnimationFrame`. Target 60fps with 100k+ row datasets.

## API Design

- Expose all necessary methods in the public API. Keep them discoverable and documented in guides.
- Every configuration option must fit the cascading configuration model (`cell` → `column` → `global`).
- The public API must give good code completion in IDEs and AI assistants.
- **`Handsontable.helper` and `Handsontable.dom` are internal, so a shared helper may land there.** `src/index.ts` copies every non-`_` export of the `HELPERS` and `DOM` module lists onto those two objects, and `base.ts` types them the same way, but neither has a page in the API reference. A new export is therefore additive: no changelog line, no docs page, no deprecation cycle — see **`.ai/BREAKING-CHANGES.md`** for the exceptions (a member a guide teaches, such as `Handsontable.dom.empty()`, is public in practice).
- **Narrowing a public callback option's parameter from `any` is a breaking change on three axes.** Full rules, the per-axis table and the shapes that were measured: **`.ai/BREAKING-CHANGES.md`** (it is monorepo-wide, so a wrapper prop or a hook signature is covered by the same rule). The short version: assignment contravariance (TS2322, cleared by method syntax under `strictFunctionTypes`), minimum call arity (TS2555, hits property and method syntax alike), and optionality (TS2345/TS18048). Assignability and callability are separate checks, so a type test that only assigns callbacks will not catch the arity axis. `sanitizer` (DEV-2620) is the worked example: its signature was left untouched and `SanitizerContext` published as an opt-in annotation instead.
- **Widen a public string union with `| (string & {})`.** It keeps editor completion on the known literals while leaving arbitrary strings assignable, so a consumer branching on a value added in a later release, or sharing the callback with another library, still compiles. It survives declaration emit intact. The trade is that the union can no longer reject a wrong value: a misspelled comparison compiles into a dead branch, so say so wherever the type is documented.
- **A `| (string & {})` union cannot be pinned by assigning to it.** Every string satisfies it, so `const x: MyUnion = 'header'` passes against an empty or misspelled union and proves nothing. Pin the literals by exhaustiveness instead — `Record<KnownContext<MyUnion>, true>` with `type KnownContext<T> = T extends string ? (string extends T ? never : T) : never` — which fails on a literal added without a case (TS2741), one dropped from the union (TS2353) and one misspelled (TS2561). Add one plain `const pinned: KnownContext<MyUnion> = 'header';` alongside it: the `Record` alone cannot see the union collapsing to bare `string`, because `KnownContext` then yields `never` and `Record<never, true>` accepts any object. `Exclude<MyUnion, string & {}>` does **not** work: each literal is itself assignable to `string & {}`, so it erases the whole union. Example: `src/__tests__/core/sanitizer.types.ts`.

## Build

`npm run build`

| Output | Path |
|---|---|
| UMD / minified bundles | `dist/` |
| ES and CJS modules (used by wrappers) | `tmp/` |
| Compiled CSS | `styles/` |
| Compiled language files | `languages/`, `dist/languages/` |

Two build variants: `handsontable.js` (base, external deps) and `handsontable.full.js` (includes HyperFormula). The E2E runner loads `dist/handsontable.js` - rebuild after changing `src/`.

**Every minified file our build emits must be 7-bit ASCII, and the non-minified bundles must at least parse, whatever charset the page uses.** A page served without a UTF-8 charset decodes a script as windows-1252, so any raw UTF-8 byte in a bundle changes the strings and regular expressions it holds. In the full bundle that shrank HyperFormula's letter class and made sheet names, named expressions, and function names with letters such as `ó` or `ł` stop parsing (DEV-111). The SWC minifier re-emits every `\uXXXX` escape above U+00FF as a raw character unless `format.asciiOnly` is set, so every `SwcJsMinimizerRspackPlugin` comes from `createSwcJsMinimizer()` in `.config/helper/swc-minimizer.js`. The files `production.js` copies from HyperFormula (`dist/hyperformula/`) pass through that minimizer too, which is what cleans HyperFormula's own raw `ʯ` out of them. Three things back it. (1) `assertAsciiOutput()` (`.config/plugin/rspack/assert-ascii-output.js`) fails each minified build when an emitted `.js` asset still holds a byte above `0x7F` after minification. It catches what the minimizer option cannot: a dependency's raw text, a config that falls back to Rspack's default minimizer, and a tagged template. (2) `asciiOnly` cannot escape a **tagged** template literal, because that would change the tag's `strings.raw`. So a non-ASCII character inside `` toSingleLine`...` `` must be written as a `\u` escape, which works because `toSingleLine` reads the cooked strings. Keep `String.raw` text plain ASCII, because it keeps an escape as literal text. (3) The non-minified `dist/handsontable(.full).js` is not minified at all, so a raw non-ASCII **identifier** there is a `SyntaxError` on such a page and the bundle does not load. That is how an unquoted `zł:` key in `importFile/inference.ts` broke it; the key is now `'z\u0142'`. Two `no-restricted-syntax` selectors in `.eslintrc.js` reject a raw tagged template and a non-ASCII identifier. `test/__tests__/asciiOnlyBundles.unit.js` runs the checks of `test/helpers/asciiOnlyBundlesCheck.mjs` in a child process (`node --test`), because `@rspack/core` is a native binding whose threads outlive a Jest worker, which force-killed a worker on every full run, and the root `test:tooling` suite installs no dependencies; they pin the minimizer option and the output check, and fails if any other file under `.config/` names the minimizer plugin. Raw text in ordinary strings and comments of the non-minified bundles is still there: it decodes wrongly on such a page, but it parses.

**A stylesheet change is not applied until the BUNDLE is rebuilt too, and skipping that fails silently.** `build:styles` compiles the SCSS into `styles/` **and** regenerates `src/styles/handsontableStyles.ts`, which exports the whole base stylesheet as a string; `build:umd` then bundles that string into `dist/`, and the grid injects it at runtime. So a `_base.scss` edit followed by `build:styles` + `build:themes-css` alone leaves the OLD rules being injected from a stale bundle, on top of the freshly built `styles/*.css` the page also links - and the injected copy can win. Nothing errors, and grepping `styles/handsontable.css` for the change reports success while the browser still applies the old rule. The failure mode that costs the most is a **negative control that passes**: reverting a CSS fix and re-running without `build:umd` re-tests the fix and reports the test as unable to catch the bug. After touching any `src/styles/**`, rebuild `build:umd` (and `build:umd.min` for the `-min` legs), or just run the full `npm run build`.

**The non-minified base stylesheet goes through lightningcss too, with the `BROWSERS_LIST` targets.** `.config/styles-development.js` runs `builtin:lightningcss-loader` between `css-loader` and `sass-loader`, and `styles-production.js` extends that config and minifies with the same targets. Before, only the minifier ran lightningcss, so `styles/handsontable.css` and the copy `dist/handsontable.js` injects shipped with no vendor prefixes. Safari applies only `-webkit-user-select`, so every `user-select: none` did nothing there on those two outputs (sheet tab names got selected while dragging). Do not drop the loader to "keep the dev CSS untouched". With it, both files carry the same prefixes (6 `-webkit-user-select` each at the time of writing). Two side effects are expected: the dev file loses its comments (the `/*!` banner stays) and `::after` is written `:after`. Running lightningcss twice on the minified file only reorders declarations that do not conflict. `tests/e2e/sheets-bar-bundle-css.spec.ts` pins it on WebKit, with a fixture that links no base stylesheet: the minified one would bring its own prefixes and hide the bug.

**A `.gitignore` rule for something that exists only at the package root starts with a slash.** Git applies a rule with no slash, or only a trailing one, at every depth. Unanchored, `languages/` (meant for the `build:languages` output) matched every file in `src/i18n/languages/`, so a new language file never appeared in `git status`, and `dev*.ts` (meant for local dev pages) did the same to any `src/**/dev*.ts`. The monorepo root's own `dev*.html` and `dev*.js` hid every such name in the package too. So every rule here for a dev page or for an output directory at the package root starts with a slash, and in the root file `/dev*.html` and `/dev*.js` cover the repository root only. A slash in the middle of a rule anchors it too, to the directory of its own `.gitignore`, so an output below the package root needs a rule that names its path, as `test/dist/` and Walkontable's `dist/` and `test/dist/` rules do. The comments in `handsontable/.gitignore` explain the rules whose reason is not obvious, such as `/es/` and `/commonjs/`. The repository's `scripts/__tests__/gitignore-scope.test.mjs` (the root `scripts/`, not this package's) pins every rule here except `node_modules/` and `npm-debug.log`, which the root file's own rules shadow. It lives in the root `test:tooling` suite, which CI runs on every pull request, because the Unit job's path filter skips a change that touches only a `.gitignore`. It fails when an ignore rule matches a tracked file of this package or one of its probes for a new source, or stops matching an output, which matters because the release jobs commit the built tree with a bare `git add .`. SonarCloud skips every file git ignores, tracked or not, so the dictionaries were missing from its analysis while `languages/` matched them; `sonar.cpd.exclusions` in `sonar-project.properties` keeps them out of its duplication check.

## Build and test scripts

All `npm run` entries are thin shims that delegate to `scripts/run.mjs`. Task commands and pipeline dependency graphs live in `scripts/tasks.json` - edit that file to add, remove, or modify any build/lint/test step. The dispatcher supports three modes:

```
node scripts/run.mjs <task>                     # run one task
node scripts/run.mjs --sequential <pipeline>    # run pipeline steps in order
node scripts/run.mjs --parallel <pipeline>      # run pipeline with DAG scheduler (used by build)
```

Extra args after `--` flow through to tasks with `"passthrough": true` in `tasks.json`. `--testPathPattern=` and `--theme=` are also propagated as env vars to all pipeline tasks so the dump step and Puppeteer compute the same run-ID filename.

## TypeScript

- Type check: `npm run test:types`
- **Never type-check with `npx tsc`.** npm can resolve the deprecated `tsc` placeholder package instead of the compiler, and it prints "No errors found" without type-checking anything. Use `npm run test:types`, or `./node_modules/.bin/tsc --noEmit -p tsconfig.json` from `handsontable/`
- **`tsc -p tsconfig.json` does not compile the `*.types.ts` regression files.** Those files live next to the code they pin, in `src/**/__tests__/` (and `src/__tests__/`), and `tsconfig.json` excludes them. They compile in their own project, `test/types/tsconfig.json`, whose `include` is `../../src/**/*.types.ts` and whose `paths` resolve `handsontable` to the generated declarations in `tmp/` (which is why `test:types` depends on `build:types` and `downlevel:types`). So a source-level type change that breaks one — widening `XlsxEngineKind` broke the `importFile` type test's `'exceljs'` pin (DEV-3011) — passes the main config and fails only in `npm run test:types` and CI. After changing a public type, run `npm run test:types`, not just the main config. The direct `./node_modules/.bin/tsc -p ./test/types` form checks whatever `tmp/` already holds, so it only sees a source change after `build:types` and `downlevel:types` have run
- `readonly #field` syntax IS valid TypeScript — do NOT convert `#field` to `private readonly field` to add `readonly`
- When removing `as T` casts (e.g. SonarCloud S4325), always rerun `npm run test:types` — some casts are load-bearing
- Prefer fixing function/method signatures or making them generic over adding `as T[]` casts at call sites
